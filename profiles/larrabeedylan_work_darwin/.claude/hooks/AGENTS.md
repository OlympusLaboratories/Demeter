# `hooks/` — the hook scripts and the notification channel

Two hooks live here and both are registered in every profile's `settings.json` by a
`$HOME/.claude/hooks/<name>` path, so they resolve on any machine.
`link-worktree-session.py` files a worktree's transcripts under the main checkout's
project slug. `notify.py` is the notification channel: it pushes to the user's phone on
`Stop`, `StopFailure`, `Notification`, and `PreToolUse` for `AskUserQuestion` and
`ExitPlanMode`.

Three invariants hold across everything here, and the root `CLAUDE.md` states them.
**Every path logs and exits 0** — a hook that fails is invisible, so a wrong gate and a
broken token must be distinguishable in `~/.claude/notify-state/notify.log`.
**Nothing here holds a turn open**: one HTTP POST and exit. And **the channel is one-way**
— a notification says *come and look*; it is never the thing that lets the user answer.

Delivery is the only transport-specific part: Slack and Telegram differ in how a reply
notifies, which is why `scripts/notify-send.sh` is allowlisted out of the profile
transform while composition is shared.

## What an edit here has to know

- **A rule telling a skill to include the change request's link is an instruction a model forgets, so the hook finds the link itself**: pings routinely named a change request — "shipped (MR #11)", "working the review" — with no URL and often no number, leaving the user to hunt for it from a phone, which is the one place hunting is most expensive. Both the `ping` skill and `autopilot` already *said* to include it; saying it is what failed. `notify.py` reads the URL out of the session's own transcript and appends it to any body that carries no link. **The link is taken from the forge's own answer rather than from prose**: `html_url`/`web_url` is a key only the API helper emits, so a worked example, a fixture, or a link to somebody else's change request cannot reach it — and it is the only signal that stays correct when the session's checkout and the change request belong to **different repositories**, which is the ordinary case for a run driven from one clone against another. A transcript carrying no such answer falls back to the most recent URL bearing the session remote's own `owner/repo`, resolved from `git remote get-url origin`, because **recency alone picks the wrong URL**: the first implementation returned `gitlab.com/o/r/-/merge_requests/9` from a test string echoed minutes earlier, against a session whose real change request was `merge_requests/10`. **Nothing is answered from the cache while a scan can answer instead.** Caching the first URL found read as free — "it cannot change for the life of the session" — and is wrong twice over: a session merges one change request and opens the next, so the cached value is the oldest rather than the current one; and the cache feeds itself, since reading the state file back into the transcript makes the stale URL the most recent URL in it. Observed exactly that way — every ping for hours carried a merged change request belonging to a different repository. The cache survives only as the answer for a scan that found none. One case is knowingly left through: a session editing **this hook** with a keyed fixture in a tool result, where the fixture is indistinguishable from the real thing.

  **Recency within the forge's own answers was still wrong, and the repo filter only existed on the fallback.** `change_request_answered_in` returned `found[-1]` of *every* keyed URL in the window, so any transcript naming more than one change request — a listing, a stack's base, comment URLs on something else, a review bot's payload — handed over its last entry. Observed on this machine: a session titled "OLY-13 Fix and Merge" holding Demeter `pull/23`, while OLY-13 had landed as `pull/22`. The repair is a **preference order rather than a filter**, and the distinction is the whole of it. Hard-filtering tier 1 on the session's `owner/repo` is the obvious fix and destroys the one case this tier exists for — the cross-repository run the paragraph above calls ordinary — so the order is: the record opened from the session's **current branch**, then one carrying the session remote's slug, then a **lone** cross-repository answer, and nothing at all when a listing matches none of them. That last clause is what stops a foreign `pr list` winning by default while a single foreign answer still does. **Each tier gets its own `scan_tail` pass, and that is the whole of why the order works.** Evaluating all three inside one finder silently degrades the order to *preferred within the tail chunk*: `scan_tail` reads the last 256KB first and returns on the first answer, so a slug-only record near the end beats the branch-tagged record that opened the session. Measured on a 497KB transcript — the branch's own change request lost to an unrelated one 77 lines from the end, which is the exact defect class this change exists to remove. Three passes cost three scans of a tail that is already in the page cache, and each widens independently, so the branch match wins from anywhere in the file. **The branch and the state cost nothing to know**: the forge helper emits one flat object per change request and the keys naming both are siblings of the URL — `head` from `create-pr`, `source_branch` and `state` from `pr-info`, and `pr-for-branch` lists only open ones — so `change_request_records` reads them out of the transcript rather than calling the forge. That matters more than it looks: the ticket asking for an open-only link described the state as available "from the forge helper", and a live call here would be a second network request inside a hook whose first invariant is one POST and exit. A record the transcript shows **closed or merged** is dropped at every tier, and each tier needs its own check for a different reason. The prose scan needs one because the regex otherwise re-finds the URL inside the very answer that declared it closed. **The cache needs one because it outlives the evidence**: both scans correctly reject a merged change request, fall through, and the cache then hands back the exact URL they just rejected — found by running the code rather than reading it, and the reason `change_request_closed_in` exists. An **absent** state is unknown, not closed, so suppressing on it would have silently deleted both fallback tiers; a cached URL the transcript says nothing about still answers.

  **Neither marker had an age bound, and one of them was never read at all.** `cmd_gate` wrote `{"url", "at"}` and nothing anywhere read `at`, so a plan gate recorded many turns earlier was still appended verbatim to the next `Stop` — the reported "link that was only relevant many messages ago". The TTL is not a free parameter: the three retentions in this file's plan-gate section — a failed send, a rate-limited turn, quiet hours — are a contract, and a stated quiet-hours window can run eight hours or more, so a threshold under that would silently break the guarantee it sits beside. 12h for `gate_pending`, 4h for the `change_request` cache, which is only ever the answer for a scan that found nothing. A marker carrying **no** timestamp is kept rather than aged out, since an absent field is an older writer rather than an old plan. The cache reader accepts both the bare string it used to be and the `{url, at}` it is now, so no state file is thrown away.

  **A URL this hook records has to look like one.** `cmd_gate` accepted any non-empty string, and `mark_gate` grepped `https?://\S+` out of arbitrary publisher stdout and took the last match. Together they are how `https://example.invalid/abc` reached a real notification: `tests/check-publish-artifact.sh` ran against the developer's own `$HOME` in call sites that had not stubbed `NOTIFY_HOOK`, so the test's placeholder was written into live session state and the next turn end appended it. Commit `9d003cb` isolated the test; these are the two gates behind it. `cmd_gate` requires http(s), a host with a dot, no whitespace, and refuses the RFC 2606 reserved TLDs (`.invalid`, `.test`, `.example`, `.localhost`) — which is exactly what a placeholder is — then logs the rejection and exits 0 like every other path here, leaving any gate already pending untouched. `mark_gate` stops scanning for a URL anywhere in the output and takes the publisher's **last line**, accepted only when that whole line is a URL, which is what the publisher actually prints.

  **The append fires on two conditions now, and the old one was wrong in both directions.** It used to append whenever the body contained no `http` at all. So a line about a cron migration was given a change request's link it never mentioned, and a line naming a change request *beside* a published-plan URL was given none — because `"http" in body` cannot tell a plan page from a pull request, and the one link on the lock screen the user could act on was the one it suppressed. The body must now **name** a change request, and must not already carry a **change-request** URL. Two traps in the naming regex. It lives in a file the profile transform rewrites, so a literal `MR` or `merge request` would arrive on the home side as a duplicated alternative — writing it `\b[MP]R\b` and `\b(?:pull|merge)\s+requests?\b` spells neither substitution's left-hand side and is what keeps `notify.py` byte-identical across all three copies. And the bare token is case-**sensitive** while the numbered form is not, because `\bMr\b` under `re.I` matches a person's name.

  **`summarize` rewrites the body before both URL injectors, and nothing checked its work.** `SUMMARY_PROMPT` politely asks the model to reproduce a URL verbatim; the word-count trim could then cut one off the end of the line regardless. Either failure produces a notification naming a change request with no way to reach it, and a *mangled* number is worse than a missing URL because the result is syntactically valid, satisfies the suppression guard above, and keeps the correct link out. So the output is measured against the input: every URL the summarizer was given is re-extracted from its answer, and one that did not come back is re-appended **after** the trim, which is what makes the trim incapable of being the thing that removed it. A URL that survived is not duplicated. A mangled one is left where it is with the real one added beside it — dropping text the model produced is the riskier repair, and the body is read, not parsed.

  **Four details in `restore_urls` are each load-bearing, and the first two were wrong in the version this replaced.** Presence is tested by **set membership over `urls_in(line)`, never by substring**: `".../pull/7" in ".../pull/70"` is true, so a substring test treats a mangled number as proof the real URL survived and silently drops the correct link — precisely the failure the function exists to prevent, and it made the test for it pass vacuously. The source is the **un-windowed** `strip_markdown(text)`, not `window()`'s output: `window()` cuts at 5333 characters and a URL straddling that cut becomes a fragment, so reading the windowed text appended `https://github.com/ow` to a real notification. The model only ever sees the windowed copy, which is unavoidable; what is restored is the whole URL from the full text. The append is **capped at `RESTORE_URL_MAX`**, because a body naming a dozen links otherwise turns a 68-word notification into a wall of them. And the cap **ranks change-request URLs first**, so the one link the user can act on is never the one the cap discards.

  **A bare `#123` no longer counts as naming a change request.** It was in the first version of the naming regex and it fires on "shipped release #3", "closed issue #412" and every other numbered thing, which is the Part D defect wearing a different hat. The trade is deliberate and worth stating: a body whose only reference is `#7` now gets no link. Every body this repo's skills actually write says `PR`, `MR` or "pull request", all of which still match. `notify.py --ping` runs this resolution for the `ping` skill's own message, so the deliberate path gets the link by **not** composing its own envelope: it reaches this code instead of reimplementing it, and the append happens on the one path both kinds of notification share. `--change-request <session-id>` stays as the standalone query.

### Hooks

One script per hook under `.claude/hooks/`, duplicated across profiles like `scripts/`. Two live there: `link-worktree-session.py` and `notify.py`. Register it in every profile's `settings.json` using `$HOME/.claude/hooks/<name>` so the path resolves on any machine. **Claude Code spawns hooks with a bare `PATH`**, not your shell's — a `#!/usr/bin/env python3` hook resolves at your prompt and never under mise, and the failure is silent from the user's side, so the installer probes each hook under `env -i PATH=/usr/bin:/bin` rather than trusting that linking it was enough. `link-worktree-session.py` additionally needs a **backfill** at install time: linking it only arms future sessions, while every transcript written before this run is still filed under its worktree's own project slug where the main checkout's window never looks. It makes each worktree's `~/.claude/projects/<slug>` a **directory symlink** to the main checkout's, never per-file links: Claude Code 2.1.296's panel lists only the main slug and opens transcripts with `O_NOFOLLOW`, so a symlinked transcript is dropped after every reload, while a symlinked directory turns Claude Code's own move-on-`EnterWorktree` into a no-op and leaves each transcript a real file

### Notifications are one-way, and that is a property of hooks, not a shortcut

`notify.py` pushes to Slack (work) or Telegram (home) on `Stop`, `StopFailure`, `Notification`, and `PreToolUse` for `AskUserQuestion|ExitPlanMode`. Replying from chat is impossible for the cases that matter — a permission prompt and an `AskUserQuestion` are blocking UI that only the session's terminal can clear. A `Stop` hook *can* return `{"decision":"block","reason":...}` to resume a finished turn with text from elsewhere, which is the one case chat could serve; it is deliberately not built, because it is the only design here that could hold a turn open, and a session that stalls waiting on a notification is strictly worse than one that merely did not tell you about itself. Everything therefore does one HTTP POST and exits. Keep it that way: the `thread` field in the envelope is the seam to add replies later without reshaping anything

### Telling the user and letting them answer are two channels, and a skill can arm only one of them

a ping says *come and look*; what lets the user act on it from a phone is Claude Code's **Remote Control**, which forwards the live session to claude.ai and the Claude app and can clear a blocking permission prompt or an `AskUserQuestion` from there. The obvious design — `/ping` sets the remote session up and `/ping off` tears it down — **cannot be built**: Remote Control is established by the `/remote-control` slash command, a slash command is typed by the user, and an agent has no way to run one in its own session. Writing `remoteControlAtStartup` reaches only sessions started afterwards, and the connection state cannot be read back from inside the session either, so a skill cannot even report honestly on whether it is up. It is therefore armed at **startup** — `remoteControlAtStartup` is `true` in every profile that ships a `settings.json`, and that file symlinking to `~/.claude/settings.json` is what makes it count: the key is honoured at user and managed level, while a `true` in a project or local `settings.json` is **ignored** and only a `false` there has any effect. The Pi ships no `settings.json` and needs none, since its sessions are spawned by a `claude remote-control` server. The alternative considered was a reminder line in the ping telling the user to run `/remote-control`, and it fails in precisely the case the feature exists for: the ping that matters most is the one an `autopilot` run sends hours after the user walked away, where nothing printed in the terminal will ever be read, and an instruction they cannot see reads in the run report as though it had been followed. Two corollaries. `/ping off` **disconnects nothing** — the connection was never the skill's to make, and dropping it would cut off a session the user may still be driving from the phone. And a ping must **never claim the session is answerable from the phone**: the startup setting is the reason it usually is, not evidence that it is this time, since a box with no claude.ai login, a gateway `ANTHROPIC_BASE_URL`, or an org policy toggle starts without it and says nothing

### A notification is only as good as its gate

with a dozen sessions live, an ungated `Stop` hook is indistinguishable from no notifications at all. The primary gate is now **opt-in arming** (below); `min_interval_seconds` per session and the suppression of anything carrying `agent_id` apply always, since subagents `Stop` constantly, and `min_turn_seconds` (a turn shorter than this was you at the keyboard, not you away from it) survives only as the fallback gate when `only_when_armed` is `false`. Turn length is measured from the **last handoff back to you**, which is *not* the last freely-typed prompt: answering an `AskUserQuestion` or rejecting a plan returns control just as much, and measuring only typed prompts reported a 20-minute turn as 24 hours. `handoff_epoch()` therefore correlates `tool_result` blocks against the ids of `AskUserQuestion`/`ExitPlanMode` `tool_use` blocks. It scans the transcript backwards in widening windows rather than a fixed tail, because a fixed tail misses the prompt on exactly the long turns worth reporting. `handoff_at()` exposes that same epoch absolutely rather than as a duration, because the opt-in gate needs to compare it against a timestamp. **The one kind of event no gate may swallow is one where the session is blocked on the user**, and `BLOCKING_KINDS` (`question`, `permission`) therefore clears the arming requirement — see the bullet after next, where the reasoning sits

### Notifications are opt-in per session, and `/ping` is the opt-in

the automatic hook is off in every session until the user asks for a ping, which writes `armed_at` into that session's state and switches it on. The reason is the gate bullet above taken to its conclusion — `min_turn_seconds` is a *proxy* for "you walked away", and a bad one: a 60-second floor fires on most substantial turns while the user is sitting right there watching, which is precisely how a notification channel becomes something they stop reading. Asking for a ping is not a proxy, it is the gesture itself, so it is what the hook triggers on. Three properties make it safe to leave armed. It is a **latch, not a timer**: only an explicit `/ping off` clears it, and the first version of this got that wrong by inferring the user had returned from their next prompt, from `back`, or from time passing. All three are wrong for the same reason — answering in chat and then walking away again is the normal way the feature is used, so a prompt is not evidence of presence, and a wrong inference here fails silently in the one direction that matters: the session goes quiet precisely when it was being relied on, and nothing reports that it did. The latch belongs to the user, never to the skill and never to the hook. It is **per-session, never global**, so a ping from one of a dozen sessions opts in only that one; `away` remains the global override that notifies for everything regardless. And the arming is written **only on the send's success path**, since a session silently opted in to notifications the user was just told did not go out is worse than either outcome alone. `armed_at` is written whether or not a thread id came back, which is why it sits outside the `if thread:` branch — a transport that cannot thread returns no id, and gating the arming on one would leave the session mute on exactly the machines where threading is unavailable

### The latch gates news, never stuck, and the gap was found by a plan gate that went unannounced

`only_when_armed` was applied to every event kind, so an unarmed session stayed silent through its own `ExitPlanMode` — observed here, `skip: session not armed` logged against the approval gate of this very change, on a `/fix-linear … --merge` run where the user had plainly said they were leaving. The near-miss fix is the instructive one: `autopilot` does arm the session, at its Step 0d, but a fix-skill hand-off reaches that at **Step 6, after implementation**, so every gate in Steps 1–5 sits ahead of the arming — and moving the arming earlier would have fixed autopilot runs while leaving a `/review-code`, a `/security-audit` remediation gate and every future skill just as mute. So the carve-out belongs in the hook, and it turns on a distinction the original gate missed: the latch is right for *this session has news*, since a finished turn keeps until the user is back, and wrong for *this session will do nothing at all until you act*, where silence costs an unbounded wait and a buzz the user is present for costs one ignored buzz. Four things keep it from undoing the opt-in. It **notifies without arming** — `armed_at` stays unwritten, because the latch belongs to the user and a hook that set it would be the silent wrong inference the bullet above forbids; the session's eventual `Stop` is still mute. **`idle` is excluded**, since `idle_prompt` is a timer that fires on any session left at a prompt rather than a gate the session ran into, and including it would buzz for every open window. **`events.question`/`events.permission` and quiet hours still outrank it**, so a real off switch stays real and a stated sleeping hour is still a preference rather than a gate on worth. And **the log names the path** — `sent question for X (…; unarmed: blocking gate)` — because a notification arriving in a session nobody armed is otherwise indistinguishable from a broken gate, which is the same reason every skip is logged. `notify_when_blocked` defaults `True` in `DEFAULTS` and merges under `~/.claude/notify.json`, so an existing config needs no re-seeding

### A published plan is a promise of a question, and the hook holds the skill to it

The carve-out above only fires on a gate the session actually ran into. It does nothing about the adjacent failure, which has also happened here: the plan was published, the link was posted to the chat, and the turn ended **without the `AskUserQuestion` ever being called**. Nothing was blocked, so nothing claimed the carve-out; the turn-end `Stop` hit `skip: session not armed`; and the run sat finished-looking with an approval nobody had been asked for. The user waited an hour on a plan that had been ready the whole time. Every rule in `fix-linear` Step 4 was already correct and already said to ask — which is the point: a step the model is told to reach is a step it can skip, and the gate that would have notified is the very thing that went missing.

So the promise is recorded where forgetting it cannot hide. `publish-artifact.sh --purpose plan` writes `gate_pending: {url, at}` into the session state on a successful publish, and a `Stop` arriving with that marker set is treated exactly like a blocking kind: it notifies **regardless of arming**, carries the plan URL in the body, and relabels the event `published a plan and is waiting on you` rather than `finished`. Marking is deliberately narrow and deliberately harmless — only `--purpose plan`, only after the publish succeeded, never for a diagram or an unpurposed page, and the call is `|| true` behind an `-f` check so a machine with no `notify.py` publishes exactly as before. `--purpose plan` is the signal because it already means "this page is going to a human to approve"; a diagram is published for the record and nobody is waiting on it.

Three properties make it survivable rather than noisy. **The marker is cleared only when a notification actually reaches the user** — a failed send, a rate-limited turn and quiet hours all leave it set, so the next turn retries instead of the one stranded plan being the one notification that got dropped. **Asking the gate question clears it**, since `question` notifies on its own, so the normal path never double-sends. And **an unrelated event does not consume it**: a permission prompt mid-plan notifies on its own merits and the marker survives to the turn end. `tests/check-plan-gate.py` holds all of that over every profile copy, and its `rules` subcommand prints the contract.

**Notifying was not enough, because it fires after the thing it is reporting.** It happened again: the plan published, the link posted to the chat, the turn ended, and the user came back to ask why nothing had been asked of them. A notification a turn late still spends a round trip they did not owe, and the rule it was backing up was already in bold in both fix skills. So the hook now **blocks** rather than only reporting. A `Stop` arriving with `gate_pending` set returns `{"decision": "block", "reason": …}` on stdout at exit 0, which Claude Code feeds back to the model as an instruction to send the link and call `AskUserQuestion` in the turn it was about to end. The turn cannot finish between a published plan and its question.

Four things keep that interlock from becoming the worse failure, and each one is a way a blocking hook turns into a hang. **It blocks at most once per plan**: `held` is stamped into `gate_pending` and checked on the way in, and `stop_hook_active` is honoured too, so the two guards are independent and a run that ignores the instruction falls through to the notification rather than into a loop — Claude Code's own eight-continuation cap is a third backstop nobody should reach. **It cannot block without persisting that fact**: when the `held` write fails the hook declines to block, because a block it will not remember making is exactly the loop. **A question clears the marker before any of the notification machinery is consulted**, which matters more than it looks. The existing clear sits at the end of `handle`, behind `load_config`, quiet hours and the rate limit, so a question asked during quiet hours left the marker set — and the interlock would then have blocked a turn that did everything right. So `plan_gate` clears it first and that one stays where it is, which is why the diff adds a clear rather than moving one. **And `--gate-clear` is the escape hatch**, named in the reason text itself, for the plan that genuinely needs no question.

None of those four bounds held until the writes stopped clobbering each other, and the review that caught it is worth recording because the bug is invisible in the diff. `handle` reads the session state once and writes it back whole at the end, with `summarize` (`claude -p`, 180s in the shipped config), `generate_title` and `send` in between — so a permission prompt raised mid-plan can be holding a snapshot for three minutes. The Stop hook stamps `held` inside that window, the run asks its question, the `PreToolUse` hook clears the marker, and then the slow process writes its snapshot verbatim and **puts `gate_pending` back with no `held` on it**. The next turn end sees a fresh `Stop`, an absent `held` and a false `stop_hook_active`, blocks a plan the user already approved, and fires a stranded-gate notification after the answer. So every writer now **merges**: `merge_state` re-reads the file immediately before writing and applies only the keys that process owns, `record_sent` names the three it carries plus the ones it sets, and a key to remove is passed as `drop` rather than popped from a stale dict. That is the same single-writer discipline this file already states for the title cache, generalised — the title cache got it by keeping one dict, which stops working the moment a second process writes the same file.

**The decision is asserted through `main()`, on real stdout.** The first version of the test suite checked `plan_gate`'s return string, which is not what Claude Code reads: renaming the printed key to `action`, or sending the same `print` to stderr, each ship a hook that blocks nothing and each left the suite reporting `passed (45 checks)`. A contract carried by a process's output has to be tested through that output, or the test passes for a hook that cannot work — which is this file's own "a hook that fails is invisible" rule applied to the thing testing the hook.

The notification stays as the layer behind the block, for the run that is told to ask and ends the turn anyway. It is still a smoke alarm rather than a safety net: the fix is asking in the same turn as the publish, and the interlock only guarantees that failing to is answered immediately instead of an hour later.

### Reachability changes what an unattended run may do about an ambiguity, and the premise it overturned was load-bearing

`autopilot` was written on the line *from the commit onwards there is nobody to ask*, and that single sentence is what forced every mid-run judgment call down the decide-alone-and-ledger path. With the session reachable from a phone and `notify.py` registered on `PreToolUse` for `AskUserQuestion`, raising a question both notifies and can be answered — so asking is now right for the calls that are expensive to get wrong: anything irreversible or chargeable, a fork where one branch is hard to undo, and the Step 11 escalations the run could act on immediately (a product or policy call, a merge conflict's intent), which previously **ended** a run that could have carried on. It stays the exception rather than the default for one reason: **a question stalls the run until somebody answers it**, and a user asleep or at dinner turns an unattended run into a parked one — so most calls still take the most defensible option plus a ledger line, and a question that *was* answered earns no ledger entry, because that decision was the user's and is already on the record. Three things make the ask real rather than theatrical. **It must stand alone**: it is read on a lock screen and answered in an app, so an option saying *as discussed above*, naming a file to open, or needing two paragraphs weighed against each other is unanswerable. **It comes before the irreversible step, never halfway through**, where neither answer is any use. And **it is never accompanied by a ping**, since the hook already fires on the question and the second copy is what teaches the user to ignore both. Step 10c's old wording is the incoherence this fixes — *ask by pinging rather than parking silently… ask for a yes*, over a channel that cannot carry one. The counterpart hazard is unchanged and now more likely to come up: `pause` still refuses to park with a question dangling, because a paused session swallows an answer that may be in flight from the phone

### The notification body is summarized by a model, and the hook shells out to do it

`last_assistant_message` is a turn's closing chat message — written for a terminal with the diff open, routinely 500 words of headings, tables and file links, against a lock screen that shows about 140 characters. Clipping it, which is what it did, produces a wall of markdown whose first line is often a sentence ending in a colon pointing at a table nobody can see. `notify.py` therefore passes the body through `claude -p` before sending. **Use the subscription, not the API**: an `x-api-key` call is faster and was the first implementation, and it was wrong here because the API account carries no credit while the Claude Code subscription is already paid for — the symptom was an `HTTP 400 credit balance` that no amount of correct code fixes. Five things are load-bearing. **The budgets are deliberately loose** — 180s for the summarizer inside a 240s hook, against an observed 9–29s spread — because the alternative to waiting is the truncated dump the feature exists to prevent, and the only state in which any of this fires is one where the user is away and waiting is free; every tight budget tried here (6s, 25s, 35s, 45s) was tuned to a sample and then blown by an outlier. **Every failure degrades to a mechanical condense** and still sends, since a missing CLI, a logged-out machine or a slow model must never cost a notification, and the log records which path ran so a degraded machine is visible rather than inferred. **The child gets a neutral `cwd` and no MCP, hooks or plugins**, or it loads this repo's `CLAUDE.md` and every skill before answering; `NOTIFY_SUMMARIZING=1` in its environment is the backstop that stops a hook spawning a session that fires hooks. **Long input is windowed head-and-tail rather than truncated**, because the outcome sits at the top of a message and the ask at the bottom, so cutting the tail discards precisely what the user needs. **Questions are summarized like everything else** — an `AskUserQuestion` body is the literal questions, written for a terminal, and the user cannot answer from the notification anyway: all it has to convey is that the session is waiting on them and what about. The CLI is resolved by probing install locations and then `shutil.which` over an augmented `PATH`, never by name, because hooks run with a bare `PATH` where `claude` does not exist; `summarize.command` is the per-machine escape hatch and `notify.py --test` prints what it resolved, with a timed live sample

### The thread is the context, so only its first message repeats it

a session's notifications are one thread — Telegram replies with `reply_to_message_id`, Slack with `thread_ts` — and every reply renders the first message quoted above it. So the repo and the session title are already on screen in every reply, and printing them again spent roughly a third of a 140-character lock screen restating the line directly above. The shape is therefore split by position, not by transport: the **first message** is `<repo> · <session chat title>` then its body, with **no glyph**, because a thread root is an anchor and its class is the least interesting thing about it; every **reply** is `<glyph> <body>` and nothing else. `envelope["thread"]` is the discriminator and it is reliable in both producers — `notify.py` sets it from `state.get("thread")` and the `ping` skill from the same session state, so it is absent exactly once per session. The six glyphs (`✅❓🔐🔄💤🔥`) still carry the kind one-to-one, which is what makes dropping the words safe. **The thread is anchored before the first event rather than by it**: the root is the only message carrying the repo and the title, so a session whose first notification is a permission prompt opened its thread on a bare demand — observed as a root reading only `Claude needs your permission to use Bash`. `notify.py` now sends an empty-bodied envelope first, which `compose` renders as the header alone, and threads the real event under it; the `notify_when_blocked` carve-out means that first event is often a gate in a session nobody armed, so hanging the anchor on arming would have missed exactly the case that showed the bug. It costs one extra message per session, degrades to the old behaviour when the anchor send fails, and lives in the producer rather than in the two transports, since "this session has no thread yet" needs no transport knowledge. The second field is the **session's chat title**, read from the transcript where Claude Code writes `ai-title` and `custom-title` records, so it needs no editor API — `worktree-sync`'s `resolve.ts` had worked this out and its precedence is reused verbatim, a `custom-title` the user typed beating the generated `ai-title`. Two traps come with it: the record is written early and **scrolls out of a fixed tail** (only 38 of 139 local transcripts carried one in their last 256KB), so the lookup uses the widening-window `scan_tail()` shared with `handoff_at()`; and the records appear both compact and spaced, so each candidate line is `json.loads`-ed rather than regex-matched. The branch survives **only as a fallback** for a session too new to have a title, and the 8-character session id was dropped outright — it reads as a commit hash and identifies nothing a human recognises. `notify.py --label <session-id>` prints the resolved title so the `ping` skill shares the one parser, globbing `~/.claude/projects/*/<id>.jsonl` since only the hook is handed a transcript path. **A Remote Control session writes no title record at all**, which is how `remoteControlAtStartup` turned every thread root into `<repo> · <branch>`: a bridge session's transcript carries `bridge-session`, `last-prompt` and `worktree-state` records and never an `ai-title`, so the resolver found nothing and the branch fallback — the least informative field available, identical across every worktree of a repo — won by default. The fallback is now a condensed form of the session's **opening prompt**, taken from the first `last-prompt` record or the first non-`isMeta` user message, which is the one source present in both session kinds and stable for the life of the session: `lastPrompt` tracks the *latest* prompt, so reading any record but the first would label the thread with whatever turn the first notification happened to fire on. It is a **head** scan rather than the widening tail scan the title lookup uses, because a prompt is at the start of a file and a 17 MB bridge transcript is past `TAIL_LIMIT` anyway — but it still has to widen, since injected skill text pushes the first prompt to ~340 KB in. The fallback is in two tiers, because the opening prompt alone is a weak title — it is whatever the user happened to type, often a slash command plus a paragraph. So the hook **generates** one with the same `claude -p` plumbing the body summarizer already uses, from the opening prompt *plus the assistant's first reply*, which is what turns `/review-kludge on the whole of Demeter as it…` into `Demeter token consumption optimization`. Three properties make that affordable. It is **cached in the session state file** and the generator mutates the `state` dict `handle()` already persists, so there is no second write and no race with the `last_sent`/`thread` keys that write would clobber — measured at 6.6s on the first call and 0.09s on every one after. It is **skipped entirely when a real title exists**, so a titled session still resolves in 0.04s and spends nothing. And it **degrades through every tier**: a missing CLI, a disabled summarizer, a timeout or a reply the model rambles over all fall through to the prompt condense and then to the branch, each logged, because a hook that fails is invisible. `title_timeout` in `notify.json` is the knob, 25s by default against an observed 5-8s. **A markdown link had its URL thrown away on the way out**, which made every notification naming a change request unactionable: `strip_markdown` rewrote `[PR #10](https://…/pull/10)` to `PR #10` and dropped the target, and it runs on both the summariser's input and the mechanical condense, so no path survived it. It now keeps the URL for an **absolute http(s)** target and still drops it for a relative one — a file path opens nothing on a phone, while the change request is the only thing on that screen worth tapping — and the summariser is told to reproduce a URL verbatim, since a model rewriting to 68 words will otherwise spend none of them on it. The `ping` skill carries the same rule for the bodies it writes by hand. Measured honestly, the gap this closes is narrow: 17 of the 18 most recent real sessions already had a title, and the one that did not was the bridge session

### Composition is shared across transports; only delivery is not

the root/reply split above is identical in the Telegram and Slack senders, because a per-client layout is two things to keep in step for no gain. What stays transport-specific is strictly about *delivery*: Slack still needs the `<@U…>` mention prefixed into **both** `text` and the rendered block, since a threaded reply otherwise never notifies and `chat.postMessage` answers `ok` regardless; Telegram needs none of that because `reply_to_message_id` renders inline and notifies by itself. Dropping the header freed real room, so the summariser's budget went up by half — `SUMMARY_MAX_WORDS` 45→68 and the mechanical fallback `CONDENSE_LIMIT` 240→360 — and the `ping` skill's prose budget moves with it, or the skill and the hook disagree about the same message

### `--show-toplevel` answers the worktree, not the repository

every ping from a `fix-*` run labelled itself with the **branch** — a thread root reading `OLY-17 · Ticket fix` — because the session's cwd is `.claude/worktrees/dylan/OLY-17` and `rev-parse --show-toplevel` returns that worktree's own root, whose basename is the branch. Every worktree of one repo therefore looked like a different project, and the field that exists to say *which repo* said nothing about it. `--git-common-dir` is the one that survives a linked worktree: it points at the main checkout's `.git` from anywhere, so its parent is the repository, with `--show-toplevel` kept as the fallback. The trap for anyone checking this is that the bug is invisible from the main checkout — `notify.py --repo <main>` returns the right answer, which is exactly how it was declared not-reproduced once; reproduce it from **inside** a worktree or not at all.

### Outside a repository the directory names the session, not the machine

`repo_label` falls back to `host_label` when `rev-parse` finds no project, which was right for the case it was added for — a `$HOME`-rooted dotfiles repo answers `rev-parse` for every path beneath it, so the label became the home directory's name. Applied to *every* non-repo cwd it overreached: a phone session spawned in `remote-root` on the Pi read `pi`, which says where every session on that box runs and nothing about this one, where `remote-root` says what kind of session it is. So a named directory now wins and `host_label` answers only the case the directory cannot — `$HOME` itself, or no directory at all. Both halves are tested: `~/remote-root` reads `remote-root` even with `host_label` set, and `$HOME` still reads `host_label`.

### Away mode is a file, not an environment variable

`~/.claude/notify-state/away.json`, because hooks do not inherit your shell's environment — the same reason `gitlab-api.sh` reads its token from `.mcp.json` rather than `~/.secrets`. It drops the `min_turn_seconds` gate and nothing else. `away`/`back` in `shell/terminal.zsh` are thin wrappers over `notify.py --away`, guarded on the hook existing

### A `U…` id is not a DM channel

`chat.postMessage` accepts a user id in `channel` and posts to that user's DM with **Slackbot**, not with your app — it returns `ok`, so the only symptom is that the messages are somewhere nobody looks. A DM from the app needs the `D…` id that `conversations.open` returns for that user, which is why `notify-send.sh` resolves any `U…`/`W…` channel through it and caches the answer in `~/.claude/notify-state/slack-dm.json`; `im:write` is the scope that call needs, on top of `chat:write`. A `D…` or `C…` channel is passed through untouched.

### Threading a Slack DM silences everything after the first message

`chat.postMessage` with a `thread_ts` makes every notification after a session's first one a **threaded reply**, and Slack treats those as second-class — no new top-level message, no reliable push, and Slack only auto-follows threads *you* started or replied in, never a bot's. The failure is exactly the one the feature exists to prevent: a session says it has a question, then finishes forty minutes later into a thread nobody is watching. Observed here — five sends, one visible. `slack.mention` fixes it by prefixing `<@U…>` to the message, since a mention notifies regardless of subscription; it defaults to `slack.channel` when that is already a `U…` id, and `slack.mention_levels` keeps it to `stop`/`question`/`permission`/`failure` so a mention never degrades into noise. **The mention must sit in the `blocks`, not in `text`** — given both, Slack renders the blocks and keeps `text` only as notification fallback, so a mention living solely in `text` is never rendered, never registers as a mention, and never notifies, while `chat.postMessage` still answers `ok: true`. That was gotten wrong here on the first attempt and the symptom is indistinguishable from the bug it was meant to fix: a message that lands in the thread looking entirely normal. Verified end to end — the mention goes at the head of the rendered section block *and* in `text`, which is what the lock screen previews. `reply_broadcast: true` is the other option and is worse here — it copies the reply to the top level, undoing the per-session grouping the thread was for. **None of this applies to Telegram**: `reply_to_message_id` renders inline rather than collapsing, so every message stays top-level and notifies by itself, and an @-mention is meaningless in a 1:1 bot chat. Telegram's real threads (forum topics, `message_thread_id`) exist only in supergroups

### A Slack incoming webhook cannot thread

it ignores `thread_ts`, so per-session threading needs a bot token with `chat:write` plus a channel. Both are supported and the webhook is the documented default, since it needs no app scopes — but with many concurrent sessions the channel interleaves badly without threads, so the bot token is the better end state. The phone's push preview shows only Slack's `text` field, never `blocks`, so the one-line summary has to live in `text` or the notification is useless on a lock screen

### `/ping` is the deliberate counterpart to the hook, and shares its state

`notify.py` fires automatically and is therefore gated hard; the `ping` skill is invoked on purpose — by the user, or by a skill handing over a question, a blocker or a finished run — so it **bypasses every gate** (`min_turn_seconds`, `min_interval_seconds`, quiet hours, subagent suppression). An explicit ping is never noise. It sends through `notify.py --ping`, which builds the same envelope the hook builds and hands it to `notify-send.sh send` — which is why the skill is byte-identical across all three profiles: the Slack/Telegram split already lives in the sender, so nothing in the skill may name a transport. **The skill used to rebuild the hook's own state keying in two inline Python heredocs** — `session_path`'s regex pasted verbatim twice, `read_json`/`write_json` as bare `try/except` blocks, the envelope field by field, the state write — about 62 lines an agent had to read and re-emit character-perfect on a path where a mis-transcribed regex is a *silent* no-op: it writes a state file nothing reads, and the session then goes mute precisely when it was being relied on. `build_envelope()` and `record_sent()` are therefore shared, and the skill passes a level, a title and a body on stdin. `--ping` reads and writes `~/.claude/notify-state/sessions/<id>.json` so a ping lands in the session's existing thread rather than floating free — read-modify-write, never clobbering the `last_sent`/`last_kind` keys the hook owns, and tolerating a state directory that does not exist yet on a machine where no notification has fired. **Resolution and assembly are shared; the gates are not.** Every gate lives in `handle()`, which `--ping` never enters, so the split needs no flag to express it — and `record_sent()` takes `arm` off by default, which keeps the latch the hook's to leave alone and the ping's to set, on the success path only and outside the `if thread:` branch, since a transport that cannot thread returns no id and would otherwise leave the session mute. The ping deliberately does **not** write `last_sent`: that key feeds the automatic path's rate limit, and a deliberate message is not a reason to suppress the next real one. The message must carry what the session is doing *and* whether it needs anything: the lock screen shows one line, so a ping that says "done" has wasted it

### A hook that fails is invisible

`notify.py` appends a line for every invocation including the silent ones (`skip: turn 11s < 60s`), to `~/.claude/notify-state/notify.log`, capped at 1 MB. Without it, a wrong gate and a broken token look identical from the outside. Every error path logs and exits 0, and the POST timeout (5s) sits well under the hook timeout (15s) so a dead transport costs a turn seconds rather than the full budget. A missing or `REPLACE_ME`-filled `~/.claude/notify.json` is a dormant no-op, never an error — the feature ships switched off and comes alive when a token lands
