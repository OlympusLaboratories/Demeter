# skills/ — Agent Instructions

## Structure

Each skill is a subdirectory containing a `SKILL.md` file that defines the skill's behavior. Skills are symlinked into `~/.claude/skills/` by `install.sh` and become available as slash commands in Claude Code.

## Current Skills

| Skill | Purpose |
|---|---|
| `changes-branch` | Load branch context |
| `changes-description` | Adversarial four-persona debate (senior / skimmer / novice / AI-slop hawk) that converges on an MR description, then fact-checks it against the diff (uses the Workflow tool; prints a `wf_…` run ID to watch live with `wfwatch <id>`) |
| `changes-diagram` | Turns the branch's diff into an interactive call-flow page — each changed function a box with its +/- lines, grouped into module boxes, with new and dropped calls and a click-through review walk. Falls back to a file/module graph on non-Python branches, so a non-empty diff never yields an empty chart. Publishes to whichever artifact store `skill-env.sh` names |
| `changes-explain` | MR change breakdown |
| `commit-msg` | Generate commit messages |
| `docs-humanize` | Adversarial five-persona swarm (archivist / skimmer / newcomer / slop hawk / doer) that rebuilds an AI-written Notion page, markdown file or Linear ticket into something a human reads once and acts on — builds a fact ledger first, then proves against it that nothing real was lost and nothing was invented (uses the Workflow tool; prints a `wf_…` run ID to watch live with `wfwatch <id>`) |
| `docs-update` | Audit and update README.md and AGENTS.md to reflect current repo state |
| `autopilot` | A mode switched on over `fix-linear` or `fix-freeform`, never a task of its own — it overrides none of that skill's flags and adds only the automation: commits, commits, describes, pushes, opens the MR, watches the pipeline and the review bot with `Monitor`, runs a `review-code` swarm alongside that bot, works the review clean, applies infrastructure plans, merges stacked changes in order, and pings you when done or stuck |
| `fix-feedback` | Work through review feedback — merge request threads or a local review agent's output |
| `fix-freeform` | `fix-linear` without a ticket — implements a freeform problem statement. Defaults to the repo's default branch, a one-shot description, no diagram and no review swarm (`--review true` opts in); escalates to a feature branch on its own when the change touches Terraform, the default branch is protected, or the tree has unrelated uncommitted work |
| `fix-linear` | Linear ticket implementation. After the description it defaults to both a call-flow diagram and a `review-code` swarm over the branch (`--diagram false` / `--review false` to skip either) |
| `ping` | Send yourself a push notification carrying what this session is doing and what it needs. Invoked directly, or by another skill handing over a status, a question, a blocker or a finished run. The notification is one-way — answering from a phone is Remote Control, which is armed at session startup because no skill can run a slash command, and which `/ping off` therefore does not disconnect |
| `plan-initiative` | Sequence a Linear initiative's subtasks and delegate them across named engineers — dependency graph, parallelism verdict, swimlane chart, per-person work orders |
| `plan-subtasks` | Turn a design doc + implementation breakdown into a Linear ticket tree — one parent, one MR-sized subtask per reviewable slice, both doc links on every ticket; confirms team/project/assignee and writes to Linear only after the plan is approved |
| `reflect-peer` | Peer assessment generator. Unfinished — it has no output contract, and what is left to build is under Backlog below |
| `reflect-self` | Performance-review self-assessment generator |
| `reflect-week` | Generate weekly engineering snippets |
| `review-code` | Adversarial multi-agent review of proposed local changes, or of an incoming branch someone else pushed — the latter is fetched into a detached review worktree and comes back with a pack of ready-to-paste review comments (uses the Workflow tool; prints a `wf_…` run ID to watch live with `wfwatch <id>`) |
| `review-kludge` | Adversarial swarm that reviews recent large features for accumulated kludge/AI-slop and proposes refactors (uses the Workflow tool; prints a `wf_…` run ID to watch live with `wfwatch <id>`) |
| `workflow-resume` | Rescue a `Workflow` swarm that died mid-run — diagnoses why (spend limit, kill, API errors), then either resumes it from the on-disk agent cache or harvests the finished agents' results |

The three `reflect-*` skills ship **only in the two work profiles**, and that is deliberate rather than an oversight. `reflect-week` reads Slack and is the sole producer of the input the other two consume — `reflect-self` reads its weekly reports out of `reflect-self/context/`, and `reflect-peer` reads its per-peer collaboration profiles out of `reflect-peer/context/`. Nothing on a home machine writes either directory, so shipping the consumers there would put two skills in every session's skill index that can only ever report an empty context directory, and a user who reads the listing would reasonably assume they work. `profiles/check-transform.py` carries all three in `PRESENCE_EXEMPT` with that reason, so the absence is *reported* on every drift run rather than silently tolerated, and `install.sh` creates a `context/` directory only for a `reflect-*` skill the profile actually linked.

## Backlog

**`reflect-peer` is unfinished, and this is what is left.** It has three steps and no output contract — no output format, no sections, no review-period selection. The list lives here rather than as a `## TODO` at the end of `SKILL.md`, because a TODO list inside a skill body is text the model reads and tries to act on: an invocation would work through the unbuilt items as if they were instructions. As documentation it is a backlog; as a skill step it was a trap.

- Parameterize by peer name, rather than naming the argument and never using it.
- Pull the peer's merged merge requests for the review period, to tie code contributions to the collaboration evidence already in the context reports.
- Define the output format and sections. `reflect-self` is the template worth copying — it states where the answers go, how the word count is shown, and how an unverified claim is flagged.
- Define review-period selection (quarterly, half, custom range).
- Add instructions for synthesizing across multiple weekly profiles.

Finishing it is a feature build, not a cleanup. Until somebody does, the skill stays listed and unfinished on work only.

## Worktrees

`fix-linear`, `fix-freeform` (when it escalates to `--branch new`) and `fix-feedback` isolate each fix in its own git worktree by default (under `.claude/worktrees/<branch>`), entered via the `EnterWorktree` tool, so multiple non-blocking fixes can run in parallel — one session per worktree. They offer to install dependencies in the fresh worktree and leave cleanup manual (`git worktree remove`). Pass `in place` / `--here` / `no worktree` in the skill argument to fall back to an in-place checkout. `commit-msg` and `changes-description` operate on the current directory and need no worktree awareness, and `docs-humanize` touches no checkout at all unless its target is a file path. `review-code` does too in its default local mode, but when handed an incoming branch it creates a **detached** review worktree at `.claude/worktrees/review/<branch>` — never checking their branch out over yours — and leaves removal to you. `autopilot` creates no worktree of its own — it inherits whichever one the fix skill it delegated to set up, and owns that single branch for the whole run. Full guide: `WORKTREES.md` at the repo root.

## Workflow Runs

`changes-description`, `docs-humanize`, `review-code`, and `review-kludge` orchestrate swarms through the **Workflow** tool. `fix-linear`, `fix-freeform` and `autopilot` reach two of them indirectly — `changes-description` always, and `review-code` on the `--review` flag — so a single fix run can leave two run directories behind. Each run leaves a manifest, a script snapshot, and a `journal.jsonl` agent cache under `~/.claude/projects/<slug>/<session>/`. All four **launch and yield**: the tool returns a `wf_…` run id immediately, the skill prints it with the `wfwatch` command, ends the turn, and resumes on the run's completion notification. None of them may hold the session open waiting on a swarm — no `TaskOutput`, `Monitor`, `ScheduleWakeup`, or polling — so the user keeps a free prompt line for the whole run. `workflow-resume` reads all of it through `~/.claude/scripts/workflow-runs.py` (`list`, `show`, `args`, `script`, `link`, `merge`, `harvest`).

Two facts those four skills depend on: a workflow reports `completed` even when agents died mid-run (`agent()` returns `null`, the script carries on), and the resume cache is a **prefix** — a hash chain over agent calls that stops replaying at the first agent with no recorded result. Neither is visible from the report a swarm prints.

## GitLab Data

MR-related skills (`changes-explain`, `fix-feedback`, `fix-linear`, `fix-freeform`, `reflect-week`) name `~/.claude/scripts/gitlab-api.sh` directly; `autopilot` reaches it through `skill-env.sh`'s `api_script` instead, which is the form a new skill should copy. The script reads the GitLab token from `~/.claude/.mcp.json` so tokens never enter conversation context. Run it with `help` to get every subcommand and its arguments, generated from the script's own source.

`fix-feedback` is the only one that **writes** through it, and both writes are gated on an explicit yes in chat: Step 3b opens one new anchored discussion per unique review-swarm finding (`create-diff-comment` — body over stdin, so the single-quote rule that governs `reply-to-thread` does not apply; falls back to an unanchored note when the line sits outside the MR diff or the commit is unpushed), and Step 7b replies into an existing thread (`reply-to-thread`). `mr-for-branch` finds the MR when only the branch is known — both its arguments accept `-` to derive the project from `origin` and the branch from `HEAD`.

## User Data

Some skills accumulate context data that is NOT tracked in git:
- `reflect-week/slack-context.md` — ephemeral Slack threads pasted before each run
- `reflect-self/context/` — weekly self-reports
- `reflect-peer/context/` — per-peer collaboration profiles
- `reflect-self/prompts.md`, `reflect-peer/prompts.md` — review questions pasted per cycle
- `plan-initiative/team.md` — team roster (seniority, specialties, ramp areas, capacity); `team.example.md` is the tracked template

These files are gitignored, and the paths above are the ones the root `.gitignore` actually names — an entry here that does not appear there is tracking a file somebody will commit by accident. The installer creates the two `context/` directories; the rest are created on first use.

## Skill Environment

Nothing in a skill may hardcode the forge, the AI reviewer's username, the infrastructure
bot, or the artifact store. Every one of them differs between the work profiles and home,
and a skill that bakes one machine's answer in fails silently on the other — grepping for
the wrong bot username finds no threads and reports a clean review. This paragraph names
none of those values on purpose, because it is subject to its own rule: a sentence saying
which profile is on which forge cannot survive the work→home transform, which rewrites the
forge name wherever it appears, so the two copies drift into contradicting each other. Ask
`skill-env.sh`.

`~/.claude/scripts/skill-env.sh` is the seam. It carries this profile's defaults **in its
own code** and merges `~/.claude/environment.json` over them, so a missing or malformed
config degrades to working defaults instead of breaking a run.

```bash
~/.claude/scripts/skill-env.sh check          # everything a skill will see
~/.claude/scripts/skill-env.sh get review_bots
```

**An empty value means the capability is absent on this machine, never "guess at it".**
Empty `review_bots` means treat every non-operational bot thread as real feedback; empty
`iac_bot` disables the apply-before-merge gate; empty `review_job` means a review cannot be
re-triggered and the skill must say so rather than retry something that does not exist.

A skill added here that touches the forge, a reviewer, or an artifact store reads these
values rather than naming anything. The example file is committed; the real one is seeded
by the installer and never overwritten.

## Autonomous Runs

`autopilot` is a **mode on a fix skill, not a task of its own** — it cannot be invoked
against nothing, and `/autopilot <ticket or statement>` still routes through `fix-linear`
or `fix-freeform` and inherits that skill's defaults. It composes the ordinary skills
rather than reimplementing them: the fix skill, then `commit-msg`,
`changes-description`, `review-code`, `fix-feedback --autonomous`, `changes-diagram` and
`ping`. Six invariants it must never lose:

- **It waits with the `Monitor` tool, never a sleep or a poll loop.** Several runs may be
  live at once and each blocking one costs a session. Every terminal state must emit a
  line — a watcher that reports only success stays silent through a crashloop, and silence
  is indistinguishable from "still running". A failed poll is a terminal state like any
  other, so it emits rather than being swallowed by `|| true`, and the script is
  smoke-tested with a single pass before it is armed.
- **Review comments outrank CI.** Fixing comments means pushing, and a push restarts the
  pipeline, so handling CI first throws away a whole run.
- **The swarm is launched with the watcher, not after it.** `review-code` and the forge's
  own reviewer read the same pushed diff and neither gates the other, so both start in the
  turn that arms the `Monitor` and the run yields once for both. The swarm runs once per
  run, not once per review round. Whichever run opens a change request also
  passes `--review false` down, so the swarm runs here rather than before the push and
  `fix-feedback` has somewhere to post its findings.
- **It owns no flag but `--merge` and `--max-rounds`, and overrides none.** It is a
  modifier on a fix skill, not a peer: every decision a parameter expresses was already
  made there, `--branch` included. `--review` is therefore on through `fix-linear` and off
  through `fix-freeform`, and being unattended is not a reason to spend a fleet the user
  declined. A `--branch default` run pushes the default branch and ends — Steps 5–10 have
  no change request to drive — which is safe to honour because `fix-freeform`'s own Step 2b
  has already forced a feature branch for Terraform, a protected default branch, or a dirty
  tree.
- **It supersedes `fix-linear`/`fix-freeform` Important Rule 1** (never push, never open a
  merge request) for the one branch it created, and for nothing else. That carve-out is
  written into `autopilot` explicitly; it is not something an agent may infer.
- **It may ask, but asking is the exception.** Remote Control makes a mid-run
  `AskUserQuestion` answerable from a phone, so the calls that are expensive to get wrong
  — anything irreversible or chargeable, a product decision a thread needs — get asked
  rather than guessed, and an escalation the run could act on immediately no longer has to
  end it. Everything else still gets the most defensible option and a ledger line, because
  a question stalls the run until somebody answers it.

`fix-feedback --autonomous` is the only sanctioned relaxation of that skill's "never write
unasked" rule. It still never pushes — committing and pushing belong to the caller — and it
still never resolves a thread it disagreed with.

## Adding a New Skill

1. Create a new directory: `<skill-name>/`
2. Add a `SKILL.md` file defining the skill's prompt and behavior
3. If the skill needs helper scripts, add them to `../scripts/`
4. Run `./install.sh` from the repo root to symlink it
5. Update this file with the new skill entry

**If the skill writes or edits code, restate the no-comments rule in its `SKILL.md`.**
`~/.claude/CLAUDE.md` (from `.claude/CLAUDE.md` in this repo) forbids agent-written code
comments in every repository, but a skill's subagents receive only the skill's own prompt
— they never see the user's `CLAUDE.md`. A skill that leaves the rule implicit will have
its subagents comment freely. Copy the wording from `fix-linear`'s Step 5.

## Why the autonomous skills are shaped the way they are

The root `CLAUDE.md` carries the invariants a session must not break. This section carries
the reasoning: what each gate is for, which failures it was written against, and the
orderings that look arbitrary until the invalidation direction is spelled out. Nothing
here is optional reading before changing `autopilot`, `pause`, `unpause`, `review-code` or
either fix skill — most of it records a bug that shipped.

### A skill must never hardcode what differs between machines

the work profiles review on GitLab with one AI reviewer and publish to Claude Artifacts; home reviews on GitHub with a different reviewer and publishes to mnemosyne, which exists on no work box at all. Writing those facts into the skills produces something that works only where it was written and fails silently everywhere else — the brittleness is invisible, because a skill that greps for the wrong bot username finds nothing and reports a clean review. `scripts/skill-env.sh` is the seam: it carries the per-profile defaults **in code** and merges `~/.claude/environment.json` over them, so a missing or malformed config degrades to working defaults instead of breaking, and `skill-env.sh check` prints what a skill will actually see. The keys that matter are `forge`, `api_script`, `change_request`/`change_request_short`, `review_bots`, `review_job`, `operational_bots`, `iac_bot` and its two markers, `artifact_store` and the five keys that reach the self-hosted store (`mnemosyne_host`, `mnemosyne_user`, `plan_folder`, `diagram_folder`, `tasks_folder`), `require_human_approval`, and the seven `fix_*` run defaults. **An empty value means the capability is absent on this machine, never "go and guess"** — empty `review_bots` means treat every non-operational bot thread as real feedback, empty `iac_bot` disables the apply-before-merge gate outright, and empty `review_job` means a review cannot be re-triggered and the skill must say so rather than retry something that is not there. The example file is committed with placeholders and the real one is seeded by installer step 9

### A forge helper's own source is the only honest list of what it can do, and the usage line must be generated from it

`gitlab-api.sh`'s was hand-written and had drifted to 30 of its 35 subcommands, silently hiding `job-log`, `mr-pipelines`, `pipeline-jobs`, `pipeline-bridges` and `group-members`. That line is not documentation — it is the skills' **only discovery mechanism**, since `fix-linear`, `fix-freeform` and `autopilot` all instruct the agent to read it before calling a subcommand, and only a third of the subcommands are named literally anywhere in a skill. So the five that drifted off were unreachable, `job-log` among them — the one `autopilot` needs for "never blind-retry a failing job, read the log and classify it first", which is the single most damaging unattended behaviour there is. Both helpers now derive their list: the shell one greps its own `case` labels (anchored at **both** ends, or the pattern matches inside the embedded Python heredocs), the Python one already joined `COMMANDS`. A bare list is only half of it, though, because it carries no arguments and an agent that needs them reads the whole 835-line file — so each has a `help` that pairs every subcommand with the argument text already in the file: the `# Args:` comment on the shell side, the `Usage:` literal inside each command function on the Python side, read back with `inspect.getsource`. That costs ~700 tokens against ~12k, on every run that touches the forge. Three consequences worth keeping. **The token read has to be lazy** or `help` dies on a machine with no `.mcp.json`, which is exactly the machine someone is trying to orient themselves on — a pre-dispatch `case` ahead of the token assignment is enough and leaves the 35 existing arms untouched. **A derived list can only see what is statically there**: three GitHub commands had no visible usage literal (two delegated theirs to a shared helper, `pr-for-branch` had none at all because every argument is optional), and the fix is to put the literal at the command rather than to make the extractor clever. And **the skill text and the helper have to change together** — `fix-linear`/`fix-freeform` are a transform pair, so a work copy that says `gitlab-api.sh help` becomes `github-api.sh help` on home, and pointing the skills at a `help` that exists on only one forge would have shipped an instruction that fails on the machine it was transformed onto

### Projection and bounding belong at the helper boundary, and a clip has to announce itself

`job-log` was the only one of 35 subcommands piping `curl` straight to stdout — a CI trace is routinely 1-10MB, ~500k tokens at 4 chars/token, so the run either truncated blindly or died, on the exact path where guessing costs the most. It takes an optional line budget now, defaulting to the last 400, because the reason a job failed is at the **end** of its trace; `all` opts out so nothing is lost, only deferred. The bound lives in the helper for the same reason the field projection does: a caller that has to remember to pipe through `tail` is a caller that will forget once. Every path prints a header naming the total and what was dropped — `agent-watch`'s rule that a clipped string looks like a short one applies here more than anywhere, since an agent reading a silently-truncated trace concludes the job failed for whatever reason happens to sit at the cut. GitHub had no log command at all, so `autopilot`'s hardest safety rule was unimplementable on home; `github-api.sh job-log` closes that, and two things about it are not guessable. A `github-actions` check run's `id` **is** the Actions job id, so the id `pr-checks` already emits is the one `/actions/jobs/{id}/logs` takes, with no resolution step. And **that endpoint 302s to Azure Blob Storage, where `urllib` helpfully replays the `Authorization` header and gets `401 InvalidAuthenticationInfo`** — the naive implementation fails on every single call, so the redirect must be caught and the `Location` re-fetched with no auth header at all. It reports rather than guesses when the id is not an Actions job: a check run from another app, or none at all, is named in a JSON error rather than retried or silently empty

### An empty diagram is worse than no diagram

`changes-diagram` builds a per-function call graph with Python's `ast`, which is high fidelity and useless on the Go, Terraform and TypeScript repos that make up most of the work here. The original it was ported from simply produced zero nodes there — and a chart with no boxes reads as *this branch changed nothing*, not as *this language is unsupported*, so the failure is silent and actively misleading. The guarantee is therefore mechanical: **a non-empty diff always produces a non-empty chart.** When the AST pass yields no nodes, it falls back to a file/module graph with import edges resolved per language (Go via the `go.mod` prefix, TS via relative-path probing with extension and `index` fallbacks, Terraform via `module`/`source` and cross-file resource references), and everything else gets grouped boxes with line counts and no edges. The JSON carries a `mode` of `callgraph` or `files` so the page can say which it is. Proven across Go-only, Terraform-only, TypeScript-only, Markdown-only, mixed-with-binary, tests-only and module-level-Python diffs

### The diagram's HTML is the artifact, and the publish target is configuration

the page is self-contained apart from elkjs on jsDelivr and Google Fonts, which are all on the Artifact tool's CSP allowlist, so it publishes unmodified — that compatibility is load-bearing and any new external resource has to be checked against that allowlist or it fails invisibly. Where it publishes comes from `skill-env.sh`'s `artifact_store`: `claude` uses the Artifact tool, `mnemosyne` is the home store and publishes through `scripts/publish-artifact.sh`, which was a runtime-discovery stub for exactly as long as it could not be inspected from the machine this was written on. `auto` tries mnemosyne, then the Artifact tool, then writes the file locally — and a local file is a success, never a failure. Two traps the port left behind: the Artifact tool takes a `favicon` of one or two emoji, not the `icon` string the source used, and it **prefers the HTML `<title>` over the `title` parameter**, so a template title leaks into every publish — the rendered copy is retitled per branch before publishing and the shared template is never modified

### The diagram page is read on a phone, and nothing about that was true

every change request's diagram link is opened from a push notification, so the phone is the *primary* reader rather than a degraded one, and on that reader the page was close to useless. Four defects, and they compound. **The template carried no `<meta name="viewport">`** — measured in headless Chromium at a 390px device width, the page laid itself out at **930px** and the browser shrank the whole thing, which is the mechanism behind "the diagram is way too zoomed out" and behind text that wrapped as if the column were wide when it was not. That one line is the largest single fix here and the one most likely to be silently reintroduced, because the page renders perfectly on a laptop without it; `tests/check-diagram-template.py` pins it. **`fit()` fitted everything**, which is the right answer for a `Fit` button and the wrong one for an opening view: the same 91-node graph on a phone canvas scaled its 12.5-unit labels to **0.5px**, a grey rectangle that reads as a broken page rather than as a large diagram. The opening view now clamps to a floor of 8px of label and anchors at the **top left**, where a `DOWN` layout puts the entry points, so the page opens readable and is panned rather than squinted at; `Fit` is unchanged and one tap away, and zooming all the way out stayed a thing you ask for. **`.canvas` sets `touch-action: none`**, which switches the browser's own pinch off, and the pointer handlers tracked exactly **one** pointer — so a two-finger pinch was processed as a one-finger pan and the only zoom on a touch screen was the `+`/`−` buttons. Taking the touches means owning the gesture: pointers live in a `Map`, two of them pinch about the gesture midpoint (so pinch and two-finger pan are one gesture), dropping back to one **re-baselines** the pan so lifting a finger does not jerk the canvas, and a double tap zooms in for the one-handed case. And **`window.addEventListener("resize", fit)` discarded the view** on every resize — which on a phone is every time the URL bar hides, so the diagram snapped back to fit mid-pan. Resize now holds the centre and the pixels-per-unit, and a `ResizeObserver` on the canvas covers the full-screen toggle, which no window resize reports.

The view maths live in a **`<script id="view-math">` block outside the main IIFE** purely so they are testable: the block touches no `document`, `window` or ELK, so the test slices it out and runs it under `node` with **nothing stubbed**. That is deliberate avoidance of the trap `tools/AGENTS.md` already records for `vscodeStub.ts` — a DOM stub with a gap is a test that passes while testing nothing, and the whole IIFE needs ELK, fonts, a canvas 2d context and a layout engine. The same test also asserts the **three profile copies are byte-identical**, which nothing else did: `check-transform.py` covers `SKILL.md` and never looked at the template, so it could have drifted between profiles indefinitely. The template carries no forge vocabulary, so there is no transform to apply and byte-identity is the whole contract.

Two smaller things, both measured rather than assumed. **`word-break: break-all` breaks at any character**, which is how a path rendered as `…_darwin/.` / `claude/hooks` and a test name as `…gets_the_l` / `ink`; the fix is `overflow-wrap: anywhere` plus a `wbr()` helper that inserts real `<wbr>` opportunities after `/`, `_`, `.`, `-` and `:`, so the line breaker prefers a boundary and only breaks mid-token when a single run genuinely will not fit. And **the review walk was a wrapping flex row with `margin-left: auto` on the counts**, so a long name pushed `+11 −0` onto a line of its own, right-aligned under nothing; it is a three-column grid now, and the name wraps inside its own column. The touch targets go to 42px under `@media (pointer: coarse)` only — a mouse keeps the 30px it had.

### The self-hosted store is reached through one script, and five keys carry what differs

`scripts/publish-artifact.sh` publishes an HTML file and prints its URL, and both fix skills' plan gate and `changes-diagram` call it rather than each reimplementing the path. It runs `publish-artifact` directly when that is on `PATH` — the case on the Pi itself — and otherwise copies the file to `mnemosyne_host` and runs it there over SSH. **`mnemosyne_user` is not a nicety**: `/etc/mnemosyne/publish-token` is `root:jarvis` mode 640 and the SSH login is not in that group, so a direct remote call dies on an unhandled `PermissionError` and the invocation has to be `sudo -n -u <user>` — which was found by running the deploy rather than by reading it, and would otherwise have failed the first time a plan was published from a laptop. **A caller names what it is publishing, not where it goes**: `--purpose plan`, `--purpose diagram` or `--purpose tasks` makes the script read `plan_folder`/`diagram_folder`/`tasks_folder` itself and omit the flag when that key is empty, because publishing deliberately refuses a folder that does not exist and a substituted guess loses the artifact rather than filing it somewhere harmless. That resolution sits **inside** the script because the obvious alternative does not survive contact with a real shell: `${FOLDER:+--folder "$FOLDER"}` in a skill body splits into two arguments under bash and stays **one** under zsh, so it shipped `--folder PRtifacts/Plans` fused into a single argument and argparse rejected the flag it does define. It reached a merged commit because the test suite drove the script with already-separated arguments and never through the idiom. **Resolve it before the local-exec branch, not after** — a run on the Pi takes that branch and would otherwise drop the folder silently, which is the second bug this one step now has a test for. **Exit status 3 is the capability-absent answer rather than a failure** — this machine has no self-hosted store, so the caller falls through to the Artifact tool, which is the ordinary path on every work box; any other non-zero status is real and gets reported. **A page nobody can open is not a published page**, so `--purpose` also carries visibility: both purposes exist to be read from a link by somebody who is not at this laptop, and a private artifact is a 404 to everyone without an admin session while the management URL redirects to `/login`, so every plan and every diagram was unreadable by its only intended reader. The script therefore passes `--public` whenever a purpose is named, and the server hands back the link that opens rather than the one that asks for a password. That is a real widening of what the publish token can do — it is the one thing it can do to the outside world — and the compensating control is an audit rather than a prompt: the store's index answers "what is public right now" in one click. The plan gate publishes with `--expires 7d`, since a plan earns its keep while it is being approved and is clutter a fortnight later, and it **never blocks the gate on the publish**: a plan the user can only read in the terminal still gets approved, while a question that never arrives strands the run. **The link reaches the user as a chat message of its own, immediately before the question**, because `AskUserQuestion` renders no links — a URL in the question text is characters on a phone screen, and the screen is the whole reason the page gets published. The question then carries no plan at all: the compressed per-file summary that used to live there was written when the question was the only copy that reached the phone, and beside a tappable link it is a worse second copy filling the screen the question is read on. **That message carries the URL and nothing else**, which is the half that was missing: the instruction already said "its own short message" and sat in one sentence with "write the full plan into your reply", so the plan landed between the link and the question and the reader scrolled past a copy of what the link opens to reach the only tappable thing on the screen. The plan prose now goes into the reply **ahead of** the publish, where it is still the fallback for a publish that fails and can no longer wedge itself into that gap. **The URL is then recorded on the run checklist as `plan_page`**, because the gate is not the only reader: `autopilot` Step 4b writes it into the change request's description beside the checklist link, where a reviewer wants the plan before the diff rather than after the merge. It rides in the items file rather than in context because that file is the one piece of run state surviving both the hand-off and a pause, and an empty `plan_page` writes no line. The merge request reader of a diagram link is why that page is public too.

### A run's obligations live on a page it reads, not in its context window

`autopilot`'s arming instruction is in that file **twice** — Step 0d and an Important Rule — and a run skipped it anyway, which is the evidence that prose is the wrong mechanism for an obligation rather than evidence that a third sentence was needed. What replaces it is a checklist the run reads and ticks: `scripts/run-checklist.py` seeds a page from the run's **resolved flags**, so it can neither list a diagram the run will not draw nor omit a merge it will perform, and the page embeds its own items as a JSON block so reading the artifact back hands the run its obligations as **data rather than prose to parse**. The fix skills publish it before their first step and report the link; `autopilot` adopts that page rather than minting a second one, writes the link into the change request description at Step 4b so it can be refreshed *during* the run, and closes it at Step 11. **Updating it is one command — `tick` — and that is load-bearing rather than ergonomic.** The first version said to re-read and update the page at every step boundary, which is read-edit-publish: three steps, and on the very run that built the feature all three were skipped through a push, a change request, a review verdict and a swarm launch. The page still read `commit: in flight` while the review was running, and the user had to point it out. `tick <items> id=state --publish` validates, renders and updates in one call, rejects an id the page does not have so a typo is loud, and clears `waiting_on` when an item leaves `in-flight`; the skills now carry the literal command at each boundary rather than an instruction to remember, and a turn ending with the page behind the run is a defect in the same way a turn ending with nothing armed is. Five properties carry the design. **The URL never changes**: the first publish records the identity — the mnemosyne hash, or the Artifact tool url — and every later write is an update against it, because the link is already in the description and a second plain publish freezes the page the user is holding at step one with nothing reporting it. **"Nothing armed" is computed from the items, never asserted by the run** — outstanding work with no item in flight renders as an alarm, which is what makes the never-yield rule checkable instead of aspirational. **A `skipped` item must carry a reason and an `in-flight` item must carry a blocker**, both enforced by the renderer, since "skipped" alone records that an obligation was dropped and nothing about why, and an item claiming to be in flight behind nothing is the exact lie the page exists to catch. And **`mark_gate` stays `plan`-only**: the task page is published before the first step and rewritten at every boundary after it, so wiring it into the plan gate would refuse the first turn end of every run and one more per update — `tests/check-publish-artifact.sh` pins that, and `tests/check-run-checklist.py` pins the rest. The local pause-state file survives as the substrate `/pause` and `/unpause` work from and as the fallback when the store is absent, which is what exit `3` means and is the ordinary answer on a work box; `/unpause` reads the page before its first write, because a publish to an artifact the conversation has not read is refused and a fresh session is the normal case there.

### Never yielding is the silent half of never blocking

Rule 1 forbids holding a turn open, and the skill said nothing at all about the opposite — which is strictly worse, because a turn that ends with nothing running is indistinguishable from a turn that ends having handed work off. Observed on a real run: it announced the two review swarms it would start next, then ended the turn with both earlier panels already finished and **nothing in flight**. Had the user not replied it would have idled until morning, behind a transcript that read like work in progress. So a turn may end only when something will cause the next one — a running workflow, a `Monitor`, a scheduled wakeup — and with an empty queue and budget intact the run does the next item **in that turn** rather than announcing it. A queue that is empty because everything left is blocked is said explicitly and paused on, so silence is never ambiguous between working and stopped. The checklist is what makes the condition answerable: it is a query over the *waiting on* column rather than a reading of the transcript.

### A rewrite needs a substrate

`changes-description` can check every claim against a diff; `docs-humanize` has no such thing — the source text is at once the ground truth and the thing on trial, so a rewrite that is fluent and subtly wrong is undetectable once the original is gone. Its first phase therefore builds a numbered **fact ledger** out of the source, and every later phase is measured against it: the auditor reports *item F14 is absent* rather than *feels complete*, and a claim tracing to no ledger item is an invention to be cut. The same reason makes open questions non-negotiable output — a generated document's most expensive lie is the one where it smooths over what nobody has decided. Its slop detector is mechanical and split in two: HARD patterns (no legitimate technical use) are defects the judges must block on, SOFT ones (`ensure`, `robust`) are shown as evidence only, because a single false positive on a real `ensure the pod is Running` teaches the panel to ignore the whole measure. Match against a **whitespace-flattened** copy — markdown wraps wherever the author's editor wrapped it, so a line break lands inside "plays a crucial role" and the phrase goes undetected in exactly the documents the list exists to catch. The write-back is gated on an explicit yes, saves the original to the scratchpad first, never renames a Linear ticket (every pasted link breaks), and prefers a Notion **suggested edit** over an overwrite on any page the user does not own

### An autonomous run waits with `Monitor`, never with sleep

`autopilot` composes the ordinary skills rather than reimplementing them, and the thing that makes it safe to leave running is that it never holds a turn open. A `sleep 120` poll loop — the obvious implementation, and the one the third-party tooling this was modelled on uses — costs the user their prompt line for the length of a CI cycle, which with a dozen concurrent sessions is the whole point of the feature gone. A `Monitor` runs in the background and wakes the session on an event. Its filter must emit on **every** terminal state, not just success: a watcher greping only for green stays silent through a crashloop, and silence is indistinguishable from still-running. Poll remote forges no faster than 60s and tolerate a failed request, since one blip must not kill the watch

### A watcher that cannot see must say so, and a smoke test is the only thing that proves it can

Step 5 told a run two things that conflict on any box with less tooling than the author's: *every terminal state produces a line*, and *tolerate a failed request (`|| true`) so one blip cannot kill the watch*. The second was written for a 5xx and absorbs a permanent failure identically. Observed on a phone session driving piserver, where the Pi reaches these skills through the home profile's `skills/` symlink and therefore executes text authored against a Mac's toolchain: the watcher used external `jq` and a `--json` flag the installed `gh` does not carry, both guarded, so every poll failed silently — the completed-check list was always empty, the state line was always suppressed, and the exit test could never be true. Only the comment counter worked, which is exactly why it looked alive: it *was* emitting events, just never the ones it was armed for. A merge request went green and was approved, the run reported that it was still waiting, and the merge happened only because a human noticed seven minutes later. **A correct reading of the instructions produced that bug**, so the fix is to the instructions and not to one script. Three rules carry it now. A failed poll **emits** a `POLL ERROR` line carrying the command's stderr, and only its *consequences* are tolerated — the distinction `|| true` cannot make by itself. The script is **smoke-tested with a single pass** (`MAX_POLLS=1 SLEEP=0`) before it is armed, which costs one command and is the only check that catches a tool this machine does not have; enumerating what a given box lacks is the alternative, and it is both a machine difference a skill may not hardcode and a list that goes stale the first time a box changes. And a **parser that cannot parse emits**, because an `except` that exits 0 on a parse error turns a broken parser into a silent healthy report — the same failure from the other direction, since `gitlab-api.sh` prints one JSON object per line and a whole-stream `json.load` therefore succeeds on the single-item subcommands and throws on every multi-item one. `help` prints each subcommand's shape so a run reads it rather than guessing — derived on the GitHub adapter by an ast walk of each subcommand, with nothing to maintain, and declared in a comment beside the `case` arm on the GitLab adapter, which is bash with no syntax tree to walk. `tests/check-api-help-shape.py` re-derives the shape from the code on both and fails on a mismatch, a missing annotation or a value outside the four, because an annotation nothing checks is a hand-maintained list with extra steps. Step 10b inherits all three rules and needs them most: a deploy watch that went quiet because a binary is missing reports no deploy at all, which that step is required to treat as unverified rather than as success

### Reviews outrank CI, and the gates that stay are the point

addressing review comments means pushing, and every push restarts the pipeline — so handling a red or running pipeline before open threads throws away a complete CI run, every time. Four things autonomy never relaxes. `require_human_approval` means a bot's approval does not merge, and the user driving the run counts as the human while other bots do not. **The verdict is re-read in the merge step itself, not carried from the watcher**, because the staleness window is the step's own length: observed here, a reviewer requested changes 77 seconds before the merge and after the last state read, so the merge went through and no amount of care at the earlier read could have caught an event that had not happened yet. Two fields get conflated in exactly one direction — **a review job going green means the reviewer ran, not that it approved** — and a green check beside a rejecting verdict is what that failure looks like from one step back. Changes-requested therefore blocks outright and routes to the feedback loop, while an *empty* verdict stays non-blocking where the repository configures no approval rule; collapsing those two into "no approval yet, carry on" is the bug. A failing job is classified against its log before any retry, because a real failure retried until it looks flaky is the most damaging thing an unattended agent can do — and the same failure twice is not a flake. On repos with an `iac_bot`, the plan is applied and confirmed **before** the merge and auto-merge is never armed, because auto-merge fires the instant the pipeline is green and can beat the apply, merging infrastructure that was never created — and the apply itself waits on the **review**, never on the plan: a green plan says the configuration is valid and shows what would change, which is no evidence at all that the change should happen, so the apply sits behind the AI reviewer's verdict and the `--review` swarm's findings, both where both are relevant. Where neither review exists in a repository the run reviews the diff against the plan itself and records that, because the one thing this gate forbids outright is an apply with nothing but the planning bot behind it. `--merge false` does not switch it off: landing an infrastructure change means apply *then* merge, so that flag holds back only the merge. And the fix skills' Important Rule 1 is now a statement of *accountability* rather than a prohibition on the run: they never push and never open a change request, `autopilot` does, and it owns that one branch and nothing else. Writing it that way is what makes `--autopilot false` reliably mean *nothing left this machine*, and it is what stops an agent quoting the rule back as a reason to refuse the hand-off — exactly the kind of thing one would otherwise infer its way into. `fix-feedback --autonomous` is the one sanctioned relaxation of that skill's "never write unasked" rule; it still never commits, never pushes, and never resolves a thread it disagreed with

### A blocking verdict is cleared, not escalated, and a button press is not a hand-off

The run that exposed this drove a change to three green checks, received exactly one review finding, established that the finding was **factually wrong** — the file it complained about was already committed with the mode it asked for, and the change's own CI had executed it and passed — answered it on the thread with that evidence, and then **stopped and asked the user to dismiss the review by hand.** Everything expensive was already done. The user was away from the terminal, which is the premise the whole skill is built on, and what they were called back for took one click. That is the failure this entry exists to prevent, and it is worse than it looks: a run that stops one rung from the end has spent the entire budget and delivered nothing landable.

The branch is on the **finding**, never on the verdict. A finding that is right, or that cannot be shown wrong, is review feedback and goes through the feedback loop to become a code change — a finding merely disliked is a finding fixed. A finding disprovable from the repository, the diff, or the change's own pipeline makes the verdict *stale*, and clearing a stale verdict is the run's own work: answer it on the thread first so the reasoning sits where a human reads it, then take the first rung the forge helper actually has — re-run the review job, re-run the whole workflow run (a different object from the check run, and re-runnable when it is not), re-request the review where the job triggers on that event, or dismiss the stale review with a message naming the evidence. Three limits hold absolutely. **A finding that has not been disproved is never dismissed**, because dismissal asserts the reviewer is factually wrong about the code and asserting that for convenience is the one abuse here that beats stopping. **No empty or no-op commit** is pushed to shake a verdict loose. And where the helper carries no such subcommand at all, the capability is absent on this forge and *that* is the escalation — named by which subcommands were looked for, per the empty-value rule, rather than worked around.

### The blocking verdict is not in the thread list, and the thread list looks fine without it

A reviewer can block with a review whose **body is empty**, and the threads helper drops empty-bodied reviews deliberately — they carry no text worth reading. The consequence is that every surface a run naturally checks looks healthy: the thread list shows one ordinary inline comment, the pipeline is green, and the forge's own mergeability field reads clean, because mergeability answers *are there merge conflicts and required checks* and not *did a reviewer object*. The only trace is the review-decision field on the status call. So the verdict is read from the status call and never inferred from threads, and where the reviews themselves are needed — their ids, their states, who submitted them — that is a separate listing from the thread listing. Ask the helper's `help`: the two are different subcommands because they answer different questions, and a run that asks the thread question and accepts the answer as a verdict merges over a rejection.

### Two reviews, and the swarm is the one with a filter

the forge's AI reviewer makes a single pass over the finished diff, which is why it misses things worth catching. `review-code` runs a fleet from independent angles and then makes a panel of skeptics try to **refute** every candidate, so only findings that survive refutation are reported — and that filter is the difference, not the agent count. Wiring it into the fix flow is what makes it happen: it was being run by hand, which means it was being forgotten. `--review` is a per-machine default (`fix_review`) rather than a per-skill one: **on** at work, where somebody else is going to read the change, and **off** at home, where nobody is. Two ordering facts are load-bearing and opposite. In `fix-linear` the swarm runs **after** `changes-description`, because only one of the two can invalidate the other: a confirmed finding means a code change, and a description written against a diff that is about to move is the thing that goes stale. In `autopilot` it is launched **in the same turn that arms the `Monitor`**, because the diff is already pushed, CI and the bot are already running on it, and neither gates the other — serialising them there adds a full swarm's latency to a run whose whole point is to need nothing from anybody. `autopilot` has **no default of its own** — all seven live in `skill-env.sh` beside the fix skills' — and the only flags it owns are `--merge` and `--max-rounds`, which describe how far the automation goes rather than what the change is. It overrides nothing, **`--branch` included**: the tempting exception is forcing `--branch new` so a change request exists to review, and it is wrong because that judgment was already made, and made better, by the fix skill's Step 2b escalation checks — Terraform, a protected default branch, a dirty tree. A `--branch default` that reaches `autopilot` survived those on the repository's own terms, so the run pushes the default branch and ends, Steps 5–10 having no change request to drive. **Which skill fires the swarm is about *where*, not whether**: on a run that will open a change request the fix skill does not run it at all and `autopilot` owns it at Step 5b, because fired before the push there is no change request for `fix-feedback` to anchor a finding to; on a `--autopilot false` or `--branch default` run there will never be one, so the fix skill runs it where it stands. It runs once per run, never once per review round

### Autopilot is on by default, and the whole design follows from one number

the user reaches for it on 99% of fix runs, so making them type it is making them type the same token 99 times to get the behaviour they always want. `fix_autopilot` is therefore `true` on every profile and the fix skills *hand over* at the end of their own flow rather than waiting to be wrapped. Three things keep that from becoming a loaded gun. **It automates the tail, not the thinking** — the fix skill's gates stay open, so a vague ticket still gets a question and the plan still gets shown; the user who typed `/fix-linear` is at the keyboard at that moment, and what they asked not to sit through is the pipeline, the review and the merge, which is hours, not the five minutes of deciding. An earlier version had `autopilot` self-resolving those gates, which bought nothing and cost a whole implementation whenever a reading was wrong. **`--autopilot false` is the way out**, and it has to exist precisely because the default is on: it yields a branch, a commit message and a description with nothing leaving the machine, which is what a spike wants. And **the direction of the hand-off is what preserves every ordering decision** — `autopilot` stays the wrapper, so the swarm still fires post-push where `fix-feedback` can anchor findings and the diagram still attaches once the code has stopped moving. Inverting it so the fix skill ran the tail itself would have broken both, silently

### `/autopilot <flags>` mid-run is an amendment, and the rule that matters is what it does *not* touch

the user's two real cases are "I got the verbal go-ahead, merge it" (`/autopilot --merge`) and "actually draw me the diagram and hold the merge" (`/autopilot --diagram --merge false`). So the flags it names change and **every flag it does not keeps its current run value, never the machine default** — re-reading `skill-env.sh` on an amendment would silently revert an earlier amendment, which is worse than ignoring the new one. Each flag then carries a defined catch-up for arriving late, because a flag whose moment has passed is the normal case rather than the exception: `--diagram true` publishes one even after the merge, `--review true` runs the swarm against what is pushed and feeds the findings into a fresh round, `--quick-description false` regenerates the description and replaces it on the change request while a late `true` is a no-op nobody wants, and `--merge false` **disarms an auto-merge already armed** — an armed auto-merge fires on green and would otherwise beat the instruction, which is the one amendment that can lose a race. `--autopilot false` means *stop driving*, never *undo*: nothing pushed is deleted and no change request is closed, because an agent tidying up after a change of mind is how work disappears

### One flag surface across both fix skills, differing by machine and not by skill

`fix-linear` and `fix-freeform` take the same seven flags with the same meanings, because the user types them interchangeably and a flag that meant one thing in one skill and something else in the other is a trap with no upside. They had diverged exactly that way — `--quick-description false` mapped to `changes-description --quick` in one and to the full panel in the other, a 4-agent difference behind an identical invocation. The split that *is* real runs the other way: work gets the full description panel, the diagram and the swarm and stops one step short of the merge because three people and two bots are going to read the change; home gets the one-shot, no diagram, no swarm and merges itself because nobody is. That belongs in `skill-env.sh` rather than the skill text for the reason every per-machine fact does — written into the prose, the two profiles' copies stop being transforms of each other and drift goes back to being invisible. `--branch` has exactly two values, `new` and `default`, in both skills; the old `in place` / `--here` / `no worktree` escape hatch is gone as a user-facing flag and survives only as the automatic fallback for a repo that cannot host worktrees, because a third value on that axis described a combination nobody reached for

### `--quick-description` is about latency, not about agent count

it reads as *spend fewer agents on the description*, and that reading cost the thing the flag is actually for. The user reaching for quick does not care about the description and does care about the change request being **open**; a workflow of any size prints a run ID and ends the turn, so the description, the push, the change request and every later autopilot step all arrive one completion notification later. `changes-description --one-shot` is 4–6 agents instead of 20 and still pays that latency in full, which is why `true` now maps to **`--inline`** — no `Workflow` call, no run ID, no yielded turn, the description written in the same turn and the run carrying straight on to the hand-off. What survives the drop is the half that is arithmetic rather than opinion, and it survives because a lone writer needs it *more* than a panel does: the template and the house rules (the banned design-decisions section is what comes back when nobody referees), the word budget **measured by a command rather than estimated** — the one writer here trusted to respect a stated limit produced 913 words while satisfying every rule it had been given — and a fact-check the writer runs against the diff claim by claim. Two things keep the honesty: the budget snippet in Step 2-INLINE is a hand port of the workflow's `measure()` and says so, since the tiers now live in two places; and the run reports `self fact-checked`, never `fact-checked`, because a claim the author verified and a claim an independent agent verified are not the same claim and the user is owed the difference. `--one-shot` and `--quick` stay reachable by hand and unreachable from a boolean flag

### The decision record is captured early and published late, and the two halves have opposite reasons

an unattended run makes calls a reviewer never weighed in on, so they have to survive the run — but the first version posted them as their own comment on the change request, at the moment each decision was made, with no format and no budget. Every property of that was wrong in a different way. It was **in the wrong place**: a comment is the first thing a reviewer sees, ahead of the diff it discusses, and it cannot be collapsed. It was in the **wrong shape**: unedited generated prose with no word budget and no slop check, which is unreadable in exactly the way the thing it was replacing — a conversation — is not. And it was **unavoidably in a comment**, because `changes-description` does not run until Step 3 and the record was being written before that: there was no description to append to, so the comment was not a choice so much as the only surface left. The fix splits the two. **Capture stays at the moment of the decision** — a line appended to a local scratchpad ledger — because a ledger reconstructed at the end of a long run is reconstructed from memory and the entries it invents read exactly like the ones it remembers. **Publication moves to the end**, one edit appending the ledger to the description inside a collapsed `<details>` fold, which is the whole point: present for whoever wants it, invisible to whoever does not. Two things keep it short, and the filter matters more than the formatting: **an entry earns its place only if a reviewer could reasonably have decided differently**, which excludes following an existing pattern, doing what the ticket said, and anything the diff shows faster — and more than about eight entries means the filter was not applied rather than that the cap is too low. The budget is 25 words per entry against `docs-humanize`'s `HARD_SLOP`, matched on a whitespace-flattened copy. **The fold's label is `Relevant Decisions (N)` and is fixed**: it read `Decisions made without review`, which describes the *run* on a surface that belongs to the *change* — a reviewer opening it is told, in the author's own change request, that what follows got less scrutiny than normal, and it is the author who wears that rather than the automation. The run's autonomy is a fact about the run and goes in the Step 11 report, where the user can act on it; the fold is just the judgment calls behind a change, which is an ordinary thing a change request carries. Three traps are written down because each one silently reintroduces the original problem: a `--quick-description false` amendment **replaces** the description and drops the fold, so it has to be re-appended from the ledger; the fold sits outside `changes-description`'s mechanical word budget and must never be handed to that skill as input; and a failed description edit **must not fall back to a comment** — it reports and carries the ledger in the run report, because the fallback is the exact surface the design exists to avoid

### "Merged" is not "deployed", and the gap is where an unattended run lies without meaning to

`autopilot` used to end at the merge, which reports on the easy half — the merge succeeds, the run says success, and the deploy goes red twenty minutes later with nobody watching. Two steps close it. **Step 0b runs before the merge gate**, which is the non-obvious half of the placement: a verifier that works out the deploy path *after* merging has already merged, and if it finds nothing it is too late to say so usefully — whereas run early it also tells a `--merge false` user what pressing the button will set off. It establishes the trigger (which jobs fire on a push to the default branch, *not* on a tag or a manual dispatch — a tag-triggered deploy does not fire on merge and saying it did is a lie with a green tick on it), the target (read the job, not its name — a job called `deploy` might print a plan and stop), and the observable signal, which is the one that gets skipped and the one that decides whether verification is possible at all. Plus two facts about the run's own position: whether this session can see the signal, and how long the repo's own recent runs take, which becomes the budget — a budget invented from nothing is either a false alarm or a watch that never ends. **It is derived contextually and never enumerated**, because repositories differ, the same repository changes, and a baked-in expectation is worse than none for the usual reason: it keeps passing after it has gone stale. "Nothing deploys" and "the path is unreadable from the repo" are both complete answers to record rather than gaps to paper over. **Step 10b then verifies the new revision, not that something succeeded** — every subtle post-merge failure has one shape, something green about the wrong commit: a pipeline that passed for the previous commit, a rollout that succeeded because the manifest never changed, a GitOps app Healthy on the revision it synced an hour ago, a mutable tag that let the workload restart onto the same image. All four are indistinguishable from success one step back, so every check is tied to the landed SHA. Five terminal states, and the value is in the last three: **cannot-observe and timed-out are never upgraded into success**, because being told a deploy worked when nobody established it is strictly worse than not checking — the user stops checking too. And it **warns, never remediates**: no rollback, no revert, no re-running a deploy job (Step 7's retry classification is about CI jobs, which are expected to be idempotent; a half-applied deploy run twice can do what neither run would), no touching the runtime. A `--branch default` run routes through it too and needs it most, since nothing reviewed that change and it is already on the branch every other checkout is cut from; in a stack an intermediate failure **stops the stack**, because merging the next change onto a broken default branch is how one bad deploy becomes three

### The phone is armed at the start of the run, by whichever skill the run starts in

notifications are opt-in per session and the opt-in is a *sent* ping — `notify.py` writes `armed_at` only on a successful send and otherwise logs `skip: session not armed`. Autopilot originally pinged only at Step 11, which arms the session **after the run is over**: the hours in between, where a permission prompt or an `AskUserQuestion` or a failure actually happens, ran into a session that could not speak. Observed exactly that way — a `/autopilot --merge` handed over mid-work, drove a change request to merge and verified the deploy, and never armed anything. So Step 0d sends one `progress` ping before the first unattended step, carrying what was taken over and where the run will stop, which does both jobs at once: it confirms the hand-off and it arms everything that follows. Four details keep it from becoming noise or a dependency. It is **skipped when `armed_at` already exists**, since the user has already opted this session in and a second announcement is just noise. It is **never sent on `--autopilot false`**, where there is no unattended tail for *this* skill to notify about. **A failed send never fails the run** — an unconfigured `notify.json` makes it a no-op, and the `ping` skill deliberately withholds `armed_at` on a failed send rather than opting a session into notifications it was just told did not go out. And **every route arrives at Step 1 armed, the mid-run amendment included** — that is the route most likely to be missed, because the run is already in flight with Step 0d behind it, and it is simultaneously the clearest possible statement that the user is leaving

**Fixing it only in autopilot fixed the wrong 4% of the run.** A hand-off happens at the *end* of a fix skill — line 404 of `fix-freeform`'s 422 at the time, and the same shape in `fix-linear` — so arming there left the phone mute through the interrogation, the plan-approval gate, the whole implementation and the description. Every step a user actually walks away from is in that window, and the user reported it as a run that "forgets to arm the ping"; it was never forgetfulness, because neither fix skill armed at all. One `/ping` token in the invocation was wired up first, which covered the run that announced itself and left the default silent. So **both fix skills now arm unconditionally at their own Step 0**, in the same tool-call batch as the checklist publish and with the checklist URL in the body, and the hand-off becomes the *skip* path rather than the send — one announcement per run, at the start of it.

Three things decide the shape, and the first is why the justification is not copied from Step 0d. **Starting a fix run is not the gesture Step 0d is about.** The user is at the keyboard as they type it, so "they are walking away" cannot carry the argument. What carries it is the asymmetry of the latch: arming early costs **one notification the user is present to ignore**, since `min_interval_seconds`, the turn-length floor and quiet hours all still gate everything after it, while arming late costs **every silent event before the latch**, unrecoverably, because they went nowhere. The memory rule against pinging a present user is about not re-sending what they just read and has never covered an arming ping. **`--autopilot false` arms too**, which is the one case that had to be decided rather than inferred: autopilot's own *never arm when `--autopilot false`* is scoped to its unattended tail, which such a run never reaches, and reading it as a rule about the fix skills would leave the plan gate of every spike silent. And **the three statements of the old behaviour had to go with it** — the two fix skills each claimed at their plan gate that "the arming ping does not go out until the hand-off", and autopilot's route list said the hand-off arms. A gate whose stated reason for existing is a fact that is no longer true is worse than one with no reason written down, because the next reader fixes the prose instead of the behaviour

### The merge request's link is pushed when it is created, not when a turn mentions it

the opening ping arms the phone before there is anything to link, and the closing ping goes out after the merge, so for the whole interesting middle of a run the link was delivered by accident or not at all. The accident is specific: the automatic turn-end notification appends a change request's URL **only when the body already names one**, and that body is a model's summary of the turn — a turn whose headline was *opened it and armed a pipeline watcher* summarises as watching CI, so the link never appears and nothing reports that it didn't. Observed from the user's side rather than the run's: a merge request available for hours, no message about it, and under `--merge true` the first link arriving after the change had already landed. Hard-filtering on it in the hook was rejected, because this file's own notification rules record that appending a link to any body lacking an `http` was wrong in both directions. So the fix is timing, not matching: Step 4b pings at level `progress` in the same batch that opens the request, with the URL in the body, where the existing resolver picks it up for free. Three things keep it honest. It is **owed even when the opening ping was skipped**, since an `armed_at` that already existed means the user left earlier, not that anything told them about this change request. It is **not owed when the opening ping already carried the URL** — the resumed and amended routes, where the request can already be open before Step 0d runs, and where two notifications minutes apart carrying one link is exactly the noise being avoided. And it is an **item on the run checklist** rather than a third sentence of prose, because this is the same class of obligation as arming, which was stated twice in `autopilot` and skipped anyway: `link`, discharged by `ping`, ticked with the outcome so a send that failed reads `skipped` with its reason instead of `done`

### A pause is only graceful if it was affordable, which inverts where the work happens

the moment a run needs to pause is the moment it has least quota to pause with, so a `/pause` that composes a twelve-section state file from scratch does not finish — and a truncated state file is strictly worse than none, because it reads as resumable. The run therefore **journals as it goes**: the step and round, the `next_action` as an instruction, and the decision ledger text, appended at every step boundary exactly as the ledger already is, so the pause itself is one atomic temp-file-and-rename. Everything else (forge state, `git` state) is read at pause time, which is cheap; prose is not. The second constraint is that **the state file must stand alone without the transcript** — by resume time the context may be compacted and the session closed, so a path to something is not a record of it. That is why the ledger is **inlined as text**: it lives in the session scratchpad, which is session-scoped and reaped by the OS, so a resumed run in a fresh session finds nothing and Step 11.3 publishes an empty fold. The corollary is that pausing *during implementation* is not supported at all — the interrogated statement, the locked plan and the gate answers exist only in the transcript, so that case stops and pings rather than parking

### Stopping a run means stopping it, not noting what was running

an armed `persistent: true` watcher survives a pause, wakes the paused session, spends the window the pause existed to protect, and hands control to a step that starts work — it un-pauses the pause. So `pause` `TaskStop`s every watcher and records a **re-arm instruction**, not an inventory. The same logic forces the unsafe-park list, where each entry is a specific mechanism rather than caution: an **armed auto-merge fires on green while you are away**, so it is disarmed first; a **dangling `AskUserQuestion`** is swallowed by a paused session along with the answer the user is mid-way through giving; a **merge whose deploy is unverified** turns a "paused" ping into "nothing is wrong" while production may be broken. One state had to be allowed rather than forbidden: a **running infrastructure apply can outlast a whole window on its own** and can be neither pushed through nor unwound, so pausing there is permitted, the hazard leads the ping, and resume re-reads the apply markers **per directory** before considering the apply comment — it is posted once and idempotently, and a resumed run that re-posts has triggered a second apply. The adjacent state worth naming: apply succeeded, merge not yet done, means infrastructure exists that no merged code uses

### The resume trigger is a detached background poll on wall-clock, and all three of those words were wrong at first

`Monitor` is the house mechanism for waiting, and it is wrong here because `timeout_ms` is hard-capped at 30 minutes against a window that can be hours out — ten re-arms, each a wake spending the budget being protected. A detached background command keeps running across turns and re-invokes the session once on exit; measured at 660s with exit 0, so the Bash `timeout` cap does **not** apply to `run_in_background`. The exit condition then has to be **wall-clock against the absolute `resetsAt`**, never the usage percentage: once the editor windows close, nothing refreshes the usage cache, so a poller waiting for a percentage to drop waits forever and reports nothing. And it compares `date +%s` rather than counting iterations, because a `sleep` loop stops accumulating while the laptop is suspended. The house rule that silence must never look like success binds the poller too — it emits on a missing cache, a stale cache, a `retryUntil` still in the future and a max-wait backstop, not only on a clean reset. **Auto-resume is session-window only**: a refreshed 5-hour window is a reasonable thing to restart on, a spent weekly quota is the user's call, and the stricter window always wins — so weekly, `scoped:<Model>` and `spend` are all re-read *at wake*, not trusted from pause time, since weekly can go from 70% to 99% while the poller sleeps

### Quota is read from the `claude-usage` cache and never from the API

`/api/oauth/usage` is rate-limited per account and the Claude Code CLI already polls it from every open session, so another caller is how a run throttles itself. The cache is written atomically (tmp + rename) so reads need no lock — and **taking `usage.lock` is forbidden**, because a holder makes every editor window skip its own refresh and a dead holder stalls them all for a minute; **writing anything into that directory** is equally forbidden, since a file-watch there fires in every window. `percent` is quota *used*, `resetsAt` is absolute epoch **milliseconds**, and the meter ids are `session`, `weekly`, `scoped:<Model>`, `spend`. All four are read at a `/unpause` wake, because a `session` at 40% with a model-scoped meter at 100% fails every agent launched while the headline reads healthy — but **only `session` gates an autopilot pause**, and reading one of the other three as a reason to stop is the failure recorded at the end of this paragraph, which happened a second time: a run stopped to ask whether to spend a review swarm at `weekly 85%`, holding an approved change request one step from the merge. They are diagnostic there, never budgetary, and never a question. Two fields look like freshness and only one is. `snapshot.fetchedAt` is when the numbers were fetched and is what the extension itself displays — `adopt()` reads `cached.snapshot?.fetchedAt ?? cached.updatedAt`, and both the chip and the tooltip age off that — while the top-level `updatedAt` is when the **file** was last written, which `canReuse()` pairs with `intervalMs` to decide whether to refetch. On a success path the two agree to the millisecond, which is how the distinction stayed hidden; but `publish()` writes `updatedAt: Date.now()` on every publish **including the failure paths**, where the previous snapshot is still attached, so `updatedAt` is the optimistic one in exactly the case where the numbers are stale. So freshness is `snapshot.fetchedAt` with the top level as the fallback — which is also what `cache.ts` substitutes when a snapshot carries none — and the cadence is read from the file's own `intervalMs` rather than named in prose, since a run that asserted `60000` against a live `480000` was wrong about the whole calculation. The reading that caused all this was not a timestamp at all: the status bar draws **one chip per meter**, and a run quoted a weekly percentage as though it were the session window — then killed two review swarms, planned a pause, and told the user their own extension was less reliable than its reading. Hence two rules on top of the field names: every percentage a run quotes **names its meter**, and because this is the same file the extension reads, a disagreement with the status bar is a reading bug rather than evidence against the extension

### A swarm's resume cache is keyed on the diff, and the chain of run ids is cumulative

the `Workflow` cache is content-addressed over each agent's whole prompt and `review-code` embeds the literal unified diff in its `args`, so a single changed line changes all 26 keys — there is no per-file partial reuse to exploit. The ordinary pause (nothing happens in between) leaves the diff byte-identical and every finished agent replays free; a branch that **moved** while paused voids the cache entirely, and the right answer is a full re-run rather than a harvest, because the cached findings describe code that no longer exists and a partial review is not a review. Two traps on top. A resumed run journals only its **own live agents**, so resuming off the newest run id discards the previous generation — the state file keeps an **ordered chain** of every run id per logical swarm and `workflow-runs.py merge` unions them, which makes repeated pause/resume accumulate instead of reset. And **`cleanPrefix` is the wrong number to reason from**, because it counts only the contiguous run from the start: a 26-agent run that lost agent 3 reports `2` while 23 results sit cached and eligible, which read literally argues for re-running a run that is nearly complete. `resumeFromRunId` reuses every completed agent whose key still matches rather than a prefix, so **`finished` is the figure that predicts the saving** and `cleanPrefix` is a lower bound — neither gets recorded in the pause state, both get read fresh

### `scriptPath` is a trap for resuming a swarm, and `workflow-resume` is the one place allowed near `resumeFromRunId`

every `Workflow` call snapshots its script to disk and offers the path back for a cheap re-run, which is exactly wrong when the reason you are re-running is that the skill had a bug. The snapshot is frozen, so resuming through it silently replays the *pre-fix* pipeline while the run looks entirely normal — and it has already happened here once, a fixed skill bypassed by a `scriptPath` pointing at the snapshot from the very run it was fixing. `review-code` therefore forbids `scriptPath` and `resumeFromRunId` outright and names `workflow-resume` as the single sanctioned exception, because that skill pairs `resumeFromRunId` with the script **re-read from the live `SKILL.md`**. Both halves work at once for a non-obvious reason worth keeping: the cache keys each agent on its own `(prompt, opts)`, so an edit that does not touch an agent's prompt leaves that agent replaying for free and only the agents the fix actually changed re-run. The cache is reused *and* the correction is not discarded. The `script` subcommand of `workflow-runs.py` exists to **diff** snapshot against live so the cost is knowable before anything is spent — its own help text says diff only, never resend. Rewriting `workflow-resume` got this backwards on the first attempt, which is the argument for the rule being written down somewhere other than the skill it protects

### Recorded authority survives a pause; recorded evidence does not

a `--merge true` chosen before a five-hour gap still authorises the merge, because a run that stops to re-ask has failed at being unattended — but the approvals, the pipeline state and the apply markers are all re-read, and the ordinary gates then apply to what is actually found. `require_human_approval` is unchanged by a pause. This is why forge state is recorded as *inputs to a diff* and never as substitutes for looking, and why thread state needs an author class plus committed/pushed flags rather than a flat list of ids — a finding the run posted and never fixed is not new reviewer feedback, and treating it as such duplicates both the comment and the fix. Per-job CI retry counts go in for the same reason: without them a resumed run blind-retries a failure it already retried, which is the single most damaging unattended behaviour. And `diagram_attached` / `ledger_published` go in because Step 11 is only partly idempotent — without them resume appends a second collapsed fold to the description

### Run state belongs outside the repository, and the old path proved why

`git/ignore` covers only `**/.claude/settings.local.json`, so `autopilot`'s original `.claude/autopilot/<run>/stack.json` sat untracked in whatever repo the run happened in — visible in `git status`, committable by a run that stages broadly, and noise in the pause state's own dirty-tree diff. Both it and `~/.claude/pause-state/` now live under `~/.claude`, which is outside every repo. The pause state is keyed by repo and branch rather than by session id so a *different* session can find it, and a `SessionStart` hook already exists in every profile if automatic discovery is ever wanted; a stack run additionally records the ordering and which members merged, or "never arm auto-merge on a change request whose predecessor has not merged" breaks on resume. A state file nothing expires is a loaded gun, so resume checks for a superseded run — merged elsewhere, branch deleted, recorded HEAD unreachable — and archives rather than acting

### A resumed run must enter its worktree before anything else

the wake can land while the session's working directory is somewhere else entirely, and **subagents inherit the session's working directory** — so a swarm launched from the wrong place reviews the wrong repository and looks entirely plausible doing it. The wake is also an event rather than a user turn, so an interleaved wake authorises no irreversible action (no push, merge, apply or comment) without announcing itself first: a merge arriving unannounced while the user is mid-conversation about something else is indistinguishable from a bug. And the one free moment to ask is an interactive gate — a blocked `AskUserQuestion` spends nothing while it waits, so the threshold cannot be crossed during the wait, and when the answer does arrive the user is demonstrably at the keyboard; that is the one point where "the window is nearly out, pause or push on?" is both cheap and correct rather than decided silently from a threshold

### Deleting the merged branch is part of merging, because it is the signal something else waits on

`wtclean` decides a worktree is finished by its branch's upstream being **gone**, and that is its only signal — so `autopilot` merging and leaving the branch on the remote means the worktree, the local branch and the checkout sit there indefinitely while `wtc -y` reports nothing to remove. Observed on this repo: three merged change requests, three surviving branches. The forge hides half of it — GitLab's `create-mr` sets `remove_source_branch=true`, so work cleans itself and only the GitHub side rotted, which is exactly the shape of bug the profile transform cannot catch because the skill text was identical and the *forge* differed. The fix is `git push origin --delete` at **confirmed** merge rather than a per-forge merge flag, because one line then covers a direct merge, an auto-merge the forge performed later, and a human merging mid-run, and `remote ref does not exist` becomes a success rather than an error. Two things it must not touch: a stack member's branch while an open change request still targets it (some forges retarget a dependent change request when its base is deleted and some leave it pointing at nothing), and the worktree itself **while standing in it**. That last one is what Step 10d then resolves rather than leaves: a run that deletes the remote branch and stops has produced the signal and left nobody to read it, so the worktree and the local branch sit there until the user next thinks to look — which is the original complaint one step further along. So after the deploy question is settled the run moves to the **main working tree** and invokes the user's own `freshen`, which pulls the default branch up and runs `wtclean --no-fetch -y` behind it. Three things about that are easy to get wrong and were all verified rather than assumed. It must run **from the main checkout**, because `wtclean` deliberately skips the worktree you are standing in and on this run that is precisely the finished one. **`freshen` is an interactive alias**, so `zsh -c 'freshen'` exits `command not found` and it needs `zsh -ic`; the `can't change option: zle` that an interactive zsh with no tty prints is noise, not failure. And **getting to the main checkout is the `ExitWorktree` tool with `action: "keep"`, not a `cd`** — the first draft prescribed `zsh -ic 'cd "$(git -C <main> rev-parse --show-toplevel)" && freshen'` and a `--branch new` run, which is inside the finished worktree at that point by construction, cannot run it. Measured from inside one: the isolation guard refuses **every** `zsh -ic '…'`, including a payload naming neither `cd` nor `git`, so the diagnosis that it was the command substitution was wrong and a narrower fix would have left the step just as unreachable — `freshen` is interactive-only, so no Bash route to it survives. A bare `cd` to the main root *is* accepted and still does not help, because the harness resets the working directory back to the worktree once the command returns. The exit lifts the isolation and lands the session where it launched from in one move, which is what lets the command drop both the `cd` and the path; `keep` is the action because the worktree was entered by path rather than created by the tool, so the step removes nothing and leaves `wtclean` to judge it on its own signal. The session's own working directory can still be deleted underneath it, so nothing reads from the old path afterwards. It never fails the run, since the change is already merged and none of this is on the critical path

### Review findings are persisted, not just chatted

a `review-code` swarm finding lives only in the transcript, so `fix-feedback` Step 3b posts every finding the MR does not already carry as its own anchored comment *before* working through the queue — deduped against the MR's existing threads (fetched, not assumed from context) and against comments an earlier run posted, which it recognises by their hidden `<!-- review-note:<dimension> -->` marker. Posting is one batch approval; a posted finding gains a discussion ID, so the reply drafted when the user rejects or modifies it lands back on that same thread. **Nothing in a posted body says where the finding came from** — Rule 9 — and the marker is what makes that affordable rather than a thing to remember. It used to be a visible `🤖 **review-code — <dimension>**` header that the skill told the run to keep *exactly as written*, because dedup matched on it: the recognition token and the attribution were one string, so removing either removed both. An HTML comment separates them. GitLab and GitHub each strip one out of the rendered view and each hand it back verbatim from the API, so a later run finds its own comment by an exact match on a line no reader ever sees, and GitHub's extra thread-id round trip in 3b.5 is unaffected. What a reader sees in its place is a bare `**correctness**` label — the categorisation a human reviewer writes anyway. The rule is not cosmetic: a finding attributed to a tool invites the reader to weigh the tool instead of the defect, and the account that posted it is accountable for it on the thread either way. The chat side keeps its `review-code: <dimension>` tags, because that is the user's record of their own run rather than something that leaves the machine

### A published link is appended bare

a label and the URL, with nothing after them. `autopilot` Rule 17 holds that end — the run checklist at Step 4b, the diagram at Step 11.2, and anything linked there later — and `changes-diagram` Step 7 holds the other: the sentence about what the page embeds is said to the user in the chat and never travels with the link. Both annotations were real sentences somebody wrote on purpose, and both were noise where they landed. The checklist's "what this run still owes, updated as it goes" restated the page's own heading to the one reader who had just been told what the page was for. The diagram's "private; the diff of every changed file is embedded in the page" was **false** on a work box, because `publish-artifact.sh --purpose diagram` publishes **public** precisely so the merge request's reader does not meet a login screen — so the annotation contradicted the configuration it was describing. That is the shape worth keeping: an annotation beside a link is written once and read on every change request, and it goes stale against whichever store published the page. The reach note itself survives, since deciding whether to share a link needs it; it is scoped to the chat and to the store that applies, and a local file earns no sentence at all

### `/resume` is a built-in, so the skill is `/unpause`

Claude Code already ships `/resume` as the past-session picker, built-ins are not skills and win the name, so a skill called `resume` is simply unreachable. Worth remembering as a class of bug — a skill name that silently never fires looks identical to a skill that does not work

### A `$<digit>` anywhere in a skill body is rewritten at invocation, so a skill may never contain one

the harness substitutes the user's argument words into the skill text it hands the model, and it is **zero-indexed** — invoking a skill with `ALPHA BRAVO CHARLIE DELTA` turns `$1` into `BRAVO`, which means `$0` becomes `ALPHA` and is just as exposed. That is catastrophic in an `awk` program, where `$1`…`$3` are the fields and `$0` is the whole record: `review-kludge`'s churn ranking arrived as `added=BRAVO; deleted=CHARLIE; path=DELTA`, and `review-code`'s `substr($0,10)` became `substr(ALPHA,10)` — an unset awk variable, so `ROOT` silently went empty and the review worktree path it builds rooted itself at `/`. **The failure is invisible from the repository**, because the file on disk is correct and only the rendered copy is corrupt, so it survives every `grep`, every review and every CI check; the only way to see it is to invoke the skill with arguments and read the text that comes back. Verified safe in the same render: `$(…)`, `${…}` and `$<letter>` all pass through untouched, so `$(NF-2)`/`$NF` and `sub(/^worktree /, ""); print` are the forms to reach for, and a shell variable needs no defending. `$ARGUMENTS` is the one substitution that is wanted. The sweep that finds them all is `grep -rn '\$[0-9]' --include='SKILL.md' profiles/`, and it must include `0` — looking only for `$1`/`$2`/`$3` is what hid the `review-code` instance

### `acceptEdits` is the mode that makes an unattended run unattendable, and the destination after a plan is not a setting

approving a plan into "edit automatically" auto-approves edits and filesystem commands and then **prompts for every single `Bash` call**, which on an autopilot run means the user is interrupted constantly for exactly the hours the mode exists to cover. `auto` is the one that differs where it matters: a classifier reads each shell command and blocks the dangerous ones rather than asking about all of them. So `permissions.defaultMode` is `auto` on every profile that ships a `settings.json`. Two limits are worth knowing before reaching for this again. **The post-approval mode is chosen at the ExitPlanMode prompt, not by any key** — per the docs there is no setting that forces an approved plan into `auto`, so `defaultMode` sets the session's baseline and the gate's own answer still wins; `useAutoModeDuringPlan` (default `true`) governs behaviour *during* planning and not after it. And **`auto` is a real reduction in oversight**, not a formatting preference: it is the classifier's judgment standing in for the user's on every shell command, which is the trade the mode is, and is why it is recorded here rather than left as an unexplained key.

### Plan mode is not what gates `Bash`, and a compound command is judged segment by segment

a planning run that stops to ask about `git log` reads as plan mode being read-only, and that mental model is wrong in a way that costs a whole unattended run — per the Claude Code docs, plan mode blocks edits and leaves `Bash` entirely to the permission rules, so `permissions.allow` pre-approves there exactly as anywhere else and only `permissions.ask` still forces a prompt. The allowlist being thin is the whole cause. The non-obvious half is that Claude Code **splits on shell operators** — `&&`, `||`, `;`, `|`, `|&`, `&` and newlines — and **every segment must be allowed**, so a rule is worth nothing against a command whose other half is not covered; a built-in read-only set carries the common readers without a rule. That is why the entries added here are per-subcommand and read-only (`Bash(git log:*)`, `Bash(git diff:*)`, `Bash(git rev-parse:*)`, `Bash(rg:*)`) rather than a blanket `Bash(git:*)`, which would also pre-approve `git push` and `git reset --hard`. `settings.json` is in the transform-enforced set, so the three copies differ only by the forge helper's name and an entry goes into all three at once.
