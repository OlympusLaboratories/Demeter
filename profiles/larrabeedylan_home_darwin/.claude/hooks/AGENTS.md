# `hooks/` — the hook scripts and the notification channel

Two hooks live here and both are registered in every profile's `settings.json` by a
`$HOME/.claude/hooks/<name>` path, so they resolve on any machine.
`link-worktree-session.py` files a worktree's transcripts under the main checkout's
project slug. `notify.py` is the notification channel: it pushes to the user's phone on
`Stop`, `StopFailure`, `Notification`, and `PreToolUse` for `AskUserQuestion` and
`ExitPlanMode`.

Three invariants hold across everything here, and the root `CLAUDE.md` states them.
**Every path logs and exits 0** — a hook that fails is invisible, so a wrong gate and a
broken token must be distinguishable in `~/.claude/notify-state/notify.log`.
**Nothing here holds a turn open**: one HTTP POST and exit. And **the channel is one-way**
— a notification says *come and look*; it is never the thing that lets the user answer.

Delivery is the only transport-specific part: Slack and Telegram differ in how a reply
notifies, which is why `scripts/notify-send.sh` is allowlisted out of the profile
transform while composition is shared.

## What an edit here has to know

- **A rule telling a skill to include the change request's link is an instruction a model forgets, so the hook finds the link itself**: pings routinely named a change request — "shipped (PR #11)", "working the review" — with no URL and often no number, leaving the user to hunt for it from a phone, which is the one place hunting is most expensive. Both the `ping` skill and `autopilot` already *said* to include it; saying it is what failed. `notify.py` reads the URL out of the session's own transcript and appends it to any body that carries no link. **The link is taken from the forge's own answer rather than from prose**: `html_url`/`web_url` is a key only the API helper emits, so a worked example, a fixture, or a link to somebody else's change request cannot reach it — and it is the only signal that stays correct when the session's checkout and the change request belong to **different repositories**, which is the ordinary case for a run driven from one clone against another. A transcript carrying no such answer falls back to the most recent URL bearing the session remote's own `owner/repo`, resolved from `git remote get-url origin`, because **recency alone picks the wrong URL**: the first implementation returned `gitlab.com/o/r/-/merge_requests/9` from a test string echoed minutes earlier, against a session whose real change request was `merge_requests/10`. **Nothing is answered from the cache while a scan can answer instead.** Caching the first URL found read as free — "it cannot change for the life of the session" — and is wrong twice over: a session merges one change request and opens the next, so the cached value is the oldest rather than the current one; and the cache feeds itself, since reading the state file back into the transcript makes the stale URL the most recent URL in it. Observed exactly that way — every ping for hours carried a merged change request belonging to a different repository. The cache survives only as the answer for a scan that found none. One case is knowingly left through: a session editing **this hook** with a keyed fixture in a tool result, where the fixture is indistinguishable from the real thing.

  **Recency within the forge's own answers was still wrong, and the repo filter only existed on the fallback.** `change_request_answered_in` returned `found[-1]` of *every* keyed URL in the window, so any transcript naming more than one change request — a listing, a stack's base, comment URLs on something else, a review bot's payload — handed over its last entry. Observed on this machine: a session titled "OLY-13 Fix and Merge" holding Demeter `pull/23`, while OLY-13 had landed as `pull/22`. The repair is a **preference order rather than a filter**, and the distinction is the whole of it. Hard-filtering tier 1 on the session's `owner/repo` is the obvious fix and destroys the one case this tier exists for — the cross-repository run the paragraph above calls ordinary — so the order is: the record opened from the session's **current branch**, then one carrying the session remote's slug, then a **lone** cross-repository answer, and nothing at all when a listing matches none of them. That last clause is what stops a foreign `pr list` winning by default while a single foreign answer still does. **Each tier gets its own `scan_tail` pass, and that is the whole of why the order works.** Evaluating all three inside one finder silently degrades the order to *preferred within the tail chunk*: `scan_tail` reads the last 256KB first and returns on the first answer, so a slug-only record near the end beats the branch-tagged record that opened the session. Measured on a 497KB transcript — the branch's own change request lost to an unrelated one 77 lines from the end, which is the exact defect class this change exists to remove. Three passes cost three scans of a tail that is already in the page cache, and each widens independently, so the branch match wins from anywhere in the file. **The branch and the state cost nothing to know**: the forge helper emits one flat object per change request and the keys naming both are siblings of the URL — `head` from `create-pr`, `source_branch` and `state` from `pr-info`, and `pr-for-branch` lists only open ones — so `change_request_records` reads them out of the transcript rather than calling the forge. That matters more than it looks: the ticket asking for an open-only link described the state as available "from the forge helper", and a live call here would be a second network request inside a hook whose first invariant is one POST and exit. A record the transcript shows **closed or merged** is dropped at every tier, and each tier needs its own check for a different reason. The prose scan needs one because the regex otherwise re-finds the URL inside the very answer that declared it closed. **The cache needs one because it outlives the evidence**: both scans correctly reject a merged change request, fall through, and the cache then hands back the exact URL they just rejected — found by running the code rather than reading it, and the reason `change_request_closed_in` exists. An **absent** state is unknown, not closed, so suppressing on it would have silently deleted both fallback tiers; a cached URL the transcript says nothing about still answers.

  **Neither marker had an age bound, and one of them was never read at all.** `cmd_gate` wrote `{"url", "at"}` and nothing anywhere read `at`, so a plan gate recorded many turns earlier was still appended verbatim to the next `Stop` — the reported "link that was only relevant many messages ago". The TTL is not a free parameter: the three retentions in this file's plan-gate section — a failed send, a rate-limited turn, quiet hours — are a contract, and a stated quiet-hours window can run eight hours or more, so a threshold under that would silently break the guarantee it sits beside. 12h for `gate_pending`, 4h for the `change_request` cache, which is only ever the answer for a scan that found nothing. A marker carrying **no** timestamp is kept rather than aged out, since an absent field is an older writer rather than an old plan. The cache reader accepts both the bare string it used to be and the `{url, at}` it is now, so no state file is thrown away.

  **A URL this hook records has to look like one.** `cmd_gate` accepted any non-empty string, and `mark_gate` grepped `https?://\S+` out of arbitrary publisher stdout and took the last match. Together they are how `https://example.invalid/abc` reached a real notification: `tests/check-publish-artifact.sh` ran against the developer's own `$HOME` in call sites that had not stubbed `NOTIFY_HOOK`, so the test's placeholder was written into live session state and the next turn end appended it. Commit `9d003cb` isolated the test; these are the two gates behind it. `cmd_gate` requires http(s), a host with a dot, no whitespace, and refuses the RFC 2606 reserved TLDs (`.invalid`, `.test`, `.example`, `.localhost`) — which is exactly what a placeholder is — then logs the rejection and exits 0 like every other path here, leaving any gate already pending untouched. `mark_gate` stops scanning for a URL anywhere in the output and takes the publisher's **last line**, accepted only when that whole line is a URL, which is what the publisher actually prints.

  **The append fires on two conditions now, and the old one was wrong in both directions.** It used to append whenever the body contained no `http` at all. So a line about a cron migration was given a change request's link it never mentioned, and a line naming a change request *beside* a published-plan URL was given none — because `"http" in body` cannot tell a plan page from a pull request, and the one link on the lock screen the user could act on was the one it suppressed. The body must now **name** a change request, and must not already carry a **change-request** URL. Two traps in the naming regex. It lives in a file the profile transform rewrites, so a literal `PR` or `pull request` would arrive on the home side as a duplicated alternative — writing it `\b[MP]R\b` and `\b(?:pull|merge)\s+requests?\b` spells neither substitution's left-hand side and is what keeps `notify.py` byte-identical across all three copies. And the bare token is case-**sensitive** while the numbered form is not, because `\bMr\b` under `re.I` matches a person's name.

  **`summarize` rewrites the body before both URL injectors, and nothing checked its work.** `SUMMARY_PROMPT` politely asks the model to reproduce a URL verbatim; the word-count trim could then cut one off the end of the line regardless. Either failure produces a notification naming a change request with no way to reach it, and a *mangled* number is worse than a missing URL because the result is syntactically valid, satisfies the suppression guard above, and keeps the correct link out. So the output is measured against the input: every URL the summarizer was given is re-extracted from its answer, and one that did not come back is re-appended **after** the trim, which is what makes the trim incapable of being the thing that removed it. A URL that survived is not duplicated. A mangled one is left where it is with the real one added beside it — dropping text the model produced is the riskier repair, and the body is read, not parsed.

  **Four details in `restore_urls` are each load-bearing, and the first two were wrong in the version this replaced.** Presence is tested by **set membership over `urls_in(line)`, never by substring**: `".../pull/7" in ".../pull/70"` is true, so a substring test treats a mangled number as proof the real URL survived and silently drops the correct link — precisely the failure the function exists to prevent, and it made the test for it pass vacuously. The source is the **un-windowed** `strip_markdown(text)`, not `window()`'s output: `window()` cuts at 5333 characters and a URL straddling that cut becomes a fragment, so reading the windowed text appended `https://github.com/ow` to a real notification. The model only ever sees the windowed copy, which is unavoidable; what is restored is the whole URL from the full text. The append is **capped at `RESTORE_URL_MAX`**, because a body naming a dozen links otherwise turns a 75-word notification into a wall of them. And the cap **ranks change-request URLs first**, so the one link the user can act on is never the one the cap discards.

  **A bare `#123` no longer counts as naming a change request.** It was in the first version of the naming regex and it fires on "shipped release #3", "closed issue #412" and every other numbered thing, which is the Part D defect wearing a different hat. The trade is deliberate and worth stating: a body whose only reference is `#7` now gets no link. Every body this repo's skills actually write says `PR`, `PR` or "pull request", all of which still match. `notify.py --ping` runs this resolution for the `ping` skill's own message, so the deliberate path gets the link by **not** composing its own envelope: it reaches this code instead of reimplementing it, and the append happens on the one path both kinds of notification share. `--change-request <session-id>` stays as the standalone query.

### Hooks

One script per hook under `.claude/hooks/`, duplicated across profiles like `scripts/`. Two live there: `link-worktree-session.py` and `notify.py`. Register it in every profile's `settings.json` using `$HOME/.claude/hooks/<name>` so the path resolves on any machine. **Claude Code spawns hooks with a bare `PATH`**, not your shell's — a `#!/usr/bin/env python3` hook resolves at your prompt and never under mise, and the failure is silent from the user's side, so the installer probes each hook under `env -i PATH=/usr/bin:/bin` rather than trusting that linking it was enough. `link-worktree-session.py` additionally needs a **backfill** at install time: linking it only arms future sessions, while every transcript written before this run is still filed under its worktree's own project slug where the main checkout's window never looks. It makes each worktree's `~/.claude/projects/<slug>` a **directory symlink** to the main checkout's, never per-file links: Claude Code 2.1.296's panel lists only the main slug and opens transcripts with `O_NOFOLLOW`, so a symlinked transcript is dropped after every reload, while a symlinked directory turns Claude Code's own move-on-`EnterWorktree` into a no-op and leaves each transcript a real file

### Notifications are one-way, and that is a property of hooks, not a shortcut

`notify.py` pushes to Slack (work) or Telegram (home) on `Stop`, `StopFailure`, `Notification`, and `PreToolUse` for `AskUserQuestion|ExitPlanMode`. Replying from chat is impossible for the cases that matter — a permission prompt and an `AskUserQuestion` are blocking UI that only the session's terminal can clear. A `Stop` hook *can* return `{"decision":"block","reason":...}` to resume a finished turn with text from elsewhere, which is the one case chat could serve; it is deliberately not built, because it is the only design here that could hold a turn open, and a session that stalls waiting on a notification is strictly worse than one that merely did not tell you about itself. Everything therefore does one HTTP POST and exits. Keep it that way: the `thread` field in the envelope is the seam to add replies later without reshaping anything

### Telling the user and letting them answer are two channels, and a skill can arm only one of them

a ping says *come and look*; what lets the user act on it from a phone is Claude Code's **Remote Control**, which forwards the live session to claude.ai and the Claude app and can clear a blocking permission prompt or an `AskUserQuestion` from there. The obvious design — `/ping` sets the remote session up and `/ping off` tears it down — **cannot be built**: Remote Control is established by the `/remote-control` slash command, a slash command is typed by the user, and an agent has no way to run one in its own session. Writing `remoteControlAtStartup` reaches only sessions started afterwards, and the connection state cannot be read back from inside the session either, so a skill cannot even report honestly on whether it is up. It is therefore armed at **startup** — `remoteControlAtStartup` is `true` in every profile that ships a `settings.json`, and that file symlinking to `~/.claude/settings.json` is what makes it count: the key is honoured at user and managed level, while a `true` in a project or local `settings.json` is **ignored** and only a `false` there has any effect. The Pi ships no `settings.json` and needs none, since its sessions are spawned by a `claude remote-control` server. The alternative considered was a reminder line in the ping telling the user to run `/remote-control`, and it fails in precisely the case the feature exists for: the ping that matters most is the one an `autopilot` run sends hours after the user walked away, where nothing printed in the terminal will ever be read, and an instruction they cannot see reads in the run report as though it had been followed. Two corollaries. `/ping off` **disconnects nothing** — the connection was never the skill's to make, and dropping it would cut off a session the user may still be driving from the phone. And a ping must **never claim the session is answerable from the phone**: the startup setting is the reason it usually is, not evidence that it is this time, since a box with no claude.ai login, a gateway `ANTHROPIC_BASE_URL`, or an org policy toggle starts without it and says nothing

### A notification is only as good as its gate

with a dozen sessions live, an ungated `Stop` hook is indistinguishable from no notifications at all. The primary gate is now **opt-in arming** (below); `min_interval_seconds` per session and the suppression of anything carrying `agent_id` apply always, since subagents `Stop` constantly, and `min_turn_seconds` (a turn shorter than this was you at the keyboard, not you away from it) survives only as the fallback gate when `only_when_armed` is `false`. Turn length is measured from the **last handoff back to you**, which is *not* the last freely-typed prompt: answering an `AskUserQuestion` or rejecting a plan returns control just as much, and measuring only typed prompts reported a 20-minute turn as 24 hours. `handoff_epoch()` therefore correlates `tool_result` blocks against the ids of `AskUserQuestion`/`ExitPlanMode` `tool_use` blocks. It scans the transcript backwards in widening windows rather than a fixed tail, because a fixed tail misses the prompt on exactly the long turns worth reporting. `handoff_at()` exposes that same epoch absolutely rather than as a duration, because the opt-in gate needs to compare it against a timestamp. **The one kind of event no gate may swallow is one where the session is blocked on the user**, and `BLOCKING_KINDS` (`question`, `permission`) therefore clears the arming requirement — see the bullet after next, where the reasoning sits

### Notifications are opt-in per session, and `/ping` is the opt-in

the automatic hook is off in every session until the user asks for a ping, which writes `armed_at` into that session's state and switches it on. The reason is the gate bullet above taken to its conclusion — `min_turn_seconds` is a *proxy* for "you walked away", and a bad one: a 60-second floor fires on most substantial turns while the user is sitting right there watching, which is precisely how a notification channel becomes something they stop reading. Asking for a ping is not a proxy, it is the gesture itself, so it is what the hook triggers on. Three properties make it safe to leave armed. It is a **latch, not a timer**: only an explicit `/ping off` clears it, and the first version of this got that wrong by inferring the user had returned from their next prompt, from `back`, or from time passing. All three are wrong for the same reason — answering in chat and then walking away again is the normal way the feature is used, so a prompt is not evidence of presence, and a wrong inference here fails silently in the one direction that matters: the session goes quiet precisely when it was being relied on, and nothing reports that it did. The latch belongs to the user, never to the skill and never to the hook. It is **per-session, never global**, so a ping from one of a dozen sessions opts in only that one; `away` remains the global override that notifies for everything regardless. And the arming is written **only on the send's success path**, since a session silently opted in to notifications the user was just told did not go out is worse than either outcome alone. `armed_at` is written whether or not a thread id came back, which is why it sits outside the `if thread:` branch — a transport that cannot thread returns no id, and gating the arming on one would leave the session mute on exactly the machines where threading is unavailable

### The latch gates news, never stuck, and the gap was found by a plan gate that went unannounced

`only_when_armed` was applied to every event kind, so an unarmed session stayed silent through its own `ExitPlanMode` — observed here, `skip: session not armed` logged against the approval gate of this very change, on a `/fix-linear … --merge` run where the user had plainly said they were leaving. The near-miss fix is the instructive one: `autopilot` does arm the session, at its Step 0d, but a fix-skill hand-off reaches that at **Step 6, after implementation**, so every gate in Steps 1–5 sits ahead of the arming — and moving the arming earlier would have fixed autopilot runs while leaving a `/review-code`, a `/security-audit` remediation gate and every future skill just as mute. So the carve-out belongs in the hook, and it turns on a distinction the original gate missed: the latch is right for *this session has news*, since a finished turn keeps until the user is back, and wrong for *this session will do nothing at all until you act*, where silence costs an unbounded wait and a buzz the user is present for costs one ignored buzz. Four things keep it from undoing the opt-in. It **notifies without arming** — `armed_at` stays unwritten, because the latch belongs to the user and a hook that set it would be the silent wrong inference the bullet above forbids; the session's eventual `Stop` is still mute. **`idle` is excluded**, since `idle_prompt` is a timer that fires on any session left at a prompt rather than a gate the session ran into, and including it would buzz for every open window. **`events.question`/`events.permission` and quiet hours still outrank it**, so a real off switch stays real and a stated sleeping hour is still a preference rather than a gate on worth. And **the log names the path** — `sent question for X (…; unarmed: blocking gate)` — because a notification arriving in a session nobody armed is otherwise indistinguishable from a broken gate, which is the same reason every skip is logged. `notify_when_blocked` defaults `True` in `DEFAULTS` and merges under `~/.claude/notify.json`, so an existing config needs no re-seeding

### A published plan is a promise of a question, and the hook holds the skill to it

The carve-out above only fires on a gate the session actually ran into. It does nothing about the adjacent failure, which has also happened here: the plan was published, the link was posted to the chat, and the turn ended **without the `AskUserQuestion` ever being called**. Nothing was blocked, so nothing claimed the carve-out; the turn-end `Stop` hit `skip: session not armed`; and the run sat finished-looking with an approval nobody had been asked for. The user waited an hour on a plan that had been ready the whole time. Every rule in `fix-linear` Step 4 was already correct and already said to ask — which is the point: a step the model is told to reach is a step it can skip, and the gate that would have notified is the very thing that went missing.

So the promise is recorded where forgetting it cannot hide. `publish-artifact.sh --purpose plan` writes `gate_pending: {url, at}` into the session state on a successful publish, and a `Stop` arriving with that marker set is treated exactly like a blocking kind: it notifies **regardless of arming**, carries the plan URL in the body, and relabels the event `published a plan and is waiting on you` rather than `finished`. Marking is deliberately narrow and deliberately harmless — only `--purpose plan`, only after the publish succeeded, never for a diagram or an unpurposed page, and the call is `|| true` behind an `-f` check so a machine with no `notify.py` publishes exactly as before. `--purpose plan` is the signal because it already means "this page is going to a human to approve"; a diagram is published for the record and nobody is waiting on it.

Three properties make it survivable rather than noisy. **The marker is cleared only when a notification actually reaches the user** — a failed send, a rate-limited turn and quiet hours all leave it set, so the next turn retries instead of the one stranded plan being the one notification that got dropped. **Asking the gate question clears it**, since `question` notifies on its own, so the normal path never double-sends. And **an unrelated event does not consume it**: a permission prompt mid-plan notifies on its own merits and the marker survives to the turn end. `tests/check-plan-gate.py` holds all of that over every profile copy, and its `rules` subcommand prints the contract.

**Notifying was not enough, because it fires after the thing it is reporting.** It happened again: the plan published, the link posted to the chat, the turn ended, and the user came back to ask why nothing had been asked of them. A notification a turn late still spends a round trip they did not owe, and the rule it was backing up was already in bold in both fix skills. So the hook now **blocks** rather than only reporting. A `Stop` arriving with `gate_pending` set returns `{"decision": "block", "reason": …}` on stdout at exit 0, which Claude Code feeds back to the model as an instruction to send the link and call `AskUserQuestion` in the turn it was about to end. The turn cannot finish between a published plan and its question.

Four things keep that interlock from becoming the worse failure, and each one is a way a blocking hook turns into a hang. **It blocks at most once per plan**: `held` is stamped into `gate_pending` and checked on the way in, and `stop_hook_active` is honoured too, so the two guards are independent and a run that ignores the instruction falls through to the notification rather than into a loop — Claude Code's own eight-continuation cap is a third backstop nobody should reach. **It cannot block without persisting that fact**: when the `held` write fails the hook declines to block, because a block it will not remember making is exactly the loop. **A question clears the marker before any of the notification machinery is consulted**, which matters more than it looks. The existing clear sits at the end of `handle`, behind `load_config`, quiet hours and the rate limit, so a question asked during quiet hours left the marker set — and the interlock would then have blocked a turn that did everything right. So `plan_gate` clears it first and that one stays where it is, which is why the diff adds a clear rather than moving one. **And `--gate-clear` is the escape hatch**, named in the reason text itself, for the plan that genuinely needs no question.

None of those four bounds held until the writes stopped clobbering each other, and the review that caught it is worth recording because the bug is invisible in the diff. `handle` reads the session state once and writes it back whole at the end, with `summarize` (`claude -p`, 180s in the shipped config), `generate_title` and `send` in between — so a permission prompt raised mid-plan can be holding a snapshot for three minutes. The Stop hook stamps `held` inside that window, the run asks its question, the `PreToolUse` hook clears the marker, and then the slow process writes its snapshot verbatim and **puts `gate_pending` back with no `held` on it**. The next turn end sees a fresh `Stop`, an absent `held` and a false `stop_hook_active`, blocks a plan the user already approved, and fires a stranded-gate notification after the answer. So every writer now **merges**: `merge_state` re-reads the file immediately before writing and applies only the keys that process owns, `record_sent` names the three it carries plus the ones it sets, and a key to remove is passed as `drop` rather than popped from a stale dict. That is the same single-writer discipline this file already states for the title cache, generalised — the title cache got it by keeping one dict, which stops working the moment a second process writes the same file.

**The decision is asserted through `main()`, on real stdout.** The first version of the test suite checked `plan_gate`'s return string, which is not what Claude Code reads: renaming the printed key to `action`, or sending the same `print` to stderr, each ship a hook that blocks nothing and each left the suite reporting `passed (45 checks)`. A contract carried by a process's output has to be tested through that output, or the test passes for a hook that cannot work — which is this file's own "a hook that fails is invisible" rule applied to the thing testing the hook.

The notification stays as the layer behind the block, for the run that is told to ask and ends the turn anyway. It is still a smoke alarm rather than a safety net: the fix is asking in the same turn as the publish, and the interlock only guarantees that failing to is answered immediately instead of an hour later.

### A checklist nobody reads back is a report, and reports get ignored

the run checklist was built because `autopilot`'s arming instruction sat in its file **twice** and a real run skipped it anyway — prose is the wrong mechanism for an obligation. The checklist inherited the same weakness one layer up. A run on 2026-11-24 published its page correctly before its first step, then left **`arm: pending`** — the ping obligation, item #1 of every checklist — untouched for the entire run, and left `implement: in-flight` across a rewrite, a new test, a root-cause discovery, a browser verification and four documentation files. The user got nothing on their phone and had to ask twice. **The page was right the whole time.** It said `arm: pending`. `standing()` even classified the run as `stalled` — outstanding work, nothing in flight — which is exactly the alarm the renderer was given. Nothing read it.

So the fix is the interlock that already works, not a third sentence. `run-checklist.py` writes a `checklist_pending` marker into the session state on every `publish` and every `tick`, carrying the url, the open item ids, what is in flight, and `standing()`'s own verdict — **one definition of "outstanding", computed where it was already computed**. `checklist_gate()` in `notify.py` then refuses the first `Stop` that leaves it behind, and hands back the open ids and the command that fixes it. It is `plan_gate()`'s shape throughout, deliberately: subagents are skipped on `agent_id`/`agent_type`, `stop_hook_active` prevents a double hold, `held` marks the one offence that was spent, `GATE_TTL` ages the marker out, and `--checklist-clear` is the explicit escape hatch beside `--gate-clear` — though the next section is about how that hatch had no latch on it.

Four details are load-bearing. **The staleness clock counts turn ends, not minutes** — one long turn is legitimate work and a wall-clock timer would punish it, while three turn-ends with no write cannot be anything but a run that stopped looking at its own page. **`stops` is incremented by the gate and reset by the writer**, so a `tick` is what clears the debt rather than the passage of time. **A publish with no artifact store still marks the run**: `publish-artifact.sh` exits `3` on a work box, which is the ordinary answer there and not a failure, and gating the marker on a successful publish would switch the interlock off on exactly the machines that have no page to look at. And **the writer must leave `armed_at`, `thread` and `last_kind` alone** — it read-modify-writes the same file the hook owns, and a writer that replaced the document would silently disarm the session's notifications, which is the failure this whole change exists to prevent.

The companion is smaller and only removes latency: **a `/ping` token in a fix skill's invocation now means the user is away**, so the opening ping goes out at Step 0 with the checklist link rather than at the `autopilot` hand-off a dozen steps later. `/autopilot` already had that rule in both fix skills and `/ping` never did, so the token was dropped as prose. Fixing only that would have sent one ping and left the checklist write-only; the gate catches a missed ping on its own, because `arm` is item #1 and an open item with nothing in flight is precisely what it holds on.

### The only thing you could run against the gate was the thing that switched it off

minutes after the gate above merged, it failed to fire and the page went stale a third time in one session — `pipeline: in-flight` while the pipeline had been green for several minutes. The cause was the step that proved the gate was live. To show the merged hook was really running, the run executed `notify.py --checklist-clear`, which deleted `checklist_pending`, so `checklist_gate()` had nothing to hold on and every turn after that ended unguarded. **The command used to prove the gate works was the command that switched it off**, and nothing said so.

Three properties made that a hole in the design rather than one operator's mistake. Clearing was **silent and permanent** — only the next `publish` or `tick` re-armed the marker, which is precisely the action a stalled run is failing to take, so the gate was disabled exactly when it was needed. There was **no way to ask whether the gate was armed**: the only observable was the absence of a hold, which is indistinguishable from a healthy run, and checking meant reading `~/.claude/notify-state/sessions/<id>.json` by hand. And a clear **could not tell "this run is finished" from "I am testing you"**, because both produce the same state.

So the escape hatch is now bounded, and there is a read-only way to look. **`--checklist-clear` refuses while items are open**, exits non-zero, changes nothing, and names the page and the open ids it declined to drop; `--force` is the clear that works, and it prints what it dropped. **`--checklist-status` reports armed or not armed, the url, the verdict, the turn-end count and the open ids, and writes nothing** — it is what the verification step should have run, and it did not exist. **`run-checklist.py arm <items>.json` rewrites the marker from the items file alone**, with no render, no publish and no network, through the same `mark_outstanding()` every other write uses, so a forced clear is recoverable and there is one definition of the marker rather than two that can disagree.

Four details carry it. **A `--force`-less clear is refused rather than warned about**, because a warning on stdout is what the original failure already produced — the run read "cleared the run checklist marker", found nothing wrong with that, and carried on. **An expired marker clears without `--force`**: the gate would not have held on it either, so refusing there is a refusal with nothing behind it, and the clear says it had expired rather than pretending it dropped live work. **`--checklist-status` does not perform the TTL drop that `checklist_gate()` performs**, which is the one place read-only costs something — a status on an expired marker leaves it for the gate to reap, because a diagnostic that mutates is how the original defect happened in a smaller font. And **the hold text had to change with the behaviour**: it told a blocked run to use a bare `--checklist-clear`, which now refuses on every held run by definition, so an unchanged reason string would have been an instruction that fails.

What is deliberately **not** built is the ticket's fourth suggestion, making the hold un-clearable while a workflow or `Monitor` is in flight. Nothing reachable from here can observe a live swarm: the hook sees the `Stop` payload and the session state, neither of which carries the harness task list, and `run-checklist.py` has no access to it either. Any signal invented for it would be a guess that reads as a fact, which is the failure mode this directory's own "cannot observe is not success" rule exists against. The case is covered anyway — a run with a live swarm has outstanding items, so a bare clear refuses.

### One marker per session, so a run that forks to a second branch tracked nothing

a `/fix-freeform` run on `dylan/diagram-mobile-zoom-and-wrapping` published its checklist, then — mid-run, at the user's direction — cut a **second** worktree and branch and carried it all the way to a commit. That second branch had **no checklist at all**: no `arm`, no `plan`, no `commit`, no `review`, no `merge`. A whole change request's worth of obligations, invisible. Meanwhile the first page still named the first branch and described a run that no longer existed. The user noticed. Nothing else did.

Neither gate above could have caught it, and the reason is worth stating precisely: **they key on a marker that a second branch never writes.** `checklist_pending` is keyed by session, and `mark_outstanding()` is called only by a `publish`, a `tick` or an `arm`. A second branch that publishes nothing writes nothing, so `checklist_gate()` has no marker to hold on — and the marker it *does* have describes the first page, which is still internally consistent. The stale-page gate reports a healthy run while an entire second run goes untracked. Nothing is wrong with either page; what is missing is a page.

So the marker now carries the run's **branch**, and `checklist_fork()` compares it against `branch_label(cwd)` at every `Stop`. A difference holds the turn end once and names both branches, with the two cases spelled out: re-seed this page when the work moved, or publish a second one when the second branch is second work. Either write clears the hold on its own, because `mark_outstanding()` rebuilds the marker from scratch and the new branch goes in with it — there is no new escape hatch, and nothing to remember to switch off.

Five things are load-bearing, and four of them are about *not* holding.

**The comparison is on the branch, never the directory — and a session on the default branch is never a fork.** Comparing paths would hold every time a run entered or left a worktree, so `branch_label` resolving the branch is the first half. The second half was missed in a first draft and the review caught it: the marker records the branch the run *declares*, not where the session is standing, and those two legitimately disagree **twice in every normal run**. Both fix skills publish the checklist at Step 0 with the feature branch's name while the session is still in the main checkout on the default branch, and the branch is only cut at Step 2 — so every turn end in between was held, including `fix-linear` Step 1d's report-and-ask. Then `autopilot` Step 10d exits the worktree back to the main checkout while `verify` and `close` are still open, so the first turn end after the merge was held too. Reproduced both ways against the shipped hook, and the hold's own advice made it worse: it told the run to re-seed with `--branch main`, which inverts the mismatch the moment Step 2 enters the worktree *and* corrupts the `run.branch` that `observed_local` reads for the `commit` and `implement` signals. Both windows have the session on the default branch while the real defect was one feature branch to another, so declining there closes both and keeps the case this exists for. What is given up is a fork *onto* the default branch, which is `--branch default`-shaped work and was never the observed failure.

**An empty answer on either side is not evidence of a fork.** A marker written before the branch was recorded, a session outside a repository, a dotfiles repo rooted at `$HOME`, and a detached HEAD all resolve to nothing, and all of them mean *the question cannot be asked here* rather than *the run has forked*. This is the same rule the `reconcile` signals follow for the same reason: absence only ever declines to act.

**The fork's spend is a sibling of the marker, not a field inside it.** It records the branch it complained about rather than a flag, so a run that forks a *third* time earns its own hold — and it is deliberately not the `held` key the stale-page hold spends, since sharing them would let a run already held for staleness fork in silence. The part a first draft got wrong, and the review found by executing it: the spend was written *into* `checklist_pending`, which is the one dict `mark_outstanding()` rebuilds from scratch on every write. So every `publish`, `tick`, `reconcile` and `arm` wiped it — and `forge-watch/watch.sh --checklist` reconciles on every poll, so a genuinely forked run would have been re-held roughly every 60 seconds with no write able to clear it, which is worse than not detecting the fork at all. Measured: `FORK`, tick, `FORK`, tick, `FORK`. The test that was supposed to cover it passed only because it never wrote between its two Stops. `checklist_forked` now sits beside the marker, where `mark_outstanding()` does not reach it, and is dropped only when the marker itself is — on a complete checklist, a forced clear, or the TTL.

**The hold names `--update`, not a plain publish.** The re-seed it recommends is a fresh `template`, which carries no page identity — so a plain `publish` of it would mint a new link and freeze the one already sitting in the change request's description, which is the single thing the checklist contract forbids. A hold whose instructions break a different invariant is worse than no hold.

And **`--checklist-status` reports the branch**, saying whether the session is on it, so a fork is answerable read-only. That is the lesson of the section above, applied without being re-learned: the diagnostic exists before the first run needs it, and it still mutates nothing.

What is deliberately **not** built is option C — one page with a section per branch — which breaks URL stability. A marker per *page* was deferred here rather than rejected, on the grounds that two markers in one session would make "nothing in flight" ambiguous across two independent runs. The section below is what happened when a run had three pages that were not independent, and why that reasoning did not survive it. The gate's job here is to make the fork *visible to a human*, who then owns every page; it is not to own them itself.

### One marker slot, so three correct pages produced a false hold and two untracked ones

a run drove three change requests from one session — two repositories, three published pages, three watchers. Every page was correct and current, the session was on the branch it should have been on, and the `Stop` hook held the turn end anyway: the checklist *it could see* described a different branch. Following the hold's advice would have corrupted a second page's recorded branch; its other diagnosis, *this is second work and owes a checklist of its own*, was answered by a page that already existed. A third thing was true and the gate had no way to say it — three pages, three correct branches, one marker slot.

The mechanism is `mark_outstanding()` rebuilding `state["checklist_pending"]` wholesale on every `publish`, `tick`, `reconcile` and `arm`, writing *its own* page's identity into the one slot. With a watcher armed per change request, each poll's `reconcile --publish` rewrote it, so whichever page polled last decided what the session claimed to be on. `branches`, added for stacks, does not reach this: it lists the stages declared on **one** page.

**The marker now holds one record per page, keyed by the page's identity** — its hash, else its url, else its branch. The fork gate holds only when the session's branch is claimed by **none** of them, and the stale-page gate judges each record on its own.

Four things are load-bearing.

**Keying per page answers the ambiguity rather than inheriting it.** The deferral above was argued against two *independent* runs, where one merged `open`/`in_flight` list cannot say which run is idle. Each page keeps its own `verdict`, `open`, `in_flight`, `stops` and `held`, so every question the gate asks is asked of one page, and a hold names the page it is about.

**The smaller fix would have disabled the detection it was meant to quieten.** The alternative on the table was to union the branches into the single record and leave everything else alone. Measured against the shipped code: one page alone goes stale after three turn ends and holds on the fourth; with a second page's watcher writing between turn ends, `stops` stays pinned at `1` and the first page **never** holds — six turn ends, nothing. Every write resets the count, and a union of branches does not change which record the count lives in. So it buys silence on the false fork hold by keeping the stale-page gate permanently reset, which is the "gate people switch off" failure arriving from the other direction. Re-measured after the change: the unwritten page accrues its own debt and holds on its own, and the watcher's page is not named in the hold.

**A turn end counts against every page, even one that holds.** A first draft returned as soon as it had a hold to give, so a stalled page swallowed its siblings' turn-end count — found by running the new test rather than reading it. The increments and the `held` stamps are now one write, because `stops` is a count of turn ends and a page nobody wrote to did not stop being unwritten because another page was worse.

**The hook never changes the marker's shape; only the writer does.** A session upgraded mid-run still has the old flat marker on disk, so both sides normalize it into a single record, and the hook writes back whichever shape it found. The writer upgrades it on its next write, and replaces rather than duplicates a record that had no identity yet — a publish that found no artifact store still marks the run, keyed by branch, and the url it later earns must not strand that first record with an open list nobody can tick.

Four more things came out of reviewing the above, and three of them are defects the keying introduced rather than refinements of it.

**The fork set is every tracked record; only the staleness scan is restricted to the open ones.** A first draft filtered once, at the top, and handed the filtered list to both — so a page whose items were all done dropped out of the branch set and a session standing on *its* branch was held as a fork. That is the same false hold this whole section exists to remove, three lines from the fix. Reproduced against the shipped code. It is not reachable from the writer today, because `mark_outstanding()` pops a completed page's record, and it is fixed anyway: this is an interlock whose job is to be right about a marker it did not write, and the legacy-upgrade path preserves whatever shape it finds. **The test that was supposed to cover it is the sharper half of the lesson** — it was named *a finished page beside an open one never blocks on a fork* and pointed at the **open** page's branch, so it passed vacuously and the defect shipped under an assertion bearing its name.

**A publish records the url it reached before rewriting the page to carry that identity.** The rewrite is a second round trip and can fail on its own, and the old order returned on that failure with the url set in memory and never written to the items file. That costs twice over: the marker keys the page by a digest the items file does not have, so the next write adds a second record for the same page — and worse, the next publish has no hash to `--update`, so it mints a second page and freezes the link already sitting in the change request's description. The page is live by the time the rewrite is attempted, so persisting the url first is simply true.

**A tracked page can be cleared on its own.** `--checklist-clear --force` stayed session-wide while the gate became per-page, so clearing one abandoned page disarmed the gate for every other page the session was tracking, and the refusal unioned open ids across all of them so a bare clear was wedged by the abandoned one. `--page <url|branch>` drops one record and says what is still armed; the refusal lists which ids belong to which page and names the option. That is also what makes the one case the keying cannot separate tolerable: with no artifact store there is no identity, so the key degrades to the branch — correctly, since the branch is the only thing distinguishing two runs there — and a branch-mode re-seed therefore reads as a new page, leaving the old record behind. Widening the prune to drop any url-less record would collapse two genuinely independent runs on a work box into one, which is the exact case the gate is for, so the fix is to make the leftover clearable rather than to guess it away.

**A record with no url is named by its branch.** Two of them used to render as the same literal string in a hold that then told the run to tick each page named above, and the hold and the escape hatch disagreed about what to call an identity-less page because one bypassed the shared helper.

### A page the run has to remember to update is a page that goes stale

the gate above catches a checklist nobody wrote to. It cannot catch one that was written to and is wrong, because `standing()` reports `armed` for an item claiming to be in flight whenever nothing behind that claim can be checked. That is the hole the gate shipped with, and it was demonstrated twice within an hour of shipping: a page read `pipeline: in-flight` while all three checks had been green for minutes, and later `implement: in-flight` while the implementation was finished and the run had stopped. Both passed the gate.

**One kind of claim can now be checked, and it is checked at both ends.** A `waiting_on` naming a workflow carries a `wf_…` handle, and a workflow's state file under `~/.claude/projects/*/*/workflows/` is written **once, when the run ends** — so the file existing is a death certificate and its absence says nothing at all. `standing()` stops counting an item whose handle has finished, and `checklist_reason()` re-checks the handles the writer recorded in `in_flight_on` at every `Stop`, because the run that produced this wrote nothing between the swarm finishing and the turn ending: the swarm reported, six findings were posted, fixed and resolved, two commits were pushed, and the turn ended with the page still reading `review: in-flight`. **The two questions it answers are separate, and conflating them is the mistake the first draft made.** *Will anything wake this run* is the verdict's question, and a live sibling genuinely answers it — so a dead item beside a live one leaves the verdict `armed`. *Was an obligation dropped* is a different question, and a live sibling says nothing about it. The first draft held only when **every** in-flight item was dead, which sounded conservative and was nearly unreachable: `autopilot` Step 5 ticks `pipeline=in-flight:a Monitor on the pipeline` beside `review=in-flight:workflow <id>` in one command, and `observed()` rewrites `pipeline`/`merge` in-flight with non-workflow blockers on every poll — so a sibling without a handle is the steady state and the dead swarm was masked in exactly the window the ticket observed. The rationale given for it was that a live sibling means a healthy run, and that premise is unfounded: `waiting_on` is a state description, not evidence the `Monitor` lives, which is the same unvalidated string the whole gate exists to distrust. So `in_flight_on` carries **every** in-flight item's `waiting_on`, dead ones included, and the hook holds on **any** handle it can prove has finished.

Four things keep it from becoming a gate people switch off. **Only `workflow <id>` counts, and every handle in that string must be finished** — `waiting_on` is prose, so a line mentioning a finished run while awaiting something live is not an item waiting on it, and an item still waiting on one live workflow is not dead because a sibling ended; both were false holds. **The item is never promoted**, because a finished workflow does not mean its findings were worked; the obligation stays open and merely stops counting as armed. **An absent file, a `waiting_on` naming a `Monitor`, a marker predating the field and a malformed one all change nothing** — there is no generic signal for a live `Monitor`, and inventing one is what *cannot observe is not success* exists to prevent. And **the hook reads the marker defensively and never reshapes it**, so a session upgraded mid-run degrades to the old behaviour rather than breaking.

**A run working the findings re-ticks the item off the handle**, which is what stops this firing on a correct run: `autopilot` Step 6 branch 1 sets `review=in-flight:working N confirmed findings` in the same batch as the `fix-feedback` call. The handle was true while the swarm ran and stops being true the moment it reports.

**A write that changes nothing keeps the stop count and the spent hold.** The watcher reconciles every 60 seconds, so counting a no-op poll as a write left the three-turn-end staleness path unreachable for the rest of a run — and the two have to move together, because preserving the count while clearing the hold would re-arm it every poll instead, which is the failure already recorded above for `checklist_forked`.

**So the items whose truth is observable are no longer written from memory.** `run-checklist.py reconcile` derives them, and `forge-watch/watch.sh --checklist <items>.json` calls it on every poll using the state that poll already parsed — no extra API call, because the watcher was already fetching the pull request's state, merge flag, review decision, unresolved-thread count and per-check conclusions and throwing all but the notification lines away. Four sources, and the split between them is the whole design:

| source | items | why it is trustworthy |
|---|---|---|
| the forge | `open`, `pipeline`, `threads`, `merge` | the watcher already holds them |
| local git | `commit`, `implement` | a commit on the branch that is not on the default branch |
| the body | `describe`, `ledger` | prose beyond the checklist link; the decision fold |
| session state | `arm` | `armed_at` is present |

**`plan`, `review`, `verify` and `close` are deliberately left manual**, and that is a result rather than an omission. There is no generic signal for *the change reached production* — Step 0b derives the deploy path per repository and it is routinely unreadable — so inventing one would manufacture exactly the false confidence Step 10b's "cannot observe is not success" rule exists to prevent. The swarm item has no forge trace either, and a plan's url is cleared from the session state the moment the gate is satisfied. Deriving badly is worse than not deriving.

Four properties carry the rest, and three were found by running the thing rather than by reading it.

**Every local signal only ever promotes.** It ticks an item `done` when it can see the obligation discharged, and says nothing when it cannot. Two findings from the review swarm forced that, and both are the same mistake: **absence is not evidence.** A merged branch has no commits ahead of its base, so `rev-list origin/main..feature` reads `0` the moment a merge commit lands and the repo fetches — a two-way signal then rewrote `commit` and `implement` to `pending` on a *merged* run, and the gate blocked the next turn end on two obligations nobody could re-do. And `armed_at` is a latch the user clears with `/ping off`, long after the ping was sent, so deriving `arm` from it un-ticked a discharged obligation and left the checklist permanently unable to reach `complete`. A first version shipped both; neither survived review. What is given up is detecting a page that claims `done` when nothing happened — which never actually occurred, where forgetting to tick occurred constantly.

**An owned item's blocker is refreshed on every pass, not only at its terminal state.** `merge` was touched only once the request merged or closed, so a page carried `merge: in-flight — PAUSED; blocked on the threads item` long after the pause had ended. An item nobody is updating is the same defect whether its *state* or its *reason* is the stale half.

**The facts must belong to this checklist.** `reconcile` refuses a url that disagrees with the recorded `change_request`, and derives nothing from the forge when none is recorded. Found by the user, on the page: a smoke test pointed one run's checklist at a different, already-merged pull request, and the page cheerfully reported `pipeline: done`, `merge: done` and `describe: done` for a change request that did not exist. Before the guard, an empty `change_request` still produced `pipeline: in-flight — the forge has reported no checks yet`, which is a claim about a pull request nobody has opened.

**A `skipped` item is never revived**, so a deliberate "no pipeline in this repo" survives every pass — the same reasoning that makes a skip carry a reason in the first place.

One consequence worth stating plainly: the page is now *more* trustworthy than the run's own account of itself, which inverts the old relationship. When a derived signal contradicts a manual tick, the signal wins and the change is named in the command's output, because that disagreement is the defect being hunted rather than noise to smooth over.

### Reachability changes what an unattended run may do about an ambiguity, and the premise it overturned was load-bearing

`autopilot` was written on the line *from the commit onwards there is nobody to ask*, and that single sentence is what forced every mid-run judgment call down the decide-alone-and-ledger path. With the session reachable from a phone and `notify.py` registered on `PreToolUse` for `AskUserQuestion`, raising a question both notifies and can be answered — so asking is now right for the calls that are expensive to get wrong: anything irreversible or chargeable, a fork where one branch is hard to undo, and the Step 11 escalations the run could act on immediately (a product or policy call, a merge conflict's intent), which previously **ended** a run that could have carried on. It stays the exception rather than the default for one reason: **a question stalls the run until somebody answers it**, and a user asleep or at dinner turns an unattended run into a parked one — so most calls still take the most defensible option plus a ledger line, and a question that *was* answered earns no ledger entry, because that decision was the user's and is already on the record. Three things make the ask real rather than theatrical. **It must stand alone**: it is read on a lock screen and answered in an app, so an option saying *as discussed above*, naming a file to open, or needing two paragraphs weighed against each other is unanswerable. **It comes before the irreversible step, never halfway through**, where neither answer is any use. And **it is never accompanied by a ping**, since the hook already fires on the question and the second copy is what teaches the user to ignore both. Step 10c's old wording is the incoherence this fixes — *ask by pinging rather than parking silently… ask for a yes*, over a channel that cannot carry one. The counterpart hazard is unchanged and now more likely to come up: `pause` still refuses to park with a question dangling, because a paused session swallows an answer that may be in flight from the phone

### The notification body is summarized by a model, and the hook shells out to do it

`last_assistant_message` is a turn's closing chat message — written for a terminal with the diff open, routinely 500 words of headings, tables and file links, against a lock screen that shows about 140 characters. Clipping it, which is what it did, produces a wall of markdown whose first line is often a sentence ending in a colon pointing at a table nobody can see. `notify.py` therefore passes the body through `claude -p` before sending. **Use the subscription, not the API**: an `x-api-key` call is faster and was the first implementation, and it was wrong here because the API account carries no credit while the Claude Code subscription is already paid for — the symptom was an `HTTP 400 credit balance` that no amount of correct code fixes. Five things are load-bearing. **The budgets are deliberately loose** — 180s for the summarizer inside a 240s hook, against an observed 9–29s spread — because the alternative to waiting is the truncated dump the feature exists to prevent, and the only state in which any of this fires is one where the user is away and waiting is free; every tight budget tried here (6s, 25s, 35s, 45s) was tuned to a sample and then blown by an outlier. **Every failure degrades to a mechanical condense** and still sends, since a missing CLI, a logged-out machine or a slow model must never cost a notification, and the log records which path ran so a degraded machine is visible rather than inferred. **The child gets a neutral `cwd` and no MCP, hooks or plugins**, or it loads this repo's `CLAUDE.md` and every skill before answering; `NOTIFY_SUMMARIZING=1` in its environment is the backstop that stops a hook spawning a session that fires hooks. **Long input is windowed head-and-tail rather than truncated**, because the outcome sits at the top of a message and the ask at the bottom, so cutting the tail discards precisely what the user needs. **Questions are summarized like everything else** — an `AskUserQuestion` body is the literal questions, written for a terminal, and the user cannot answer from the notification anyway: all it has to convey is that the session is waiting on them and what about. The CLI is resolved by probing install locations and then `shutil.which` over an augmented `PATH`, never by name, because hooks run with a bare `PATH` where `claude` does not exist; `summarize.command` is the per-machine escape hatch and `notify.py --test` prints what it resolved, with a timed live sample

### The thread is the context, so only its first message repeats it

a session's notifications are one thread — Telegram replies with `reply_to_message_id`, Slack with `thread_ts` — and every reply renders the first message quoted above it. So the repo and the session title are already on screen in every reply, and printing them again spent roughly a third of a 140-character lock screen restating the line directly above. The shape is therefore split by position, not by transport: the **first message** is `<repo> · <session chat title>` then its body, with **no glyph**, because a thread root is an anchor and its class is the least interesting thing about it; every **reply** is `<glyph> <body>` and nothing else. `envelope["thread"]` is the discriminator and it is reliable in both producers — `notify.py` sets it from `state.get("thread")` and the `ping` skill from the same session state, so it is absent exactly once per session. The six glyphs (`✅❓🔐🔄💤🔥`) still carry the kind one-to-one, which is what makes dropping the words safe. **The thread is anchored before the first event rather than by it**: the root is the only message carrying the repo and the title, so a session whose first notification is a permission prompt opened its thread on a bare demand — observed as a root reading only `Claude needs your permission to use Bash`. `notify.py` now sends an empty-bodied envelope first, which `compose` renders as the header alone, and threads the real event under it; the `notify_when_blocked` carve-out means that first event is often a gate in a session nobody armed, so hanging the anchor on arming would have missed exactly the case that showed the bug. It costs one extra message per session, degrades to the old behaviour when the anchor send fails, and lives in the producer rather than in the two transports, since "this session has no thread yet" needs no transport knowledge. The second field is the **session's chat title**, read from the transcript where Claude Code writes `ai-title` and `custom-title` records, so it needs no editor API — `worktree-sync`'s `resolve.ts` had worked this out and its precedence is reused verbatim, a `custom-title` the user typed beating the generated `ai-title`. Two traps come with it: the record is written early and **scrolls out of a fixed tail** (only 38 of 139 local transcripts carried one in their last 256KB), so the lookup uses the widening-window `scan_tail()` shared with `handoff_at()`; and the records appear both compact and spaced, so each candidate line is `json.loads`-ed rather than regex-matched. The branch survives **only as a fallback** for a session too new to have a title, and the 8-character session id was dropped outright — it reads as a commit hash and identifies nothing a human recognises. `notify.py --label <session-id>` prints the resolved title so the `ping` skill shares the one parser, globbing `~/.claude/projects/*/<id>.jsonl` since only the hook is handed a transcript path. **A Remote Control session writes no title record at all**, which is how `remoteControlAtStartup` turned every thread root into `<repo> · <branch>`: a bridge session's transcript carries `bridge-session`, `last-prompt` and `worktree-state` records and never an `ai-title`, so the resolver found nothing and the branch fallback — the least informative field available, identical across every worktree of a repo — won by default. The fallback is now a condensed form of the session's **opening prompt**, taken from the first `last-prompt` record or the first non-`isMeta` user message, which is the one source present in both session kinds and stable for the life of the session: `lastPrompt` tracks the *latest* prompt, so reading any record but the first would label the thread with whatever turn the first notification happened to fire on. It is a **head** scan rather than the widening tail scan the title lookup uses, because a prompt is at the start of a file and a 17 MB bridge transcript is past `TAIL_LIMIT` anyway — but it still has to widen, since injected skill text pushes the first prompt to ~340 KB in. The fallback is in two tiers, because the opening prompt alone is a weak title — it is whatever the user happened to type, often a slash command plus a paragraph. So the hook **generates** one with the same `claude -p` plumbing the body summarizer already uses, from the opening prompt *plus the assistant's first reply*, which is what turns `/review-kludge on the whole of Demeter as it…` into `Demeter token consumption optimization`. Three properties make that affordable. It is **cached in the session state file** and the generator mutates the `state` dict `handle()` already persists, so there is no second write and no race with the `last_sent`/`thread` keys that write would clobber — measured at 6.6s on the first call and 0.09s on every one after. It is **skipped entirely when a real title exists**, so a titled session still resolves in 0.04s and spends nothing. And it **degrades through every tier**: a missing CLI, a disabled summarizer, a timeout or a reply the model rambles over all fall through to the prompt condense and then to the branch, each logged, because a hook that fails is invisible. `title_timeout` in `notify.json` is the knob, 25s by default against an observed 5-8s. **A markdown link had its URL thrown away on the way out**, which made every notification naming a change request unactionable: `strip_markdown` rewrote `[PR #10](https://…/pull/10)` to `PR #10` and dropped the target, and it runs on both the summariser's input and the mechanical condense, so no path survived it. It now keeps the URL for an **absolute http(s)** target and still drops it for a relative one — a file path opens nothing on a phone, while the change request is the only thing on that screen worth tapping — and the summariser is told to reproduce a URL verbatim, since a model rewriting to 75 words will otherwise spend none of them on it. The `ping` skill carries the same rule for the bodies it writes by hand. Measured honestly, the gap this closes is narrow: 17 of the 18 most recent real sessions already had a title, and the one that did not was the bridge session

### Composition is shared across transports; only delivery is not

the root/reply split above is identical in the Telegram and Slack senders, because a per-client layout is two things to keep in step for no gain. What stays transport-specific is strictly about *delivery*: Slack still needs the `<@U…>` mention prefixed into **both** `text` and the rendered block, since a threaded reply otherwise never notifies and `chat.postMessage` answers `ok` regardless; Telegram needs none of that because `reply_to_message_id` renders inline and notifies by itself. Dropping the header freed real room, so the summariser's budget went up by two thirds — `SUMMARY_MAX_WORDS` 45→75 and the mechanical fallback `CONDENSE_LIMIT` 240→400 — and the `ping` skill's prose budget moves with it, or the skill and the hook disagree about the same message

**One sender speaks both, because one of the three `scripts/` directories is a symlink.** `home_darwin` moved to Slack for the same reason the work profiles are on it — a dozen concurrent sessions interleave unreadably in a flat Telegram chat, and a thread per session is the only thing that separates them. The home copy of `notify-send.sh` therefore dispatches on `transport` rather than being replaced, and the Slack half is the work copy's behaviour unchanged, verified by composing both senders over the same envelopes. What forces the dispatch is the Pi: `larrabeedylan_home_pi/.claude/scripts` is a symlink into `home_darwin`, so a Slack-only sender runs there too, against a config that is deliberately Telegram with `bot_token_file`/`chat_id_file` pointing at credentials the box already holds. It would `fail("has no slack section")` on every send, which `notify.py` logs and exits 0 on — so the Pi would go silently mute, and it is the box whose sessions nobody is watching. The `_file` indirection now covers the Slack keys too, so putting that box on Slack later is a credential file and one word in its config rather than another sender

### A thread id belongs to the transport that issued it

switching `transport` from Telegram to Slack left **41 armed sessions silently mute**, and not one of them reported it. `~/.claude/notify-state/sessions/<id>.json` carries `thread` so every notification from a session lands under the first one, and the id is whatever the transport handed back — a Telegram `message_id` is an integer, a Slack `thread_ts` is a `1795673991.631919` string. The sender passes the stored value straight into `thread_ts`, Slack answers `invalid_thread_ts`, `notify.py` logs it and exits 0, and the session goes quiet for the rest of its life. The config switch is the trigger, but the defect is in the state file: it recorded the id and never which transport minted it, so nothing downstream could tell a live thread from a foreign one. Three things carry the fix. The state records **`thread_transport` beside `thread`**, written only when a thread is written, and `carried_thread()` hands the id back **only when it matches the configured transport** — so a mismatch drops to `None`, the anchor block opens a fresh root in the new transport, and the session self-heals on its next event rather than needing its state file deleted. **An absent `thread_transport` is unknown, never a match**: a state file written before the field existed could have come from either transport, and guessing costs the exact silent mute this exists to prevent, so the one-off price is a single extra thread root per pre-existing session. And the check lives in **`notify.py`, not in either sender** — the producer already owns the thread, which is why the anchor logic sits there, and a per-transport `thread_ts` validator would be the same rule written twice with no shared definition of *stale*. Deliberately **not** done: no retry-without-the-thread on an `invalid_thread_ts` reply. It would have delivered these 41 notifications, and it would also have hidden the provenance bug behind an un-threaded message that still arrived, which is how a feature whose whole purpose is per-session grouping degrades to a flat chat with nobody noticing

### `--show-toplevel` answers the worktree, not the repository

every ping from a `fix-*` run labelled itself with the **branch** — a thread root reading `OLY-17 · Ticket fix` — because the session's cwd is `.claude/worktrees/dylan/OLY-17` and `rev-parse --show-toplevel` returns that worktree's own root, whose basename is the branch. Every worktree of one repo therefore looked like a different project, and the field that exists to say *which repo* said nothing about it. `--git-common-dir` is the one that survives a linked worktree: it points at the main checkout's `.git` from anywhere, so its parent is the repository, with `--show-toplevel` kept as the fallback. The trap for anyone checking this is that the bug is invisible from the main checkout — `notify.py --repo <main>` returns the right answer, which is exactly how it was declared not-reproduced once; reproduce it from **inside** a worktree or not at all.

### Outside a repository the directory names the session, not the machine

`repo_label` falls back to `host_label` when `rev-parse` finds no project, which was right for the case it was added for — a `$HOME`-rooted dotfiles repo answers `rev-parse` for every path beneath it, so the label became the home directory's name. Applied to *every* non-repo cwd it overreached: a phone session spawned in `remote-root` on the Pi read `pi`, which says where every session on that box runs and nothing about this one, where `remote-root` says what kind of session it is. So a named directory now wins and `host_label` answers only the case the directory cannot — `$HOME` itself, or no directory at all. Both halves are tested: `~/remote-root` reads `remote-root` even with `host_label` set, and `$HOME` still reads `host_label`.

### Away mode is a file, not an environment variable

`~/.claude/notify-state/away.json`, because hooks do not inherit your shell's environment — the same reason `github-api.sh` reads its token from `.mcp.json` rather than `~/.secrets`. It drops the `min_turn_seconds` gate and nothing else. `away`/`back` in `shell/terminal.zsh` are thin wrappers over `notify.py --away`, guarded on the hook existing

### A `U…` id is not a DM channel

`chat.postMessage` accepts a user id in `channel` and posts to that user's DM with **Slackbot**, not with your app — it returns `ok`, so the only symptom is that the messages are somewhere nobody looks. A DM from the app needs the `D…` id that `conversations.open` returns for that user, which is why `notify-send.sh` resolves any `U…`/`W…` channel through it and caches the answer in `~/.claude/notify-state/slack-dm.json`; `im:write` is the scope that call needs, on top of `chat:write`. A `D…` or `C…` channel is passed through untouched.

### Threading a Slack DM silences everything after the first message

`chat.postMessage` with a `thread_ts` makes every notification after a session's first one a **threaded reply**, and Slack treats those as second-class — no new top-level message, no reliable push, and Slack only auto-follows threads *you* started or replied in, never a bot's. The failure is exactly the one the feature exists to prevent: a session says it has a question, then finishes forty minutes later into a thread nobody is watching. Observed here — five sends, one visible. `slack.mention` fixes it by prefixing `<@U…>` to the message, since a mention notifies regardless of subscription; it defaults to `slack.channel` when that is already a `U…` id, and `slack.mention_levels` keeps it to `stop`/`question`/`permission`/`failure` so a mention never degrades into noise. **The mention must sit in the `blocks`, not in `text`** — given both, Slack renders the blocks and keeps `text` only as notification fallback, so a mention living solely in `text` is never rendered, never registers as a mention, and never notifies, while `chat.postMessage` still answers `ok: true`. That was gotten wrong here on the first attempt and the symptom is indistinguishable from the bug it was meant to fix: a message that lands in the thread looking entirely normal. Verified end to end — the mention goes at the head of the rendered section block *and* in `text`, which is what the lock screen previews. `reply_broadcast: true` is the other option and is worse here — it copies the reply to the top level, undoing the per-session grouping the thread was for. **None of this applies to Telegram**: `reply_to_message_id` renders inline rather than collapsing, so every message stays top-level and notifies by itself, and an @-mention is meaningless in a 1:1 bot chat. Telegram's real threads (forum topics, `message_thread_id`) exist only in supergroups

### A Slack incoming webhook cannot thread

it ignores `thread_ts`, so per-session threading needs a bot token with `chat:write` plus a channel. Both are supported and the webhook is the documented default, since it needs no app scopes — but with many concurrent sessions the channel interleaves badly without threads, so the bot token is the better end state. The phone's push preview shows only Slack's `text` field, never `blocks`, so the one-line summary has to live in `text` or the notification is useless on a lock screen

### `/ping` is the deliberate counterpart to the hook, and shares its state

`notify.py` fires automatically and is therefore gated hard; the `ping` skill is invoked on purpose — by the user, or by a skill handing over a question, a blocker or a finished run — so it **bypasses every gate** (`min_turn_seconds`, `min_interval_seconds`, quiet hours, subagent suppression). An explicit ping is never noise. It sends through `notify.py --ping`, which builds the same envelope the hook builds and hands it to `notify-send.sh send` — which is why the skill is byte-identical across all three profiles: the Slack/Telegram split already lives in the sender, so nothing in the skill may name a transport. **The skill used to rebuild the hook's own state keying in two inline Python heredocs** — `session_path`'s regex pasted verbatim twice, `read_json`/`write_json` as bare `try/except` blocks, the envelope field by field, the state write — about 62 lines an agent had to read and re-emit character-perfect on a path where a mis-transcribed regex is a *silent* no-op: it writes a state file nothing reads, and the session then goes mute precisely when it was being relied on. `build_envelope()` and `record_sent()` are therefore shared, and the skill passes a level, a title and a body on stdin. `--ping` reads and writes `~/.claude/notify-state/sessions/<id>.json` so a ping lands in the session's existing thread rather than floating free — read-modify-write, never clobbering the `last_sent`/`last_kind` keys the hook owns, and tolerating a state directory that does not exist yet on a machine where no notification has fired. **Resolution and assembly are shared; the gates are not.** Every gate lives in `handle()`, which `--ping` never enters, so the split needs no flag to express it — and `record_sent()` takes `arm` off by default, which keeps the latch the hook's to leave alone and the ping's to set, on the success path only and outside the `if thread:` branch, since a transport that cannot thread returns no id and would otherwise leave the session mute. The ping deliberately does **not** write `last_sent`: that key feeds the automatic path's rate limit, and a deliberate message is not a reason to suppress the next real one. The message must carry what the session is doing *and* whether it needs anything: the lock screen shows one line, so a ping that says "done" has wasted it

### A hook that fails is invisible

`notify.py` appends a line for every invocation including the silent ones (`skip: turn 11s < 60s`), to `~/.claude/notify-state/notify.log`, capped at 1 MB. Without it, a wrong gate and a broken token look identical from the outside. Every error path logs and exits 0, and the POST timeout (5s) sits well under the hook timeout (15s) so a dead transport costs a turn seconds rather than the full budget. A missing or `REPLACE_ME`-filled `~/.claude/notify.json` is a dormant no-op, never an error — the feature ships switched off and comes alive when a token lands
