## Slack Context & Collaboration

### 1. Cloud Trace → BigQuery Sink Debugging (platform-infra-team)
- Dylan spent significant time debugging why the Cloud Trace → BigQuery sink was silently dropping all traces. Zero errors, zero metrics.
- Opened a GCP support ticket (first time doing so; needed Mark's help with permissions).
- Google support confirmed: the sink only works with the legacy `cloudtrace.googleapis.com` API, not the OTLP/telemetry endpoint used by GKE's managed OTEL collector.
- Dylan deployed a custom OTEL collector using the `googlecloud` exporter as a workaround (MR !1975).
- Got Buildkite trace data flowing into BigQuery and began standing up Grafana dashboards.
- People involved: Dylan (lead debugger), Mark (support ticket access, discussion), Travis Thompson (context)
- Outcome: Buildkite traces now flow into `gridmatic-build.buildkite_traces.cloud_trace`

### 3. CronJob Failure Alert Investigation (prod, platform-infra)
- Marshall flagged noisy CronJob failure alerts in #k8s-pods-alerts-all.
- Dylan quickly identified that his MR !1987 (adding `--metric-labels-allowlist=pods=[*]` to kube-state-metrics) was the root cause — the wildcard was causing scrape timeouts on the build cluster.
- Dylan fixed it by narrowing the allowlist to just `buildkite-step` and `buildkite-pipeline` labels.
- Also provided detailed root cause analysis: the alerts were false positives because kube-state-metrics manifests hardcode `namespace: production`, so Buildkite job failures appeared as production CronJob failures.
- Proposed both quick fix (exclude build cluster from alert query) and proper fix (reconfigure build cluster monitoring).
- People involved: Dylan (root cause analysis + fix), Marshall (alert detection + tuning), Mark (triage)
- Outcome: Alert noise resolved; proper fix in progress as Draft MR !1988
