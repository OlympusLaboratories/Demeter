# Demeter — Shared Dotfiles

## Project Overview

Demeter is a shared dotfile repo. Each machine setup lives in its own profile directory under `profiles/`. An interactive install script symlinks everything to the right places on any machine (macOS or Linux).

## Repo Structure

```
Demeter/
  install.sh              # Interactive symlink installer (idempotent)
  .github/
    workflows/
      ai-review.yml       # Hephaestus AI review on every PR; the repo's only CI
  _starter/               # Template for new contributors — copy to get started
    .bash_profile
  _vendor/                # Vendor packages (skills + tools) — linked/installed by installer
  tools/                  # First-party projects shared by every profile
    claude-usage/         # VS Code extension, linked into ~/.claude/tools/
    worktree-sync/        # VS Code extension, linked into ~/.claude/tools/
  git/                    # Git config shared by every profile
    ignore                # machine-wide gitignore, linked to core.excludesFile
  shell/                  # Terminal experience shared by every profile
    terminal.zsh          # gap-filling zsh fragment, sourced last from each rc
    starship.toml         # prompt config (copy of rdev's)
    tmux.conf             # ~/.tmux.conf, or ~/.tmux.conf.local on rdev
    install-tools.sh      # installs the tools + zsh plugins terminal.zsh uses
  vscode/                 # Editor settings shared by every profile
    settings.json         # symlinked over VS Code's user settings.json
    extensions.txt        # extension ids the installer keeps present
    sync-extensions.sh    # rewrites extensions.txt from the current machine
  profiles/               # One directory per machine profile
    larrabeedylan_home_pi/  # Raspberry Pi app host; skills/hooks/scripts are
                            # symlinks to the home_darwin profile's — see its AGENTS.md
    <profile>/            # e.g. larrabeedylan_work_linux
      .zshrc
      .bash_profile
      .claude/
        CLAUDE.md         # global agent instructions, synced to ~/.claude/CLAUDE.md

```

## Context Discovery

Before planning or making changes in a directory, **read the `README.md` and `AGENTS.md`** at the root of that directory (and any parent directories up to the repo root) if they exist. These files contain important context about the directory's purpose, conventions, constraints, and how components interact. This applies to research, planning, and implementation — not just code changes.

## Install Script (`install.sh`)

The installer does the following in order:

1. Selects the profile to install — from the first CLI argument (a `profiles/` subdirectory name or a path), else auto if only one profile exists, else prompts. `install.sh --help` lists available profiles, and `-y`/`--yes` answers every prompt.
2. Detects machine type — macOS = `mac`, a Raspberry Pi (`/etc/rpi-issue` present) = `pi`, any other Linux = `linux`. The Pi needs a type of its own rather than sharing `linux` with the rdev box: `SKIP_LIST` is keyed by machine, and the two need opposite treatment
3. Initializes git submodules if `.gitmodules` exists
4. Symlinks dotfiles from `profiles/<profile>/` to `~/` (skipping `.claude/`, and any path listed in `~/.rdev-managed.json` on an rdev box)
5. Symlinks `shell/` config (`terminal.zsh` to `~/.config/zsh/`, `starship.toml`, `tmux.conf`) and offers to install any missing terminal tool or zsh plugin
6. Symlinks `.claude/` contents individually (skills linked per-directory into `~/.claude/skills/`)
7. Unifies worktree project dirs into their main checkout's by running `.claude/hooks/link-worktree-session.py --backfill`, first probing it under a bare `PATH` (`/usr/bin:/bin`) — the environment Claude Code actually spawns hooks in
8. Seeds `~/.claude/notify.json` (mode 600) from the profile's `notify.json.example` when absent, probes `notify.py` under the same bare `PATH`, and names the fields still set to `REPLACE_ME`. Never overwrites a filled-in config
9. Seeds `~/.claude/environment.json` from the profile's `environment.json.example` when absent, then runs `skill-env.sh check` and reports whether the forge API helper it resolves to is actually installed. Never overwrites an existing config, and a malformed one is a warning rather than a failure — the skills fall back to the defaults compiled into `skill-env.sh`
10. Symlinks vendor skills from `_vendor/*/` into `~/.claude/skills/`
11. Symlinks shared tools from `tools/*` into `~/.claude/tools/`
12. Prompts to build and install shared tools exposing an `install` target in their Makefile. Runs through `mise exec` when the tool has a `.mise.toml`, so a pinned toolchain resolves in a non-interactive shell. Skipped without prompting when no editor CLI answers `--list-extensions`; otherwise the CLI it resolved is passed to `make install` as `CODE=`, since the Makefile's own `code` lookup fails outside the integrated terminal. Verifies afterwards that the tool's extension id is registered, since a build can succeed without the editor picking it up. Honours `SKIP_LIST` by tool directory name.
13. Symlinks `vscode/settings.json` over VS Code's user settings, on every editor user directory that already exists
14. Sweeps repo workspace `.vscode/settings.json` files for color keys the shared settings own, via `vscode/strip-stale-peacock-keys.sh`
15. Symlinks `git/ignore` to the machine-wide gitignore git actually reads, and verifies it took
16. Prompts to install any extension in `vscode/extensions.txt` missing from the editor. Each `--install-extension` runs under a timeout (`EXTENSION_INSTALL_TIMEOUT`, default 180s) and is then judged by `--list-extensions`, because the server CLI can finish installing and never exit
17. Cleans stale skill symlinks (removes symlinks pointing to deleted repo paths)
18. Creates data directories for skills that accumulate context

Key behaviors:
- `-y`/`--yes` answers every prompt instead of reading stdin, and is propagated to `vscode/strip-stale-peacock-keys.sh`, the only sub-script that prompts. It **refuses to run without an explicit profile** when more than one exists: profile selection is the one prompt with no safe default, and defaulting it links another machine's dotfiles over yours. It deliberately consumes no stdin, so `yes | ./install.sh <profile>` keeps working for anything already written against it — the flag's advantage is an exit status that is the installer's own rather than `141` from `yes` catching a `SIGPIPE` under `pipefail`
- Never copies `~/.claude` aside; it only replaces symlinks, leaving your session data in place
- Backs up existing real files before replacing
- Skips already-correct symlinks
- Removes stale skill symlinks that point into the repo but whose target no longer exists
- Respects `SKIP_LIST` for machine-specific files (format: `"filename:machine"`, machine = `mac` | `linux` | `pi` | `both`). It is honoured by the dotfile loop, both `.claude/` loops, `link_directory_contents`, and every `vscode`/`shell`/`tools`/`gitignore` step gate — a new step that skips none of those will fire on a box with no editor
- `.claude/CLAUDE.md` is symlinked to `~/.claude/CLAUDE.md` — the user-level instruction file loaded in every repository (no installer change was needed; the top-level `.claude/` file loop already handles it)
- `settings.json` is **symlinked** like everything else, and only *copied* with `__DEMETER_REPO__` path templating when the profile's copy actually contains that token — templating cannot write through a symlink. No profile uses the token today, so in practice every profile's `settings.json` is a symlink, which is what lets `/config` edits land back in the repo as a tracked diff. The corollary bites on a box whose `settings.json` is owned by something else: a symlink there sends `/config` writes into the clone, leaving it dirty so the next pull silently stops fast-forwarding. That is why the `pi` profile ships no `settings.json` at all
- `settings.local.json` lives at `.claude/.claude/` and is symlinked normally
- `.mcp.json` is NOT managed by the repo (contains tokens) — configure manually
- `.claude/hooks/` is linked per-file into `~/.claude/hooks/` by the same `.claude/` directory loop; the hooks that run from there are registered in each profile's `settings.json`
- `tools/` is profile-independent and linked per-directory into `~/.claude/tools/`. Linking only makes the source available, so a tool exposing a Makefile `install` target is then offered a build (step 12) — the symlink alone gives no signal that an installed artefact is older than the source
- `vscode/extensions.txt` is the companion to `settings.json`: a theme named in settings does nothing until its extension exists, and VS Code falls back silently. The installer only ever **adds** — a locally-installed extension missing from the list is left alone. `vscode/sync-extensions.sh` writes the list back from a machine; it excludes extension ids published from `tools/*/package.json`, which are not on the Marketplace and are installed by their own make target. `editor_cli()` resolves the CLI (PATH, then the macOS app bundle) and `read_extension_list()` parses the file (`#` comments and blanks ignored)
- `vscode/settings.json` is profile-independent and symlinked **wholesale** over the editor's user settings (`~/Library/Application Support/Code/User/` on mac, `~/.config/Code/User/` on linux, plus Insiders and VSCodium when present). Because it is a symlink, VS Code writes UI changes back into the repo — machine-specific keys (`window.zoomLevel`, `claudemeter.debugLogFile`) are kept last in the file so they stand out in a diff. `vscode_user_dirs()` resolves the paths; `should_skip "vscode" "$machine"` opts a platform out
- `vscode/strip-stale-peacock-keys.sh` is the counterpart to `peacock.excludedSettings`: an exclusion stops Peacock writing a key but never removes the copies it wrote before, and a workspace file outranks the shared settings, so the pin loses silently in exactly the repos nobody thinks to check. The sweep reads the owned-key list out of `vscode/settings.json` (never hardcodes it), scans `$HOME` five deep with `PEACOCK_SCAN_ROOT`/`PEACOCK_SCAN_DEPTH` overrides, prompts once with what it found, and re-parses every file it edits to prove only the owned keys left — a file whose keys share a line is reported, not rewritten. Run standalone or let step 14 run it
- `git/ignore` is profile-independent and linked to **`core.excludesFile` when it is set, else `$XDG_CONFIG_HOME/git/ignore`** — `git_excludes_path()` resolves that, expanding a leading `~`/`$HOME`. Linking the XDG default is what makes it need no `git config` at all, and linking the configured path instead is what keeps a machine that sets `core.excludesFile` (an rdev image, say) from leaving the file inert. `is_rdev_managed` opts that path out, `should_skip "gitignore" "$machine"` opts a platform out. The step then runs `git check-ignore` in a throwaway `git init` (`git_ignores_probe()`) rather than trusting the symlink, because every failure mode here is silent
- Idempotent — safe to re-run after pulling changes

## When Making Changes

- **Shell scripts**: Use `shellcheck` on any changed `.sh` files if available
- **README**: Keep `README.md` up to date when adding features or changing the installer workflow
- **AGENTS.md**: Keep `AGENTS.md` files up to date when directory structure, patterns, or conventions change
- **CLAUDE.md**: Keep this file up to date when repo structure, installer behavior, or conventions change
- **Test the installer**: After modifying `install.sh`, verify it still works on a clean run — the script must remain idempotent

## Conventions

- **One profile directory per machine setup**, under `profiles/` (e.g. `larrabeedylan_work_linux`)
- **Dotfiles only**: Files in profile directories should be dotfiles (prefixed with `.`) or inside `.claude/`
- **No secrets in repo**: Sensitive values (API keys, tokens) belong in `~/.secrets` or similar, sourced from shell config — never committed
- **Machine-specific skipping**: Use the `SKIP_LIST` array in `install.sh` to control per-platform linking
- **rdev boxes**: rdev regenerates `~/.zshrc` and `~/.tmux.conf` from its image and lists them in `~/.rdev-managed.json`; `is_rdev_managed` keeps the installer from linking over them. The login shell there is zsh, so `.bashrc` is never read — a profile customizes rdev through `~/.zshrc.local` (sourced near the end of rdev's `.zshrc`, in login and non-login shells alike, unlike `~/.zlogin`), `~/.zshrc.pre` (before `compinit`), and `~/.tmux.conf.local`. `larrabeedylan_work_linux/.zshrc.local` is the zsh port of its `.bashrc`; it leaves history, completion, direnv, mise and the starship prompt to rdev
- **The Pi profile is an identity transform, so it is symlinks rather than a fourth copy**: `larrabeedylan_home_pi` installs as the `jarvis` service user on the Raspberry Pi, so the Claude Code Remote Control server spawns phone sessions carrying the same skills as a laptop session. Every other pair of profiles here differs by the nine-substitution work→home transform, and `cmp transform(work) home` is what makes drift in that pair detectable; home→pi is the **identity** transform — same forge, same change-request vocabulary, same reviewer arrangement — so a byte-identical fourth copy would add a drift surface with nothing to check it against. So `skills/`, `hooks/` and `scripts/` are symlinks into the home profile, and a divergence later means replacing a symlink with a real directory — a visible, deliberate act rather than an edit that happens to land in one of four places. `notify.json.example` is its own file, because the Pi already holds the bot's credential for its own alerting and references it with `bot_token_file`/`chat_id_file` rather than keeping a second copy. `environment.json.example` is its own file too, since `artifact_store` must be pinned to `mnemosyne` where a hook refuses the Artifact tool outright and claude.ai is therefore not a fallback. Three things are **deliberately absent**, and each would fail silently if added. **No `settings.json`**: the Pi's is owned by Gaia, which merges `permissions.defaultMode` and the Artifact-refusal hook into it key-by-key, and a wholesale symlink would both wipe those and redirect `/config` writes into the clone — dirtying the tree so `repos-sync` quietly stops fast-forwarding and the auto-update dies with nothing reporting it. **No user-level `CLAUDE.md`**: that slot is global to `jarvis`, which also runs the attacker-reachable voice agent and the nightly vault organize pass, so instructions meant for phone sessions belong in `remote-root/CLAUDE.md` where they are project-scoped. **No dotfiles**: the service user has no interactive shell. The Pi side — the HEAD-guarded daily timer that pulls Demeter and re-runs the installer, and the script that merges the hook registrations — lives in Gaia under `bare-metal/piserver/bootstrap/demeter/`, so changing what this profile installs may mean changing that too
- **A glob with no match is a filename**: the `.claude/.*` loop ran unguarded for months and, on every profile with no hidden entries in `.claude/` (which is all of them), created a dangling symlink in `~/.claude` literally named `.*`. It had been there since July before anyone looked. `[[ -e "$src" ]] || continue` is the fix, and the general rule is that an unguarded glob feeding `link_file` creates garbage rather than doing nothing. `link_directory_contents` also skips `__pycache__` outright — it is gitignored build cruft, so publishing it into `~/.claude` is wrong on every machine and would ship one architecture's bytecode cache to another
- **Nothing in the installer may be fatal on an unattended run**: the submodule update was a bare command under `set -e`, so a flaky network at 04:30 aborted the whole run and installed nothing. It warns now. Any step that can fail for a reason outside the repo needs the same treatment, because the Pi's timer has no one watching it
- **Skills**: Each skill gets its own directory under `.claude/skills/` with a `SKILL.md` file
- **An empty diagram is worse than no diagram**: `changes-diagram` builds a per-function call graph with Python's `ast`, which is high fidelity and useless on the Go, Terraform and TypeScript repos that make up most of the work here. The original it was ported from simply produced zero nodes there — and a chart with no boxes reads as *this branch changed nothing*, not as *this language is unsupported*, so the failure is silent and actively misleading. The guarantee is therefore mechanical: **a non-empty diff always produces a non-empty chart.** When the AST pass yields no nodes, it falls back to a file/module graph with import edges resolved per language (Go via the `go.mod` prefix, TS via relative-path probing with extension and `index` fallbacks, Terraform via `module`/`source` and cross-file resource references), and everything else gets grouped boxes with line counts and no edges. The JSON carries a `mode` of `callgraph` or `files` so the page can say which it is. Proven across Go-only, Terraform-only, TypeScript-only, Markdown-only, mixed-with-binary, tests-only and module-level-Python diffs
- **The diagram's HTML is the artifact, and the publish target is configuration**: the page is self-contained apart from elkjs on jsDelivr and Google Fonts, which are all on the Artifact tool's CSP allowlist, so it publishes unmodified — that compatibility is load-bearing and any new external resource has to be checked against that allowlist or it fails invisibly. Where it publishes comes from `skill-env.sh`'s `artifact_store`: `claude` uses the Artifact tool, `mnemosyne` is the home store and is **deliberately a runtime-discovery stub**, because it exists on no work machine and could not be inspected from the one this was written on. `auto` tries mnemosyne, then the Artifact tool, then writes the file locally — and a local file is a success, never a failure. Two traps the port left behind: the Artifact tool takes a `favicon` of one or two emoji, not the `icon` string the source used, and it **prefers the HTML `<title>` over the `title` parameter**, so a template title leaks into every publish — the rendered copy is retitled per branch before publishing and the shared template is never modified
- **A skill must never hardcode what differs between machines**: the work profiles review on GitLab with one AI reviewer and publish to Claude Artifacts; home reviews on GitHub with a different reviewer and publishes to mnemosyne, which does not exist on any work box and so cannot be inspected from one. Writing those facts into the skills produces something that works only where it was written and fails silently everywhere else — the brittleness is invisible, because a skill that greps for the wrong bot username finds nothing and reports a clean review. `scripts/skill-env.sh` is the seam: it carries the per-profile defaults **in code** and merges `~/.claude/environment.json` over them, so a missing or malformed config degrades to working defaults instead of breaking, and `skill-env.sh check` prints what a skill will actually see. The keys that matter are `forge`, `api_script`, `change_request`/`change_request_short`, `review_bots`, `review_job`, `operational_bots`, `iac_bot` and its two markers, `artifact_store`, `require_human_approval`, and the seven `fix_*` run defaults. **An empty value means the capability is absent on this machine, never "go and guess"** — empty `review_bots` means treat every non-operational bot thread as real feedback, empty `iac_bot` disables the apply-before-merge gate outright, and empty `review_job` means a review cannot be re-triggered and the skill must say so rather than retry something that is not there. The example file is committed with placeholders and the real one is seeded by installer step 9
- **Profile divergence is a mechanical transform, not prose rewriting**: a work skill becomes its home counterpart through exactly these nine substitutions, in order — `an MR`→`a PR`, `An MR`→`A PR`, `merge requests`→`pull requests`, `merge request`→`pull request`, `Merge Request`→`Pull Request`, `GitLab`→`GitHub`, `\bMR(?=\d)`→`PR`, `\bMRs\b`→`PRs`, `\bMR\b`→`PR` — plus `gitlab-api.sh`→`github-api.sh`. Treating it as a transform rather than an edit is what makes drift detectable: `cmp transform(work) home` either passes or names the line. It had not been treated that way, and the cost was real — `fix-linear` and `commit-msg` on the home profile still said "merge request" and "GitLab" throughout, because they were copied rather than transformed. Three traps. **`\bMR\b` cannot see `MR2`** — the digit is a word character — so stack labels like `MR1`…`MR5` in `plan-subtasks` survive untransformed without the lookahead rule. **`\b` silently no-ops in BSD `sed` on macOS**, producing output that looks transformed and is not; use `perl`, GNU sed, or python `re`. And **never add a URL-rewriting rule**: `reflect-peer`'s context files carry real `gitlab.com/-/merge_requests/…` links that are evidence, not vocabulary, and rewriting the host turns them into 404s. And a **frontmatter trigger list is bilingual on both profiles, so it is the second never-transform case** alongside URLs: `changes-diagram`'s `description:` carries both `"visualize the MR"` and `"visualize the PR"` on work *and* home, because those strings are utterances a user might type rather than vocabulary describing a forge — a user on either machine says either word. Transforming them collapses the pair into a duplicate and silently drops a trigger. Prose in a description still transforms normally (`autopilot`'s "merged merge request" must become "merged pull request"), so the exemption is the quoted phrases, not the line. Write the **work** copy so the transform yields clean English on the other side — never `an \`MR<n>\``, and no literal example URLs — since the transform cannot see through a backtick or into a hostname. The corollary bites in ordinary prose too: a work copy that reaches for the neutral "change request" transforms to "change request", not "pull request", so a home copy hand-edited to the right word reads as drift forever. Say "merge request" in the work copy wherever the home copy should say "pull request"
- **A rewrite needs a substrate**: `changes-description` can check every claim against a diff; `docs-humanize` has no such thing — the source text is at once the ground truth and the thing on trial, so a rewrite that is fluent and subtly wrong is undetectable once the original is gone. Its first phase therefore builds a numbered **fact ledger** out of the source, and every later phase is measured against it: the auditor reports *item F14 is absent* rather than *feels complete*, and a claim tracing to no ledger item is an invention to be cut. The same reason makes open questions non-negotiable output — a generated document's most expensive lie is the one where it smooths over what nobody has decided. Its slop detector is mechanical and split in two: HARD patterns (no legitimate technical use) are defects the judges must block on, SOFT ones (`ensure`, `robust`) are shown as evidence only, because a single false positive on a real `ensure the pod is Running` teaches the panel to ignore the whole measure. Match against a **whitespace-flattened** copy — markdown wraps wherever the author's editor wrapped it, so a line break lands inside "plays a crucial role" and the phrase goes undetected in exactly the documents the list exists to catch. The write-back is gated on an explicit yes, saves the original to the scratchpad first, never renames a Linear ticket (every pasted link breaks), and prefers a Notion **suggested edit** over an overwrite on any page the user does not own
- **Subagents are encouraged, Workflows are not assumed**: `.claude/CLAUDE.md` carries a standing instruction to spawn subagents whenever work parallelises, without asking — sessions otherwise arrive with a harness default telling them not to, which is not something this repo sets and not something a skill can see. The justification is `tools/agent-watch/`: a fan-out is observable here, so it costs nothing to watch. The **Workflow** tool keeps its own opt-in, since it launches agents by the dozen. The same section restates the two things a spawned agent never inherits — the no-comments rule, and that "read-only" has to explicitly forbid writing into the working tree, which agents have ignored when it was merely implied
- **The scannable-output spec lives in two places on purpose, and they are not duplicates**: a wall of generated prose is unreadable in a way the reader cannot fix after the fact, so the rules for avoiding one belong in `.claude/CLAUDE.md`, loaded into every conversation in every repo — a skill the agent has to be reminded to invoke is a skill that arrives after the damage. `aidr` is the retrofit for when it was forgotten anyway, and the split is by cost: the global copy is compressed to the rules themselves because it is paid for on every single turn, while the skill carries the procedure, the four-way classification, the budget and the worked template because it is paid for only when invoked. Four things are load-bearing in both. **Actions come first**, because theirs is the only section with a deadline. **The class of every line is unambiguous** — action for the reader, action already taken, fact, background — since a reader working out which is which is doing the writer's job. **Commands sit at the step that needs them** and run as-is, because a command assembled out of prose is a command retyped wrong. And **paths are markdown links, never backticked** (`[config.ts:88](src/config.ts#L88)`), since a bare path costs a search in exactly the editor these are read in. Two guards stop the cure becoming the disease: the spec is a **compression that may drop anything and add nothing** — silence in the source is reported as silence, because an invented step is worse than the wall it replaced — and **structure is only applied where structure is needed**, since headings on a two-sentence answer are the same padding in a different shape. ASD-STE100 is cited for its *writing* rules only (one instruction per sentence, under 20 words, active, imperative, simple tenses, no noun cluster past three words); compliance is never claimed, because the approved-word dictionary is not checkable here and claiming it would be the exact kind of unearned confidence the rule exists to remove
- **No comments in code**: `.claude/CLAUDE.md` forbids agent-written code comments globally. Any skill that writes or edits code must restate the rule in its own prompt — subagents spawned by a skill receive the skill's text, not the user's `CLAUDE.md`. The only sanctioned exception is `security-audit`'s PoC and verification tests, where the write-up is the deliverable
- **Vendor packages**: Third-party skill sets go in `_vendor/<name>/` as git submodules
- **rdev bootstrap**: `tools/rdev-bootstrap/bootstrap.sh` is started in the background by the first interactive zsh on an rdev box (`.zshrc.local`), so nothing runs until a terminal opens. It clones **every** repo before setting any up, so one slow setup (Demeter's installer) can't keep the others from being cloned, and runs each repo's setup in a child under `timeout` (`RDEV_BOOTSTRAP_SETUP_TIMEOUT`, default 1200s) so a hung step fails that repo and lets the run finish. Failed repos retry on the next shell. A shell opened while it runs prints the last log line instead of staying silent
- **Shared tools**: First-party projects that are not tied to one machine go in `tools/<name>/` at the repo root rather than being duplicated per profile. Build output (`node_modules/`, `dist/`, `*.vsix`) is ignored by the tool's own nested `.gitignore` — **nothing runnable ships in git**, so every machine must build, and a box that skipped step 12 has the extension id registered with no `dist/extension.js` behind it: it lists as installed and silently never activates. `editor_cli()` is what makes that step reachable on a Remote-SSH box: `code` is only on PATH inside the integrated terminal, so it also globs `~/.vscode-server/{cli/servers/*/server,bin/*}/bin/code-server` (newest first) and **proves** each candidate with `--list-extensions` before using it — `bin/*/bin/remote-cli/code` needs `$VSCODE_IPC_HOOK_CLI` and exits non-zero without a window, which is precisely the case that has to fall through
- **A README link to a sibling file fails `vsce package`**: vsce resolves every relative link in the README against the repository it would be published from, and with none detectable it **errors out** rather than warning — `--allow-missing-repository` covers the missing `repository` field, not the link. An in-page anchor (`[...](#heading)`) is fine, which is why `claude-usage` packages and `agent-watch`'s `[DESIGN.md](DESIGN.md)` did not. Each tool's `package` target therefore passes `--baseContentUrl`/`--baseImagesUrl` built from `REPO_URL`/`RAW_URL`, so the link keeps working for a human reading the repo and packaging stops depending on what the README happens to link. The failure is loud in the installer's output and invisible afterwards: step 12 prints `Failed to install <tool>` and moves on, leaving a tool that is symlinked into `~/.claude/tools/` and absent from `--list-extensions`.
- **Never truncate content to protect the webview**: `tools/agent-watch/` shows what an agent said, thought and got back from a tool, so cutting any of it defeats the tool — and the cut is invisible, because a clipped string looks like a short one. The cost of a hundred-KB `Bash` result is paid by **not rendering** instead: a detail panel fills its `<pre>` on first open, so a collapsed panel costs only its one-line header, and `detailRevision` in `panel.ts` re-posts an open node's detail only when its content changed rather than on every 2s poll. Clipping is for one-line headers alone — node labels and the per-tool summary — and `clip()` flattens whitespace, so it must never touch a body destined for a `<pre>`: that strips every newline and the panel then reports `N chars` where it should say `N lines`. Long prose is **folded, not cut** — `preview.ts` holds back everything past 20 lines or 1600 chars behind a `Show more` button that names the exact remainder, and the fold survives the live re-render keyed by event index plus panel label. A transcript's user `content` is often a bare **string** instead of a block list, so `blocksOf` must synthesize a text block for it or most prompts never render at all (614 such lines across 40 local transcripts); and a text event needs a `role`, because an `isMeta` line is harness-injected skill text or an image marker, not something the user typed.
- **Notifications are one-way, and that is a property of hooks, not a shortcut**: `notify.py` pushes to Slack (work) or Telegram (home) on `Stop`, `StopFailure`, `Notification`, and `PreToolUse` for `AskUserQuestion|ExitPlanMode`. Replying from chat is impossible for the cases that matter — a permission prompt and an `AskUserQuestion` are blocking UI that only the session's terminal can clear. A `Stop` hook *can* return `{"decision":"block","reason":...}` to resume a finished turn with text from elsewhere, which is the one case chat could serve; it is deliberately not built, because it is the only design here that could hold a turn open, and a session that stalls waiting on a notification is strictly worse than one that merely did not tell you about itself. Everything therefore does one HTTP POST and exits. Keep it that way: the `thread` field in the envelope is the seam to add replies later without reshaping anything
- **Telling the user and letting them answer are two channels, and a skill can arm only one of them**: a ping says *come and look*; what lets the user act on it from a phone is Claude Code's **Remote Control**, which forwards the live session to claude.ai and the Claude app and can clear a blocking permission prompt or an `AskUserQuestion` from there. The obvious design — `/ping` sets the remote session up and `/ping off` tears it down — **cannot be built**: Remote Control is established by the `/remote-control` slash command, a slash command is typed by the user, and an agent has no way to run one in its own session. Writing `remoteControlAtStartup` reaches only sessions started afterwards, and the connection state cannot be read back from inside the session either, so a skill cannot even report honestly on whether it is up. It is therefore armed at **startup** — `remoteControlAtStartup` is `true` in every profile that ships a `settings.json`, and that file symlinking to `~/.claude/settings.json` is what makes it count: the key is honoured at user and managed level, while a `true` in a project or local `settings.json` is **ignored** and only a `false` there has any effect. The Pi ships no `settings.json` and needs none, since its sessions are spawned by a `claude remote-control` server. The alternative considered was a reminder line in the ping telling the user to run `/remote-control`, and it fails in precisely the case the feature exists for: the ping that matters most is the one an `autopilot` run sends hours after the user walked away, where nothing printed in the terminal will ever be read, and an instruction they cannot see reads in the run report as though it had been followed. Two corollaries. `/ping off` **disconnects nothing** — the connection was never the skill's to make, and dropping it would cut off a session the user may still be driving from the phone. And a ping must **never claim the session is answerable from the phone**: the startup setting is the reason it usually is, not evidence that it is this time, since a box with no claude.ai login, a gateway `ANTHROPIC_BASE_URL`, or an org policy toggle starts without it and says nothing
- **Reachability changes what an unattended run may do about an ambiguity, and the premise it overturned was load-bearing**: `autopilot` was written on the line *from the commit onwards there is nobody to ask*, and that single sentence is what forced every mid-run judgment call down the decide-alone-and-ledger path. With the session reachable from a phone and `notify.py` registered on `PreToolUse` for `AskUserQuestion`, raising a question both notifies and can be answered — so asking is now right for the calls that are expensive to get wrong: anything irreversible or chargeable, a fork where one branch is hard to undo, and the Step 11 escalations the run could act on immediately (a product or policy call, a merge conflict's intent), which previously **ended** a run that could have carried on. It stays the exception rather than the default for one reason: **a question stalls the run until somebody answers it**, and a user asleep or at dinner turns an unattended run into a parked one — so most calls still take the most defensible option plus a ledger line, and a question that *was* answered earns no ledger entry, because that decision was the user's and is already on the record. Three things make the ask real rather than theatrical. **It must stand alone**: it is read on a lock screen and answered in an app, so an option saying *as discussed above*, naming a file to open, or needing two paragraphs weighed against each other is unanswerable. **It comes before the irreversible step, never halfway through**, where neither answer is any use. And **it is never accompanied by a ping**, since the hook already fires on the question and the second copy is what teaches the user to ignore both. Step 10c's old wording is the incoherence this fixes — *ask by pinging rather than parking silently… ask for a yes*, over a channel that cannot carry one. The counterpart hazard is unchanged and now more likely to come up: `pause` still refuses to park with a question dangling, because a paused session swallows an answer that may be in flight from the phone
- **A notification is only as good as its gate**: with a dozen sessions live, an ungated `Stop` hook is indistinguishable from no notifications at all. The primary gate is now **opt-in arming** (below); `min_interval_seconds` per session and the suppression of anything carrying `agent_id` apply always, since subagents `Stop` constantly, and `min_turn_seconds` (a turn shorter than this was you at the keyboard, not you away from it) survives only as the fallback gate when `only_when_armed` is `false`. Turn length is measured from the **last handoff back to you**, which is *not* the last freely-typed prompt: answering an `AskUserQuestion` or rejecting a plan returns control just as much, and measuring only typed prompts reported a 20-minute turn as 24 hours. `handoff_epoch()` therefore correlates `tool_result` blocks against the ids of `AskUserQuestion`/`ExitPlanMode` `tool_use` blocks. It scans the transcript backwards in widening windows rather than a fixed tail, because a fixed tail misses the prompt on exactly the long turns worth reporting. `handoff_at()` exposes that same epoch absolutely rather than as a duration, because the opt-in gate needs to compare it against a timestamp
- **Notifications are opt-in per session, and `/ping` is the opt-in**: the automatic hook is off in every session until the user asks for a ping, which writes `armed_at` into that session's state and switches it on. The reason is the gate bullet above taken to its conclusion — `min_turn_seconds` is a *proxy* for "you walked away", and a bad one: a 60-second floor fires on most substantial turns while the user is sitting right there watching, which is precisely how a notification channel becomes something they stop reading. Asking for a ping is not a proxy, it is the gesture itself, so it is what the hook triggers on. Three properties make it safe to leave armed. It is a **latch, not a timer**: only an explicit `/ping off` clears it, and the first version of this got that wrong by inferring the user had returned from their next prompt, from `back`, or from time passing. All three are wrong for the same reason — answering in chat and then walking away again is the normal way the feature is used, so a prompt is not evidence of presence, and a wrong inference here fails silently in the one direction that matters: the session goes quiet precisely when it was being relied on, and nothing reports that it did. The latch belongs to the user, never to the skill and never to the hook. It is **per-session, never global**, so a ping from one of a dozen sessions opts in only that one; `away` remains the global override that notifies for everything regardless. And the arming is written **only on the send's success path**, since a session silently opted in to notifications the user was just told did not go out is worse than either outcome alone. `armed_at` is written whether or not a thread id came back, which is why it sits outside the `if thread:` branch — a transport that cannot thread returns no id, and gating the arming on one would leave the session mute on exactly the machines where threading is unavailable
- **The notification body is summarized by a model, and the hook shells out to do it**: `last_assistant_message` is a turn's closing chat message — written for a terminal with the diff open, routinely 500 words of headings, tables and file links, against a lock screen that shows about 140 characters. Clipping it, which is what it did, produces a wall of markdown whose first line is often a sentence ending in a colon pointing at a table nobody can see. `notify.py` therefore passes the body through `claude -p` before sending. **Use the subscription, not the API**: an `x-api-key` call is faster and was the first implementation, and it was wrong here because the API account carries no credit while the Claude Code subscription is already paid for — the symptom was an `HTTP 400 credit balance` that no amount of correct code fixes. Five things are load-bearing. **The budgets are deliberately loose** — 180s for the summarizer inside a 240s hook, against an observed 9–29s spread — because the alternative to waiting is the truncated dump the feature exists to prevent, and the only state in which any of this fires is one where the user is away and waiting is free; every tight budget tried here (6s, 25s, 35s, 45s) was tuned to a sample and then blown by an outlier. **Every failure degrades to a mechanical condense** and still sends, since a missing CLI, a logged-out machine or a slow model must never cost a notification, and the log records which path ran so a degraded machine is visible rather than inferred. **The child gets a neutral `cwd` and no MCP, hooks or plugins**, or it loads this repo's `CLAUDE.md` and every skill before answering; `NOTIFY_SUMMARIZING=1` in its environment is the backstop that stops a hook spawning a session that fires hooks. **Long input is windowed head-and-tail rather than truncated**, because the outcome sits at the top of a message and the ask at the bottom, so cutting the tail discards precisely what the user needs. **Questions are summarized like everything else** — an `AskUserQuestion` body is the literal questions, written for a terminal, and the user cannot answer from the notification anyway: all it has to convey is that the session is waiting on them and what about. The CLI is resolved by probing install locations and then `shutil.which` over an augmented `PATH`, never by name, because hooks run with a bare `PATH` where `claude` does not exist; `summarize.command` is the per-machine escape hatch and `notify.py --test` prints what it resolved, with a timed live sample
- **The thread is the context, so only its first message repeats it**: a session's notifications are one thread — Telegram replies with `reply_to_message_id`, Slack with `thread_ts` — and every reply renders the first message quoted above it. So the repo and the session title are already on screen in every reply, and printing them again spent roughly a third of a 140-character lock screen restating the line directly above. The shape is therefore split by position, not by transport: the **first message** is `<repo> · <session chat title>` then its body, with **no glyph**, because a thread root is an anchor and its class is the least interesting thing about it; every **reply** is `<glyph> <body>` and nothing else. `envelope["thread"]` is the discriminator and it is reliable in both producers — `notify.py` sets it from `state.get("thread")` and the `ping` skill from the same session state, so it is absent exactly once per session. The six glyphs (`✅❓🔐🔄💤🔥`) still carry the kind one-to-one, which is what makes dropping the words safe. The second field is the **session's chat title**, read from the transcript where Claude Code writes `ai-title` and `custom-title` records, so it needs no editor API — `worktree-sync`'s `resolve.ts` had worked this out and its precedence is reused verbatim, a `custom-title` the user typed beating the generated `ai-title`. Two traps come with it: the record is written early and **scrolls out of a fixed tail** (only 38 of 139 local transcripts carried one in their last 256KB), so the lookup uses the widening-window `scan_tail()` shared with `handoff_at()`; and the records appear both compact and spaced, so each candidate line is `json.loads`-ed rather than regex-matched. The branch survives **only as a fallback** for a session too new to have a title, and the 8-character session id was dropped outright — it reads as a commit hash and identifies nothing a human recognises. `notify.py --label <session-id>` prints the resolved title so the `ping` skill shares the one parser, globbing `~/.claude/projects/*/<id>.jsonl` since only the hook is handed a transcript path
- **Composition is shared across transports; only delivery is not**: the root/reply split above is identical in the Telegram and Slack senders, because a per-client layout is two things to keep in step for no gain. What stays transport-specific is strictly about *delivery*: Slack still needs the `<@U…>` mention prefixed into **both** `text` and the rendered block, since a threaded reply otherwise never notifies and `chat.postMessage` answers `ok` regardless; Telegram needs none of that because `reply_to_message_id` renders inline and notifies by itself. Dropping the header freed real room, so the summariser's budget went up by half — `SUMMARY_MAX_WORDS` 45→68 and the mechanical fallback `CONDENSE_LIMIT` 240→360 — and the `ping` skill's prose budget moves with it, or the skill and the hook disagree about the same message
- **Away mode is a file, not an environment variable**: `~/.claude/notify-state/away.json`, because hooks do not inherit your shell's environment — the same reason `gitlab-api.sh` reads its token from `.mcp.json` rather than `~/.secrets`. It drops the `min_turn_seconds` gate and nothing else. `away`/`back` in `shell/terminal.zsh` are thin wrappers over `notify.py --away`, guarded on the hook existing
- **A `U…` id is not a DM channel**: `chat.postMessage` accepts a user id in `channel` and posts to that user's DM with **Slackbot**, not with your app — it returns `ok`, so the only symptom is that the messages are somewhere nobody looks. A DM from the app needs the `D…` id that `conversations.open` returns for that user, which is why `notify-send.sh` resolves any `U…`/`W…` channel through it and caches the answer in `~/.claude/notify-state/slack-dm.json`; `im:write` is the scope that call needs, on top of `chat:write`. A `D…` or `C…` channel is passed through untouched.
- **Threading a Slack DM silences everything after the first message**: `chat.postMessage` with a `thread_ts` makes every notification after a session's first one a **threaded reply**, and Slack treats those as second-class — no new top-level message, no reliable push, and Slack only auto-follows threads *you* started or replied in, never a bot's. The failure is exactly the one the feature exists to prevent: a session says it has a question, then finishes forty minutes later into a thread nobody is watching. Observed here — five sends, one visible. `slack.mention` fixes it by prefixing `<@U…>` to the message, since a mention notifies regardless of subscription; it defaults to `slack.channel` when that is already a `U…` id, and `slack.mention_levels` keeps it to `stop`/`question`/`permission`/`failure` so a mention never degrades into noise. **The mention must sit in the `blocks`, not in `text`** — given both, Slack renders the blocks and keeps `text` only as notification fallback, so a mention living solely in `text` is never rendered, never registers as a mention, and never notifies, while `chat.postMessage` still answers `ok: true`. That was gotten wrong here on the first attempt and the symptom is indistinguishable from the bug it was meant to fix: a message that lands in the thread looking entirely normal. Verified end to end — the mention goes at the head of the rendered section block *and* in `text`, which is what the lock screen previews. `reply_broadcast: true` is the other option and is worse here — it copies the reply to the top level, undoing the per-session grouping the thread was for. **None of this applies to Telegram**: `reply_to_message_id` renders inline rather than collapsing, so every message stays top-level and notifies by itself, and an @-mention is meaningless in a 1:1 bot chat. Telegram's real threads (forum topics, `message_thread_id`) exist only in supergroups
- **A Slack incoming webhook cannot thread**: it ignores `thread_ts`, so per-session threading needs a bot token with `chat:write` plus a channel. Both are supported and the webhook is the documented default, since it needs no app scopes — but with many concurrent sessions the channel interleaves badly without threads, so the bot token is the better end state. The phone's push preview shows only Slack's `text` field, never `blocks`, so the one-line summary has to live in `text` or the notification is useless on a lock screen
- **`/ping` is the deliberate counterpart to the hook, and shares its state**: `notify.py` fires automatically and is therefore gated hard; the `ping` skill is invoked on purpose — by the user, or by a skill handing over a question, a blocker or a finished run — so it **bypasses every gate** (`min_turn_seconds`, `min_interval_seconds`, quiet hours, subagent suppression). An explicit ping is never noise. It goes straight to `notify-send.sh send` with the same envelope the hook uses, which is why the skill is byte-identical across all three profiles: the Slack/Telegram split already lives in the sender, so nothing in the skill may name a transport. It reads and writes `~/.claude/notify-state/sessions/<id>.json` so a ping lands in the session's existing thread rather than floating free — read-modify-write, never clobbering the `last_sent`/`last_kind` keys the hook owns, and tolerating a state directory that does not exist yet on a machine where no notification has fired. The message must carry what the session is doing *and* whether it needs anything: the lock screen shows one line, so a ping that says "done" has wasted it
- **A hook that fails is invisible**: `notify.py` appends a line for every invocation including the silent ones (`skip: turn 11s < 60s`), to `~/.claude/notify-state/notify.log`, capped at 1 MB. Without it, a wrong gate and a broken token look identical from the outside. Every error path logs and exits 0, and the POST timeout (5s) sits well under the hook timeout (15s) so a dead transport costs a turn seconds rather than the full budget. A missing or `REPLACE_ME`-filled `~/.claude/notify.json` is a dormant no-op, never an error — the feature ships switched off and comes alive when a token lands

- **Claude credentials**: `tools/claude-usage/` reads the OAuth token Claude Code stores (macOS keychain item `Claude Code-credentials`, else `~/.claude/.credentials.json`) **read-only** — it must never write to or refresh that token, because a rotated refresh token there would log the user out of Claude Code. Anything needing a token it owns does its own PKCE login and keeps it in VS Code `SecretStorage`. Usage comes from `https://api.anthropic.com/api/oauth/usage` with an `anthropic-beta: oauth-2025-04-20` header; prefer the response's `limits[]` array over the older `five_hour`/`seven_day` fields
- **One extension, many windows**: every editor window loads its own copy of an extension, so anything polling a network endpoint must coordinate or it multiplies by the window count — `tools/claude-usage/` got rate limited this way. It now shares one reading through a lock file plus a JSON cache in the user's cache dir (`~/Library/Caches/claude-usage/`, `$XDG_CACHE_HOME/claude-usage/` on Linux), watched by every window so they update together. Keep that cache per-user rather than per-editor-installation, never put credentials in it, and share backoff state through it as well as data
- **Never gate an install on OS-dependent behaviour**: `make install` runs the test suite, so a test that asserts the kernel did something — `fs.watch`/inotify delivering an event, a filesystem notification arriving within a timeout — turns an ordinary install into a hard failure on any box where that mechanism is unavailable (containers, overlay and network filesystems, or an exhausted `fs.inotify.max_user_watches`). Make the code guarantee the behaviour itself (a `stat` poll backing a file watch) and assert *that* guarantee; treat the OS fast path as an optimization that is allowed to do nothing. A test simulating the failure (`fs.watch` throwing `ENOSPC`) is worth more than one hoping the platform cooperates
- **The editor's tsserver runs ahead of the pinned compiler**: VS Code bundles its own TypeScript (6.0.3 today) and paints the Problems tab with it, while `tools/*` pin `typescript: ^5.7.0` and build with esbuild — so a diagnostic from the next major shows up permanently in the editor and never in `npm run typecheck`, `make check` or CI. Fix the config rather than living with it. `rootDir` is the first one: TS 6 requires it to be explicit instead of inferred from `include`, so both tools set `"rootDir": "src"` beside `outDir`, which changes no output and makes a stray file outside `src` an error instead of a silent `dist/` reshuffle. Reproduce what the editor sees with the bundled compiler API at `/Applications/Visual Studio Code.app/Contents/Resources/app/extensions/node_modules/typescript/lib/typescript.js` — it ships `typescript.js` and `_tsserver.js` but no `tsc.js`, so drive `createProgram` directly
- **Extension test stubs**: `src/testing/vscodeStub.ts` in each tool must cover the whole `vscode` surface `activate()` touches. A missing property (`vscode.extensions`, `window.showWarningMessage`) throws inside fire-and-forget background work, which surfaces as a vitest *unhandled error* — the suite still reports every test passing while the process exits non-zero, so `make check` and `make install` fail with nothing obviously wrong. Add the property to the stub rather than defending in product code, and have `activate()` `.catch()` its background promises so one failure can never take down the run
- **Status bar glyphs**: the VS Code status bar renders in the **UI font** (SF Pro on macOS), not a monospace font, so a glyph the UI font lacks falls back per-character and neighbouring cells end up from different fonts at different widths — block elements (`█` U+2588, `░` U+2591) mismatch badly this way. Prefer geometric shapes UI fonts actually carry (`●○`, `■□`); when a look depends on the user's font, ship a picker that previews live rather than guessing
- **Driving another extension's commands**: `tools/claude-usage/`'s new-chat button runs the Claude Code extension's `claude-vscode.editor.open`, which is a contributed command and not API — it can be renamed or absent, and `executeCommand` on a missing id rejects with a raw `command 'x' not found`. Probe `vscode.commands.getCommands(true)` first and say something useful instead. Claude Code locks the new group **itself**, but only when that call created a new column *and* `claudeCode.lockEditorGroups` is on, so claude-usage locks unconditionally afterwards and tolerates the failure — `workbench.action.lockEditorGroup` sets the flag rather than toggling it, and its `activeEditorGroupLocked` precondition gates menus and keybindings, not `executeCommand`. The group it locks only ever holds Claude tabs, because Claude Code opens `ViewColumn.Beside` or reuses a column that already has one. Status bar priority is "higher sits further left" on **both** sides, so the button is `priority + 1` while the meters are `priority - index`
- **Shared rate limit on `/api/oauth/usage`**: the Claude Code CLI polls this endpoint from every running session, and the limit is per account — so anything else reading it (`tools/claude-usage/`) competes with the user's own CLI sessions and must be frugal, not merely cached. Poll adaptively: compare each reading with the last and ease off geometrically while the numbers are flat, snapping back when they move. A fixed interval spends nearly all its requests re-reading identical numbers. Two things must survive that easing off: `resets_at` is absolute, so countdowns are recomputed locally and need no fetch, and the next poll must never be scheduled past the soonest reset — that is the instant the quota frees up and the user is watching it
- **Browser OAuth**: any login flow here opens the system browser via `vscode.env.openExternal`, never a webview or popup — Okta SSO misbehaves in embedded browsers. Pair it with a loopback `http://localhost:<ephemeral>/callback` listener, and keep the copy-paste fallback for when the redirect can't reach the machine
- **Theme ids**: `workbench.colorTheme`, the `workbench.preferred*ColorTheme` keys, and the `[Theme Name]` scopes in `workbench.colorCustomizations` all take a theme's **settingsId** — `contributes.themes[].id` falling back to `label`, which is often not the display name (`Dark Modern`, not `Default Dark Modern`; only the High Contrast themes carry the `Default` prefix). A wrong id fails silently: the scope matches nothing, and the light/dark toggle no-ops. Scopes match by exact id or a `*` glob at either or both ends, on the name only — there is no scope for "every dark theme"
- **Shared terminal**: `shell/` holds one terminal experience for every machine — starship, zsh-autosuggestions/completions/syntax-highlighting, fzf, prefix history search — sourced as the **last** line of each profile's shell rc (`.zshrc` on Darwin, `.zshrc.local` on rdev). It **fills gaps only**: every block is guarded on whether the feature is already active (`$+functions[prompt_starship_precmd]` — that exact name; starship defines no `starship_precmd`, and the wrong guard loads starship then clobbers its prompt with the fallback, which reads as the config doing nothing — `$+functions[_zsh_autosuggest_start]`, `$+functions[compdef]`), verified against each tool's real init output rather than assumed, because rdev already builds this on its own boxes and owns the files it does it in. Per-feature guards, never one `is_rdev` switch — the half-configured machine is the common case. Three ordering rules are load-bearing and explained in `shell/AGENTS.md`: `fpath` before `compinit`, syntax highlighting from a one-shot `precmd` hook (after every widget, and after rdev's own load, so it can never double-load), and the `source` line staying last. Plugins live at `~/.local/share/zsh/<name>`, the same paths rdev clones to, which is what lets one code path serve both
- **VS Code shell integration is manual**: `terminal.integrated.shellIntegration.enabled` is `false` (in both `vscode/settings.json` and `vscode/machine-settings.json`, since over Remote-SSH the user settings come from the client) and `shell/terminal.zsh` sources `shellIntegration-rc.zsh` itself (path derived from `$VSCODE_GIT_ASKPASS_MAIN`, `code --locate-shell-integration-path zsh` as fallback). Automatic injection breaks revived terminals: VS Code saves the injected `ZDOTDIR` into the terminal's launch environment and re-injects on revive with `USER_ZDOTDIR=$ZDOTDIR`, so its `.zshrc` sources itself and the user rc never runs — a revived terminal shows zsh's bare `host%` prompt. Source the script at top level, and unset `VSCODE_INJECTION`/`USER_ZDOTDIR` before it, or a stale saved environment re-sources `~/.zshrc` and moves `HISTFILE`
- **Global git ignore**: `git/ignore` hides what tooling writes into a repo without touching that repo — Peacock's `.vscode/settings.json` above all. It is machine-wide and profile-independent, so an ignore belongs there only when it is true of every repo on every machine; anything repo-specific belongs in that repo's `.gitignore`. Ignore the **file** (`.vscode/settings.json`), never the directory, so a project can still commit `extensions.json` or `launch.json`. It cannot help a repo that already tracks the file — that needs `git update-index --skip-worktree` or a commit
- **Editor settings**: `vscode/` holds one shared `settings.json`, not a per-profile copy — the point is an identical editor everywhere. Color fixes belong in its `workbench.colorCustomizations` (theme-scoped, so light and dark each get correct values), never in a per-repo `.vscode/settings.json`. Anything Peacock also writes must be listed in `peacock.excludedSettings`, or Peacock's workspace-level write will outrank the user-level pin — but an exclusion only stops *future* writes, and it means "never modify or delete", so `Peacock: Remove All Colors` leaves the excluded keys behind. Adding a key to that list is only half a fix: the stale copies already in each repo's `.vscode/settings.json` have to be stripped by hand (see the Peacock section of `README.md`). Prefer a fix that holds for **any** theme over one scoped to the theme in use — a `[Theme Name]` block only ever fixes the theme you have today, and the light/dark toggle is there to be repointed. See the Editor Settings section of `README.md` for why the High Contrast themes broke the Claude Code webview
- **Peacock favorites**: `peacock.favoriteColors` replaces Peacock's shipped list rather than extending it, so the whole palette lives in `vscode/settings.json` — 12 hues 30° apart in a `Neon` and a `Dusk` family, the prefix being what lets the favorites quick pick filter to one family. Peacock paints the title, activity and status bars with the chosen color and picks the text between `#15202b` and `#e7e7e7` on a brightness threshold, so a saturated mid-tone can sit just past the boundary at 2.5:1 — every value is therefore the lightness nearest its family target that still clears 4.5:1 against the foreground that threshold picks, checked rather than eyeballed. Keep that check when adding a hue; the white-on-65%-black command center scrim is a separate guarantee and does not cover the bars
- **`workbench.experimental.modernUI` is off on purpose**: it defaults to *on* and reroutes the chrome away from the theme. Tabs resolve `modernEditorTab.activeForeground` → `modernTab.activeForeground` → **`list.inactiveSelectionForeground`**, consulting the theme's `tab.*` only when that key is *explicitly customized* in `workbench.colorCustomizations`, and the command center becomes the agent-status pill, which forces a transparent background so `commandCenter.background` is never painted. Light themes almost all use white list-selection text, so under modern UI the active tab label is invisible (every light theme installed here measures 1.00–1.23:1) and the Peacock scrim silently stops working. Turning it off restores both for every theme at once; per-theme `[Theme Name]` pins would have to be written again for each new theme. Don't re-enable it without re-checking those two
- **An autonomous run waits with `Monitor`, never with sleep**: `autopilot` composes the ordinary skills rather than reimplementing them, and the thing that makes it safe to leave running is that it never holds a turn open. A `sleep 120` poll loop — the obvious implementation, and the one the third-party tooling this was modelled on uses — costs the user their prompt line for the length of a CI cycle, which with a dozen concurrent sessions is the whole point of the feature gone. A `Monitor` runs in the background and wakes the session on an event. Its filter must emit on **every** terminal state, not just success: a watcher greping only for green stays silent through a crashloop, and silence is indistinguishable from still-running. Poll remote forges no faster than 60s and tolerate a failed request, since one blip must not kill the watch
- **Reviews outrank CI, and the gates that stay are the point**: addressing review comments means pushing, and every push restarts the pipeline — so handling a red or running pipeline before open threads throws away a complete CI run, every time. Four things autonomy never relaxes. `require_human_approval` means a bot's approval does not merge, and the user driving the run counts as the human while other bots do not. A failing job is classified against its log before any retry, because a real failure retried until it looks flaky is the most damaging thing an unattended agent can do — and the same failure twice is not a flake. On repos with an `iac_bot`, the plan is applied and confirmed **before** the merge and auto-merge is never armed, because auto-merge fires the instant the pipeline is green and can beat the apply, merging infrastructure that was never created. And the fix skills' Important Rule 1 is now a statement of *accountability* rather than a prohibition on the run: they never push and never open a change request, `autopilot` does, and it owns that one branch and nothing else. Writing it that way is what makes `--autopilot false` reliably mean *nothing left this machine*, and it is what stops an agent quoting the rule back as a reason to refuse the hand-off — exactly the kind of thing one would otherwise infer its way into. `fix-feedback --autonomous` is the one sanctioned relaxation of that skill's "never write unasked" rule; it still never commits, never pushes, and never resolves a thread it disagreed with
- **Two reviews, and the swarm is the one with a filter**: the forge's AI reviewer makes a single pass over the finished diff, which is why it misses things worth catching. `review-code` runs a fleet from independent angles and then makes a panel of skeptics try to **refute** every candidate, so only findings that survive refutation are reported — and that filter is the difference, not the agent count. Wiring it into the fix flow is what makes it happen: it was being run by hand, which means it was being forgotten. `--review` is a per-machine default (`fix_review`) rather than a per-skill one: **on** at work, where somebody else is going to read the change, and **off** at home, where nobody is. Two ordering facts are load-bearing and opposite. In `fix-linear` the swarm runs **after** `changes-description`, because only one of the two can invalidate the other: a confirmed finding means a code change, and a description written against a diff that is about to move is the thing that goes stale. In `autopilot` it is launched **in the same turn that arms the `Monitor`**, because the diff is already pushed, CI and the bot are already running on it, and neither gates the other — serialising them there adds a full swarm's latency to a run whose whole point is to need nothing from anybody. `autopilot` has **no default of its own** — all seven live in `skill-env.sh` beside the fix skills' — and the only flags it owns are `--merge` and `--max-rounds`, which describe how far the automation goes rather than what the change is. It overrides nothing, **`--branch` included**: the tempting exception is forcing `--branch new` so a change request exists to review, and it is wrong because that judgment was already made, and made better, by the fix skill's Step 2b escalation checks — Terraform, a protected default branch, a dirty tree. A `--branch default` that reaches `autopilot` survived those on the repository's own terms, so the run pushes the default branch and ends, Steps 5–10 having no change request to drive. **Which skill fires the swarm is about *where*, not whether**: on a run that will open a change request the fix skill does not run it at all and `autopilot` owns it at Step 5b, because fired before the push there is no change request for `fix-feedback` to anchor a finding to; on a `--autopilot false` or `--branch default` run there will never be one, so the fix skill runs it where it stands. It runs once per run, never once per review round
- **Autopilot is on by default, and the whole design follows from one number**: the user reaches for it on 99% of fix runs, so making them type it is making them type the same token 99 times to get the behaviour they always want. `fix_autopilot` is therefore `true` on every profile and the fix skills *hand over* at the end of their own flow rather than waiting to be wrapped. Three things keep that from becoming a loaded gun. **It automates the tail, not the thinking** — the fix skill's gates stay open, so a vague ticket still gets a question and the plan still gets shown; the user who typed `/fix-linear` is at the keyboard at that moment, and what they asked not to sit through is the pipeline, the review and the merge, which is hours, not the five minutes of deciding. An earlier version had `autopilot` self-resolving those gates, which bought nothing and cost a whole implementation whenever a reading was wrong. **`--autopilot false` is the way out**, and it has to exist precisely because the default is on: it yields a branch, a commit message and a description with nothing leaving the machine, which is what a spike wants. And **the direction of the hand-off is what preserves every ordering decision** — `autopilot` stays the wrapper, so the swarm still fires post-push where `fix-feedback` can anchor findings and the diagram still attaches once the code has stopped moving. Inverting it so the fix skill ran the tail itself would have broken both, silently
- **`/autopilot <flags>` mid-run is an amendment, and the rule that matters is what it does *not* touch**: the user's two real cases are "I got the verbal go-ahead, merge it" (`/autopilot --merge`) and "actually draw me the diagram and hold the merge" (`/autopilot --diagram --merge false`). So the flags it names change and **every flag it does not keeps its current run value, never the machine default** — re-reading `skill-env.sh` on an amendment would silently revert an earlier amendment, which is worse than ignoring the new one. Each flag then carries a defined catch-up for arriving late, because a flag whose moment has passed is the normal case rather than the exception: `--diagram true` publishes one even after the merge, `--review true` runs the swarm against what is pushed and feeds the findings into a fresh round, `--quick-description false` regenerates the description and replaces it on the change request while a late `true` is a no-op nobody wants, and `--merge false` **disarms an auto-merge already armed** — an armed auto-merge fires on green and would otherwise beat the instruction, which is the one amendment that can lose a race. `--autopilot false` means *stop driving*, never *undo*: nothing pushed is deleted and no change request is closed, because an agent tidying up after a change of mind is how work disappears
- **One flag surface across both fix skills, differing by machine and not by skill**: `fix-linear` and `fix-freeform` take the same seven flags with the same meanings, because the user types them interchangeably and a flag that meant one thing in one skill and something else in the other is a trap with no upside. They had diverged exactly that way — `--quick-description false` mapped to `changes-description --quick` in one and to the full panel in the other, a 4-agent difference behind an identical invocation. The split that *is* real runs the other way: work gets the full description panel, the diagram and the swarm and stops one step short of the merge because three people and two bots are going to read the change; home gets the one-shot, no diagram, no swarm and merges itself because nobody is. That belongs in `skill-env.sh` rather than the skill text for the reason every per-machine fact does — written into the prose, the two profiles' copies stop being transforms of each other and drift goes back to being invisible. `--branch` has exactly two values, `new` and `default`, in both skills; the old `in place` / `--here` / `no worktree` escape hatch is gone as a user-facing flag and survives only as the automatic fallback for a repo that cannot host worktrees, because a third value on that axis described a combination nobody reached for
- **The decision record is captured early and published late, and the two halves have opposite reasons**: an unattended run makes calls a reviewer never weighed in on, so they have to survive the run — but the first version posted them as their own comment on the change request, at the moment each decision was made, with no format and no budget. Every property of that was wrong in a different way. It was **in the wrong place**: a comment is the first thing a reviewer sees, ahead of the diff it discusses, and it cannot be collapsed. It was in the **wrong shape**: unedited generated prose with no word budget and no slop check, which is unreadable in exactly the way the thing it was replacing — a conversation — is not. And it was **unavoidably in a comment**, because `changes-description` does not run until Step 3 and the record was being written before that: there was no description to append to, so the comment was not a choice so much as the only surface left. The fix splits the two. **Capture stays at the moment of the decision** — a line appended to a local scratchpad ledger — because a ledger reconstructed at the end of a long run is reconstructed from memory and the entries it invents read exactly like the ones it remembers. **Publication moves to the end**, one edit appending the ledger to the description inside a collapsed `<details>` fold, which is the whole point: present for whoever wants it, invisible to whoever does not. Two things keep it short, and the filter matters more than the formatting: **an entry earns its place only if a reviewer could reasonably have decided differently**, which excludes following an existing pattern, doing what the ticket said, and anything the diff shows faster — and more than about eight entries means the filter was not applied rather than that the cap is too low. The budget is 25 words per entry against `docs-humanize`'s `HARD_SLOP`, matched on a whitespace-flattened copy. Three traps are written down because each one silently reintroduces the original problem: a `--quick-description false` amendment **replaces** the description and drops the fold, so it has to be re-appended from the ledger; the fold sits outside `changes-description`'s mechanical word budget and must never be handed to that skill as input; and a failed description edit **must not fall back to a comment** — it reports and carries the ledger in the run report, because the fallback is the exact surface the design exists to avoid
- **"Merged" is not "deployed", and the gap is where an unattended run lies without meaning to**: `autopilot` used to end at the merge, which reports on the easy half — the merge succeeds, the run says success, and the deploy goes red twenty minutes later with nobody watching. Two steps close it. **Step 0b runs before the merge gate**, which is the non-obvious half of the placement: a verifier that works out the deploy path *after* merging has already merged, and if it finds nothing it is too late to say so usefully — whereas run early it also tells a `--merge false` user what pressing the button will set off. It establishes the trigger (which jobs fire on a push to the default branch, *not* on a tag or a manual dispatch — a tag-triggered deploy does not fire on merge and saying it did is a lie with a green tick on it), the target (read the job, not its name — a job called `deploy` might print a plan and stop), and the observable signal, which is the one that gets skipped and the one that decides whether verification is possible at all. Plus two facts about the run's own position: whether this session can see the signal, and how long the repo's own recent runs take, which becomes the budget — a budget invented from nothing is either a false alarm or a watch that never ends. **It is derived contextually and never enumerated**, because repositories differ, the same repository changes, and a baked-in expectation is worse than none for the usual reason: it keeps passing after it has gone stale. "Nothing deploys" and "the path is unreadable from the repo" are both complete answers to record rather than gaps to paper over. **Step 10b then verifies the new revision, not that something succeeded** — every subtle post-merge failure has one shape, something green about the wrong commit: a pipeline that passed for the previous commit, a rollout that succeeded because the manifest never changed, a GitOps app Healthy on the revision it synced an hour ago, a mutable tag that let the workload restart onto the same image. All four are indistinguishable from success one step back, so every check is tied to the landed SHA. Five terminal states, and the value is in the last three: **cannot-observe and timed-out are never upgraded into success**, because being told a deploy worked when nobody established it is strictly worse than not checking — the user stops checking too. And it **warns, never remediates**: no rollback, no revert, no re-running a deploy job (Step 7's retry classification is about CI jobs, which are expected to be idempotent; a half-applied deploy run twice can do what neither run would), no touching the runtime. A `--branch default` run routes through it too and needs it most, since nothing reviewed that change and it is already on the branch every other checkout is cut from; in a stack an intermediate failure **stops the stack**, because merging the next change onto a broken default branch is how one bad deploy becomes three
- **Engaging autopilot is the gesture that arms the phone, so autopilot sends the opening ping**: notifications are opt-in per session and the opt-in is a *sent* ping — `notify.py` writes `armed_at` only on a successful send and otherwise logs `skip: session not armed`. Autopilot originally pinged only at Step 11, which arms the session **after the run is over**: the hours in between, where a permission prompt or an `AskUserQuestion` or a failure actually happens, ran into a session that could not speak. Observed exactly that way — a `/autopilot --merge` handed over mid-work, drove a change request to merge and verified the deploy, and never armed anything. So Step 0d sends one `progress` ping before the first unattended step, carrying what was taken over and where the run will stop, which does both jobs at once: it confirms the hand-off and it arms everything that follows. Four details keep it from becoming noise or a dependency. It is **skipped when `armed_at` already exists**, since the user has already opted this session in and a second announcement is just noise. It is **never sent on `--autopilot false`**, where there is no unattended tail and the user is at the keyboard by definition. **A failed send never fails the run** — an unconfigured `notify.json` makes it a no-op, and the `ping` skill deliberately withholds `armed_at` on a failed send rather than opting a session into notifications it was just told did not go out. And **every route in arms, the mid-run amendment included** — that is the route most likely to be missed, because the run is already in flight with Step 0d behind it, and it is simultaneously the clearest possible statement that the user is leaving
- **A pause is only graceful if it was affordable, which inverts where the work happens**: the moment a run needs to pause is the moment it has least quota to pause with, so a `/pause` that composes a twelve-section state file from scratch does not finish — and a truncated state file is strictly worse than none, because it reads as resumable. The run therefore **journals as it goes**: the step and round, the `next_action` as an instruction, and the decision ledger text, appended at every step boundary exactly as the ledger already is, so the pause itself is one atomic temp-file-and-rename. Everything else (forge state, `git` state) is read at pause time, which is cheap; prose is not. The second constraint is that **the state file must stand alone without the transcript** — by resume time the context may be compacted and the session closed, so a path to something is not a record of it. That is why the ledger is **inlined as text**: it lives in the session scratchpad, which is session-scoped and reaped by the OS, so a resumed run in a fresh session finds nothing and Step 11.3 publishes an empty fold. The corollary is that pausing *during implementation* is not supported at all — the interrogated statement, the locked plan and the gate answers exist only in the transcript, so that case stops and pings rather than parking
- **Stopping a run means stopping it, not noting what was running**: an armed `persistent: true` watcher survives a pause, wakes the paused session, spends the window the pause existed to protect, and hands control to a step that starts work — it un-pauses the pause. So `pause` `TaskStop`s every watcher and records a **re-arm instruction**, not an inventory. The same logic forces the unsafe-park list, where each entry is a specific mechanism rather than caution: an **armed auto-merge fires on green while you are away**, so it is disarmed first; a **dangling `AskUserQuestion`** is swallowed by a paused session along with the answer the user is mid-way through giving; a **merge whose deploy is unverified** turns a "paused" ping into "nothing is wrong" while production may be broken. One state had to be allowed rather than forbidden: a **running infrastructure apply can outlast a whole window on its own** and can be neither pushed through nor unwound, so pausing there is permitted, the hazard leads the ping, and resume re-reads the apply markers **per directory** before considering the apply comment — it is posted once and idempotently, and a resumed run that re-posts has triggered a second apply. The adjacent state worth naming: apply succeeded, merge not yet done, means infrastructure exists that no merged code uses
- **The resume trigger is a detached background poll on wall-clock, and all three of those words were wrong at first**: `Monitor` is the house mechanism for waiting, and it is wrong here because `timeout_ms` is hard-capped at 30 minutes against a window that can be hours out — ten re-arms, each a wake spending the budget being protected. A detached background command keeps running across turns and re-invokes the session once on exit; measured at 660s with exit 0, so the Bash `timeout` cap does **not** apply to `run_in_background`. The exit condition then has to be **wall-clock against the absolute `resetsAt`**, never the usage percentage: once the editor windows close, nothing refreshes the usage cache, so a poller waiting for a percentage to drop waits forever and reports nothing. And it compares `date +%s` rather than counting iterations, because a `sleep` loop stops accumulating while the laptop is suspended. The house rule that silence must never look like success binds the poller too — it emits on a missing cache, a stale cache, a `retryUntil` still in the future and a max-wait backstop, not only on a clean reset. **Auto-resume is session-window only**: a refreshed 5-hour window is a reasonable thing to restart on, a spent weekly quota is the user's call, and the stricter window always wins — so weekly, `scoped:<Model>` and `spend` are all re-read *at wake*, not trusted from pause time, since weekly can go from 70% to 99% while the poller sleeps
- **Quota is read from the `claude-usage` cache and never from the API**: `/api/oauth/usage` is rate-limited per account and the Claude Code CLI already polls it from every open session, so another caller is how a run throttles itself. The cache is written atomically (tmp + rename) so reads need no lock — and **taking `usage.lock` is forbidden**, because a holder makes every editor window skip its own refresh and a dead holder stalls them all for a minute; **writing anything into that directory** is equally forbidden, since a file-watch there fires in every window. `percent` is quota *used*, `resetsAt` is absolute epoch **milliseconds**, and the meter ids are `session`, `weekly`, `scoped:<Model>`, `spend` — all four get checked, because a `session` at 40% with a model-scoped meter at 100% fails every agent launched while the headline reads healthy
- **`/resume` is a built-in, so the skill is `/unpause`**: Claude Code already ships `/resume` as the past-session picker, built-ins are not skills and win the name, so a skill called `resume` is simply unreachable. Worth remembering as a class of bug — a skill name that silently never fires looks identical to a skill that does not work
- **A swarm's resume cache is keyed on the diff, and the chain of run ids is cumulative**: the `Workflow` cache is content-addressed over each agent's whole prompt and `review-code` embeds the literal unified diff in its `args`, so a single changed line changes all 26 keys — there is no per-file partial reuse to exploit. The ordinary pause (nothing happens in between) leaves the diff byte-identical and every finished agent replays free; a branch that **moved** while paused voids the cache entirely, and the right answer is a full re-run rather than a harvest, because the cached findings describe code that no longer exists and a partial review is not a review. Two traps on top. A resumed run journals only its **own live agents**, so resuming off the newest run id discards the previous generation — the state file keeps an **ordered chain** of every run id per logical swarm and `workflow-runs.py merge` unions them, which makes repeated pause/resume accumulate instead of reset. And **`cleanPrefix` is the wrong number to reason from**, because it counts only the contiguous run from the start: a 26-agent run that lost agent 3 reports `2` while 23 results sit cached and eligible, which read literally argues for re-running a run that is nearly complete. `resumeFromRunId` reuses every completed agent whose key still matches rather than a prefix, so **`finished` is the figure that predicts the saving** and `cleanPrefix` is a lower bound — neither gets recorded in the pause state, both get read fresh
- **`scriptPath` is a trap for resuming a swarm, and `workflow-resume` is the one place allowed near `resumeFromRunId`**: every `Workflow` call snapshots its script to disk and offers the path back for a cheap re-run, which is exactly wrong when the reason you are re-running is that the skill had a bug. The snapshot is frozen, so resuming through it silently replays the *pre-fix* pipeline while the run looks entirely normal — and it has already happened here once, a fixed skill bypassed by a `scriptPath` pointing at the snapshot from the very run it was fixing. `review-code` therefore forbids `scriptPath` and `resumeFromRunId` outright and names `workflow-resume` as the single sanctioned exception, because that skill pairs `resumeFromRunId` with the script **re-read from the live `SKILL.md`**. Both halves work at once for a non-obvious reason worth keeping: the cache keys each agent on its own `(prompt, opts)`, so an edit that does not touch an agent's prompt leaves that agent replaying for free and only the agents the fix actually changed re-run. The cache is reused *and* the correction is not discarded. The `script` subcommand of `workflow-runs.py` exists to **diff** snapshot against live so the cost is knowable before anything is spent — its own help text says diff only, never resend. Rewriting `workflow-resume` got this backwards on the first attempt, which is the argument for the rule being written down somewhere other than the skill it protects
- **Recorded authority survives a pause; recorded evidence does not**: a `--merge true` chosen before a five-hour gap still authorises the merge, because a run that stops to re-ask has failed at being unattended — but the approvals, the pipeline state and the apply markers are all re-read, and the ordinary gates then apply to what is actually found. `require_human_approval` is unchanged by a pause. This is why forge state is recorded as *inputs to a diff* and never as substitutes for looking, and why thread state needs an author class plus committed/pushed flags rather than a flat list of ids — a finding the run posted and never fixed is not new reviewer feedback, and treating it as such duplicates both the comment and the fix. Per-job CI retry counts go in for the same reason: without them a resumed run blind-retries a failure it already retried, which is the single most damaging unattended behaviour. And `diagram_attached` / `ledger_published` go in because Step 11 is only partly idempotent — without them resume appends a second collapsed fold to the description
- **Run state belongs outside the repository, and the old path proved why**: `git/ignore` covers only `**/.claude/settings.local.json`, so `autopilot`'s original `.claude/autopilot/<run>/stack.json` sat untracked in whatever repo the run happened in — visible in `git status`, committable by a run that stages broadly, and noise in the pause state's own dirty-tree diff. Both it and `~/.claude/pause-state/` now live under `~/.claude`, which is outside every repo. The pause state is keyed by repo and branch rather than by session id so a *different* session can find it, and a `SessionStart` hook already exists in every profile if automatic discovery is ever wanted; a stack run additionally records the ordering and which members merged, or "never arm auto-merge on a change request whose predecessor has not merged" breaks on resume. A state file nothing expires is a loaded gun, so resume checks for a superseded run — merged elsewhere, branch deleted, recorded HEAD unreachable — and archives rather than acting
- **A resumed run must enter its worktree before anything else**: the wake can land while the session's working directory is somewhere else entirely, and **subagents inherit the session's working directory** — so a swarm launched from the wrong place reviews the wrong repository and looks entirely plausible doing it. The wake is also an event rather than a user turn, so an interleaved wake authorises no irreversible action (no push, merge, apply or comment) without announcing itself first: a merge arriving unannounced while the user is mid-conversation about something else is indistinguishable from a bug. And the one free moment to ask is an interactive gate — a blocked `AskUserQuestion` spends nothing while it waits, so the threshold cannot be crossed during the wait, and when the answer does arrive the user is demonstrably at the keyboard; that is the one point where "the window is nearly out, pause or push on?" is both cheap and correct rather than decided silently from a threshold
- **Review findings are persisted, not just chatted**: a `review-code` swarm finding lives only in the transcript, so `fix-feedback` Step 3b posts every finding the MR does not already carry as its own anchored comment *before* working through the queue — deduped against the MR's existing threads (fetched, not assumed from context) and against comments an earlier run posted, which it recognises by their `🤖 review-code` header. Posting is one batch approval; a posted finding gains a discussion ID, so the reply drafted when the user rejects or modifies it lands back on that same thread
- **Hooks**: One script per hook under `.claude/hooks/`, duplicated across profiles like `scripts/`. Two live there: `link-worktree-session.py` and `notify.py`. Register it in every profile's `settings.json` using `$HOME/.claude/hooks/<name>` so the path resolves on any machine. **Claude Code spawns hooks with a bare `PATH`**, not your shell's — a `#!/usr/bin/env python3` hook resolves at your prompt and never under mise, and the failure is silent from the user's side, so the installer probes each hook under `env -i PATH=/usr/bin:/bin` rather than trusting that linking it was enough. `link-worktree-session.py` additionally needs a **backfill** at install time: linking it only arms future sessions, while every transcript written before this run is still filed under its worktree's own project slug where the main checkout's window never looks. It makes each worktree's `~/.claude/projects/<slug>` a **directory symlink** to the main checkout's, never per-file links: Claude Code 2.1.296's panel lists only the main slug and opens transcripts with `O_NOFOLLOW`, so a symlinked transcript is dropped after every reload, while a symlinked directory turns Claude Code's own move-on-`EnterWorktree` into a no-op and leaves each transcript a real file
