# Demeter — Shared Dotfiles

## Project Overview

Demeter is a shared dotfile repo. Each machine setup lives in its own profile directory under `profiles/`. An interactive install script symlinks everything to the right places on any machine (macOS or Linux).

## Install Script (`install.sh`)

The installer does the following in order:

1. Selects the profile to install — from the first CLI argument (a `profiles/` subdirectory name or a path), else auto if only one profile exists, else prompts. `install.sh --help` lists available profiles, and `-y`/`--yes` answers every prompt.
2. Detects machine type — macOS = `mac`, a Raspberry Pi (`/etc/rpi-issue` present) = `pi`, any other Linux = `linux`. The Pi needs a type of its own rather than sharing `linux` with the rdev box: `SKIP_LIST` is keyed by machine, and the two need opposite treatment
3. Initializes git submodules if `.gitmodules` exists
4. Symlinks dotfiles from `profiles/<profile>/` to `~/` (skipping `.claude/`, and any path listed in `~/.rdev-managed.json` on an rdev box)
5. Symlinks `shell/` config (`terminal.zsh` to `~/.config/zsh/`, `starship.toml`, `tmux.conf`) and offers to install any missing terminal tool or zsh plugin
6. Symlinks `.claude/` contents individually (skills linked per-directory into `~/.claude/skills/`)
7. Unifies worktree project dirs into their main checkout's by running `.claude/hooks/link-worktree-session.py --backfill`, first probing it under a bare `PATH` (`/usr/bin:/bin`) — the environment Claude Code actually spawns hooks in
8. Seeds `~/.claude/notify.json` (mode 600) from the profile's `notify.json.example` when absent, probes `notify.py` under the same bare `PATH`, and names the fields still set to `REPLACE_ME`. Never overwrites a filled-in config
9. Seeds `~/.claude/environment.json` from the profile's `environment.json.example` when absent, then runs `skill-env.sh check` and reports whether the forge API helper it resolves to is actually installed. Never overwrites an existing config, and a malformed one is a warning rather than a failure — the skills fall back to the defaults compiled into `skill-env.sh`
10. Copies the staged MCP token file to `~/.claude/.mcp.json` at mode 600 when `~/.config/nvim/mcp.json` exists. That path is an allowlisted slot in rdev's persisted-files service — not an nvim integration — which restores the file from GCP at instance provision, so this step is the rename that puts the tokens where everything reads them. The copy is unconditional on purpose: the staged file is the source of truth, so a rotated token propagates on every run. A no-op on every machine without that path
11. Symlinks vendor skills from `_vendor/*/` into `~/.claude/skills/`
12. Symlinks shared tools from `tools/*` into `~/.claude/tools/`
13. Prompts to build and install shared tools exposing an `install` target in their Makefile. Runs through `mise exec` when the tool has a `.mise.toml`, so a pinned toolchain resolves in a non-interactive shell. Skipped without prompting when no editor CLI answers `--list-extensions`; otherwise the CLI it resolved is passed to `make install` as `CODE=`, since the Makefile's own `code` lookup fails outside the integrated terminal. Verifies afterwards that the tool's extension id is registered, since a build can succeed without the editor picking it up. Honours `SKIP_LIST` by tool directory name.
14. Symlinks `vscode/settings.json` over VS Code's user settings, on every editor user directory that already exists
15. Sweeps repo workspace `.vscode/settings.json` files for color keys the shared settings own, via `vscode/strip-stale-peacock-keys.sh`
16. Symlinks `git/ignore` to the machine-wide gitignore git actually reads, and verifies it took
17. Prompts to install any extension in `vscode/extensions.txt` missing from the editor. Each `--install-extension` runs under a timeout (`EXTENSION_INSTALL_TIMEOUT`, default 180s) and is then judged by `--list-extensions`, because the server CLI can finish installing and never exit
18. Cleans stale skill symlinks (removes symlinks pointing to deleted repo paths)
19. Creates data directories for skills that accumulate context, gated on the skill being linked — a profile that ships no `reflect-*` gets no `reflect-*/context`
20. Runs `profiles/check-transform.py` to report profile drift — **warning-only**, and skipped without complaint when `python3` is absent

Key behaviors:
- `-y`/`--yes` answers every prompt instead of reading stdin, and is propagated to `vscode/strip-stale-peacock-keys.sh`, the only sub-script that prompts. It **refuses to run without an explicit profile** when more than one exists: profile selection is the one prompt with no safe default, and defaulting it links another machine's dotfiles over yours. It deliberately consumes no stdin, so `yes | ./install.sh <profile>` keeps working for anything already written against it — the flag's advantage is an exit status that is the installer's own rather than `141` from `yes` catching a `SIGPIPE` under `pipefail`
- Never copies `~/.claude` aside; it only replaces symlinks, leaving your session data in place
- Backs up existing real files before replacing
- Skips already-correct symlinks
- Removes stale skill symlinks that point into the repo but whose target no longer exists
- Respects `SKIP_LIST` for machine-specific files (format: `"filename:machine"`, machine = `mac` | `linux` | `pi` | `both`). It is honoured by the dotfile loop, both `.claude/` loops, `link_directory_contents`, and every `vscode`/`shell`/`tools`/`gitignore` step gate — a new step that skips none of those will fire on a box with no editor
- `.claude/CLAUDE.md` is symlinked to `~/.claude/CLAUDE.md` — the user-level instruction file loaded in every repository (no installer change was needed; the top-level `.claude/` file loop already handles it)
- `settings.json` is **symlinked** like everything else, and only *copied* with `__DEMETER_REPO__` path templating when the profile's copy actually contains that token — templating cannot write through a symlink. No profile uses the token today, so in practice every profile's `settings.json` is a symlink, which is what lets `/config` edits land back in the repo as a tracked diff. The corollary bites on a box whose `settings.json` is owned by something else: a symlink there sends `/config` writes into the clone, leaving it dirty so the next pull silently stops fast-forwarding. That is why the `pi` profile ships no `settings.json` at all
- `settings.local.json` lives at `.claude/.claude/` and is symlinked normally
- `.mcp.json` holds every MCP server's token and is **never committed**. On most machines you write `~/.claude/.mcp.json` by hand. On an rdev box it arrives from GCP through rdev's persisted-files service at the allowlisted path `~/.config/nvim/mcp.json` — an available slot, nothing to do with nvim — and step 10 copies it into place at mode 600, which also hardens a staged file that arrived looser
- `.claude/hooks/` is linked per-file into `~/.claude/hooks/` by the same `.claude/` directory loop; the hooks that run from there are registered in each profile's `settings.json`
- `tools/` is profile-independent and linked per-directory into `~/.claude/tools/`. Linking only makes the source available, so a tool exposing a Makefile `install` target is then offered a build (step 13) — the symlink alone gives no signal that an installed artefact is older than the source
- `vscode/extensions.txt` is the companion to `settings.json`: a theme named in settings does nothing until its extension exists, and VS Code falls back silently. The installer only ever **adds** — a locally-installed extension missing from the list is left alone. `vscode/sync-extensions.sh` writes the list back from a machine; it excludes extension ids published from `tools/*/package.json`, which are not on the Marketplace and are installed by their own make target. `editor_cli()` resolves the CLI and `read_extension_list()` parses the file (`#` comments and blanks ignored) — both from `vscode/lib.sh`, shared with the installer
- `vscode/settings.json` is profile-independent and symlinked **wholesale** over the editor's user settings (`~/Library/Application Support/Code/User/` on mac, `~/.config/Code/User/` on linux, plus Insiders and VSCodium when present). Because it is a symlink, VS Code writes UI changes back into the repo — machine-specific keys (`window.zoomLevel`, `claudemeter.debugLogFile`) are kept last in the file so they stand out in a diff. `vscode_user_dirs()` in `vscode/lib.sh` resolves the paths; `should_skip "vscode" "$machine"` opts a platform out
- `vscode/strip-stale-peacock-keys.sh` is the counterpart to `peacock.excludedSettings`: an exclusion stops Peacock writing a key but never removes the copies it wrote before, and a workspace file outranks the shared settings, so the pin loses silently in exactly the repos nobody thinks to check. The sweep reads the owned-key list out of `vscode/settings.json` (never hardcodes it), scans `$HOME` five deep with `PEACOCK_SCAN_ROOT`/`PEACOCK_SCAN_DEPTH` overrides, prompts once with what it found, and re-parses every file it edits to prove only the owned keys left — a file whose keys share a line is reported, not rewritten. Run standalone or let step 15 run it
- `git/ignore` is profile-independent and linked to **`core.excludesFile` when it is set, else `$XDG_CONFIG_HOME/git/ignore`** — `git_excludes_path()` in `lib/paths.sh` resolves that, expanding a leading `~`/`$HOME`. Linking the XDG default is what makes it need no `git config` at all, and linking the configured path instead is what keeps a machine that sets `core.excludesFile` (an rdev image, say) from leaving the file inert. `is_rdev_managed` opts that path out, `should_skip "gitignore" "$machine"` opts a platform out. The step then runs `git check-ignore` in a throwaway `git init` (`git_ignores_probe()`) rather than trusting the symlink, because every failure mode here is silent
- Idempotent — safe to re-run after pulling changes

## Conventions

## Conventions

Each bullet is an invariant, then the doc that explains why. Read that doc before changing
anything in its subtree.

- **One profile directory per machine setup**, under `profiles/` (e.g. `larrabeedylan_work_linux`)
- **Dotfiles only**: Files in profile directories should be dotfiles (prefixed with `.`) or inside `.claude/`
- **No secrets in repo**: Sensitive values (API keys, tokens) belong in `~/.secrets` or similar, sourced from shell config — never committed
- **Machine-specific skipping**: Use the `SKIP_LIST` array in `install.sh` to control per-platform linking
- **rdev boxes**: rdev regenerates `~/.zshrc` and `~/.tmux.conf` and lists them in `~/.rdev-managed.json`; customize through `~/.zshrc.local`, `~/.zshrc.pre` and `~/.tmux.conf.local`, never a managed file. → `shell/AGENTS.md`
- **The MCP token file is hand-placed everywhere except rdev**: `~/.claude/.mcp.json` carries every MCP server's token, so it is never in the repo. rdev instances are disposable and its persisted-files service only carries an allowlisted set of paths, which `~/.claude/.mcp.json` is not — so the file is restored from GCP into the allowlisted slot `~/.config/nvim/mcp.json` and the installer completes the rename. The overwrite is **deliberate**: the staged file is the source of truth, so gating it on `! -e` would stop a rotated token propagating, and nothing would report that. → `README.md`
- **The Pi profile is an identity transform**: it symlinks `skills/`, `hooks/` and `scripts/` into the home profile and ships no `settings.json`, no user-level `CLAUDE.md` and no dotfiles. → `profiles/larrabeedylan_home_pi/AGENTS.md`
- **One owner per path family**: `lib/paths.sh` and `vscode/lib.sh` own the resolvers, and a new `link_file` destination must fall under a root declared in `demeter_link_roots` or CI fails. → `lib/AGENTS.md`
- **`comm` needs one case and one collation**: `vscode/sync-extensions.sh` lowercases both sides and pins `LC_ALL=C` on every `sort` and `comm`, because `comm` does not validate its input. → `vscode/AGENTS.md`
- **A glob with no match is a filename**: the `.claude/.*` loop ran unguarded for months and, on every profile with no hidden entries in `.claude/` (which is all of them), created a dangling symlink in `~/.claude` literally named `.*`. It had been there since July before anyone looked. `[[ -e "$src" ]] || continue` is the fix, and the general rule is that an unguarded glob feeding `link_file` creates garbage rather than doing nothing. `link_directory_contents` also skips `__pycache__` outright — it is gitignored build cruft, so publishing it into `~/.claude` is wrong on every machine and would ship one architecture's bytecode cache to another
- **Nothing in the installer may be fatal on an unattended run**: the submodule update was a bare command under `set -e`, so a flaky network at 04:30 aborted the whole run and installed nothing. It warns now. Any step that can fail for a reason outside the repo needs the same treatment, because the Pi's timer has no one watching it
- **Skills**: Each skill gets its own directory under `.claude/skills/` with a `SKILL.md` file
- **An empty diagram is worse than no diagram**: `changes-diagram` guarantees a non-empty diff produces a non-empty chart, and records which mode it drew. → `profiles/<p>/.claude/skills/AGENTS.md`
- **The diagram's publish target is configuration**: a new external resource must clear the Artifact tool's CSP allowlist or it fails invisibly, a local file is a success, and the self-hosted branch goes through `publish-artifact.sh` rather than discovering a command at runtime. → `profiles/<p>/.claude/skills/AGENTS.md`
- **The diagram is drawn before the merge, because the merge destroys what it reads**: `autopilot` attached it at Step 11 for a sound reason — a diagram of a branch that changed three more times is worse than none — and by then Step 9 has merged, **Step 9a has deleted the source branch** and **Step 10d has removed the worktree**, while `changes-diagram` derives its base as `merge-base(<default>, HEAD)` and diffs base → **working tree**. So the working tree was the default branch, the diff was empty, and that skill's own Step 2 says to stop — it names an already-merged branch as the likely cause. The two skills disagreed and the one right about its own inputs lost; because a failed diagram never fails the run, `--diagram true` bought one line of apology. The attach is now **Step 8b**, between the apply gate and the merge, where the review is settled, no further push is expected, and the branch, the worktree and an open change request all still exist. Six things carry it. **After Step 8 rather than before**, since the apply gate can send a run back to Step 6 with a code change — the exact staleness the late attach existed to prevent. **That same loop makes the step re-enterable, so the append had to become idempotent**, which is the one defect the move introduced and which the review swarm found: Step 11 was terminal and post-merge, Step 8b is re-entered whenever a blocking verdict routes back through Step 6 branch 1, and a first draft saying only "append its link" grew a `**Diagram:**` line per round. **The fix is a redraw, not a skip** — skipping would leave the diagram describing pre-round code, so the step redraws against the **recorded update hash**, since a fresh invocation without it mints a second page and strands the url already in the description, and appends only when no `**Diagram:**` line exists. **The bug needed `--merge true`**, which is why it survived: `--merge false` ends at Step 9 and reaches Step 11 with the branch intact, so that path worked and still does, now with the link on a change request a reviewer can still act on. **The checklist item moved with the step**, ahead of `merge`/`ready`, because a page listing the diagram after the merge describes an order the run no longer follows; `tests/check-run-checklist.py` pins the ordering, having asserted membership only. **The post-merge path is documented rather than deleted**, since the amendment table already promises to honour a late `--diagram true` — and the recipe is a *worktree*, not a base: the builder reads the before-side with `git show <base>:<path>` and the after-side with a plain **file read**, so a base alone leaves the after-side as whatever the default branch holds now, this change plus everything merged since. `git worktree add --detach <path> <sha>` with `BASE=<sha>~1` pins both sides and needs no script change. And **`<sha>~1..<sha>` is refused by name**, because it is the trap the ticket proposing it fell into: `git diff --name-status`, `--numstat` and `--unified` all accept a range and return the right file list, so the build succeeds with a plausible node count, while `git show "<sha>~1..<sha>:<path>"` returns nothing and that empty result becomes "no before-side" — every file renders as **added** and the page is confidently wrong rather than absent. Both halves measured: the range gives 7 changed files where the plain base gives 21, and the `git show` form is empty. → `profiles/<p>/.claude/skills/AGENTS.md`
- **The diagram page's first reader is a phone, and the page must say so**: the link is opened from a push notification, so the phone is the primary reader rather than a degraded one. Four things carry that, and the first is the one a laptop can never catch. **The template declares `<meta name="viewport" content="width=device-width">`** — without it a 390px device laid the page out at **930px**, measured, and shrank the whole thing, which is both "the diagram is too zoomed out" and text wrapping as if the column were wide. **The opening view clamps to a legibility floor**, 8px of label, anchored top-left where a `DOWN` layout puts the entry points; fitting everything scaled a 91-node graph's labels to **0.5px**, so `fit()` stays behind the `Fit` button and is never the view you arrive at. **Taking the touches means owning the gesture**: `touch-action: none` switches the browser's own pinch off, and the handlers tracked one pointer, so a pinch was processed as a pan and the buttons were the only zoom on a touch screen. And **a resize may not discard the view** — on a phone it fires every time the URL bar hides, so the diagram snapped back to fit mid-pan; centre and scale are preserved, and a `ResizeObserver` covers the full-screen toggle that no window resize reports. The view maths sit in a `<script id="view-math">` block **outside** the IIFE so the test runs them under `node` with nothing stubbed, which is the `vscodeStub.ts` trap avoided rather than repeated, and `tests/check-diagram-template.py` also pins the three profile copies byte-identical — `check-transform.py` only ever looked at `SKILL.md`. → `profiles/<p>/.claude/skills/AGENTS.md`
- **A skill must never hardcode what differs between machines**: `scripts/skill-env.sh` is the seam, and **an empty value means the capability is absent here, never "go and guess"**. → `profiles/<p>/.claude/skills/AGENTS.md`
- **One script reaches the self-hosted artifact store, and five keys carry the machine difference**: `publish-artifact.sh` prints the URL or exits **3** to mean "no such store here", which is the ordinary answer on a work box rather than a failure. A caller passes `--purpose plan|diagram|tasks` and the script resolves the folder, because `${FOLDER:+--folder "$FOLDER"}` in a skill body yields two arguments under bash and **one** under zsh. The purpose also makes the page **public** — a private artifact is a 404 without an admin session and the management URL redirects to `/login`, so every plan and diagram was unreadable by the only person it was published for. **`mark_gate` stays `plan`-only**, and `tests/check-publish-artifact.sh` pins that: the `tasks` page is published before a run's first step and rewritten at every boundary after it, so a gate marker set by it would refuse the first turn end of every run and one more per update. → `profiles/<p>/.claude/skills/AGENTS.md`
- **A run's obligations live on a published page, not in its context window**: `autopilot`'s arming instruction appeared in that file **twice** and a real run skipped it anyway, so the fix is a thing the run reads and ticks rather than a third sentence. `run-checklist.py` seeds the page from the **resolved flags** — it cannot list a diagram the run will not draw nor omit a merge it will perform — and embeds its own items as JSON, so re-reading the artifact hands them back as **data rather than prose to parse**. Four things are load-bearing. **The URL never changes**: the first publish records the identity and every later write is an `--update` against it, because the link sits in the change request description from the moment it is opened and a second plain publish freezes the page the user is holding at step one, with nothing reporting it. **"Nothing armed" is computed, never asserted** — outstanding work with no item in flight renders as an alarm, which is what makes the never-yield rule checkable. **A `skipped` item carries a reason and an `in-flight` item carries a blocker**, both enforced, since "skipped" alone records that an obligation was dropped and nothing about why. And **`/unpause` reads the page before its first write**, because a publish to an artifact the conversation has not read is refused and a fresh session is the normal case there. → `profiles/<p>/.claude/skills/AGENTS.md`
- **A page the user is told to refresh must be worth refreshing**: the run checklist's footer said *refresh to see where the run is* and the page offered nothing to refresh with and discarded your scroll position when you did — on a thirteen-item run, on the phone that is the only device it is opened on.
