# `lib/` — the resolvers the three scripts share

`install.sh` creates links, `uninstall.sh` sweeps them, and `tests/` proves the two agree.
They agree because all three consume one set of resolvers rather than each computing paths
for itself: `lib/paths.sh` owns `git_excludes_path` and `demeter_link_roots`, and
`vscode/lib.sh` owns the editor concern.

Two rules bind anything added here. **A lib must be pure** — it computes and echoes,
never prints through `info`/`warn`/`success`/`error`/`bold`/`ask`, because those are
defined separately in each of the three callers. And **the include guard needs `if`, not
`&&`**, since `[[ -n "$x" ]] && return 0` returns 1 when unset and aborts the sourcing
script under `set -e`.

Adding a link root to `install.sh` means adding it to `demeter_link_roots`.
`tests/check-link-roots.sh` fails CI otherwise, which is the only guard that would have
caught the bug this file exists because of.

## Why the resolvers were hoisted

### One owner per path family, and the uninstaller sweeps a declared list rather than guessing at trees

`uninstall.sh` scanned exactly two trees — top-level `$HOME` dotfiles and `~/.claude` recursively — while the installer kept gaining link roots outside both. By November it could not reach `~/.config/zsh/terminal.zsh`, `~/.config/starship.toml`, `~/.config/git/ignore` or `~/.vscode-server/data/Machine/settings.json`, so an uninstall left a machine **still sourcing repo files** and printed `Done. Removed N symlink(s)` while doing it. The drift ran from September to November with nothing reporting it, and the mechanism was duplication rather than a missing path: the uninstaller hardcoded the six editor directories the installer computes in `vscode_user_dirs()`, so the two directions could not help diverging. Two libs now own the resolvers and all three scripts consume them — `vscode/lib.sh` for the editor concern (`editor_cli` and its candidate probe, `editor_has_extension`, `tool_extension_id`, `read_extension_list`, `vscode_user_dirs`) and `lib/paths.sh` for `git_excludes_path` and the new `demeter_link_roots`. Five things are load-bearing. **A lib must be pure**: `info`/`warn`/`success`/`error`/`bold`/`ask` are defined separately in each of the three scripts, so a lib that printed through one would work in some callers and break in others — every function here only computes and echoes. **The include guard needs `if`, not `&&`**: `[[ -n "$x" ]] && return 0` returns 1 when unset, and under `set -e` that aborts the script doing the sourcing, so the guard is a real `if` block; the same trap bites `cmd && var=()` as the last statement of a loop body, which silently exits a command-substitution subshell. **`demeter_link_roots` emits both platforms' editor directories**, because the uninstaller detects no machine type and a path that does not exist is simply skipped. **A declared list can still go stale, so it is checked mechanically**: `tests/check-link-roots.sh` parses every `link_file` destination out of `install.sh` and fails when one falls under no declared root, or when a destination leads with a shell variable the checker does not know — a new link root therefore fails CI instead of going quietly unreachable, which is the only guard that would have caught the original bug. And **the round-trip is tested on a scratch `HOME`, not on the real installer**: driving `install.sh` for real would pull submodules, install terminal tools and build three VS Code extensions, so the test plants a symlink under every declared root and asserts `uninstall.sh --yes` leaves none — with two controls, a nonzero planted count so it cannot pass vacuously, and a link pointing outside the repo that must survive so a sweep deleting everything cannot pass either. Measured against the old script, 11 of 12 planted links survived; one of those was at `$HOME` top level, because the old loop globbed `"$home"/.*` and could not see a symlink without a leading dot. `uninstall.sh` gained `-y`/`--yes` for that test, mirroring the installer's flag, because `yes |` under `pipefail` exits `141` on `SIGPIPE` and the test could not tell a pass from a crash. Three consequences are deliberate rather than incidental. The uniform `find -maxdepth 1` **widens the `$HOME` pass from dotfiles to every symlink there**, since the old loop globbed `"$home"/.*` and could not see a link without a leading dot — a real behaviour change, accepted because it is what makes a `core.excludesFile` of `~/gitignore_global` reachable, and documented in `README.md` rather than special-cased. The **backup restore is offered only where the sweep actually removed our link**, tracked in `REMOVED_LINKS`, or a `-y` run would copy an old `settings.json.bak.<ts>` over a file this repo never owned. And **the test must prove its sandbox before it creates anything**: `git_excludes_path` reads `core.excludesFile` and `XDG_CONFIG_HOME` from the environment, so a root resolving outside the scratch `HOME` would mean the test plants symlinks in the developer's real config directory — it asserts every declared root is inside the scratch tree first, and that assertion was verified to fire by pointing `GIT_CONFIG_GLOBAL` at a config with an absolute `excludesFile`
